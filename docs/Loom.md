# 1. 概述

## 1.1 背景与问题

多智能体系统已具备处理复杂任务的能力，但**把它们组织成可靠系统的工程方法尚不成熟**。生产环境中反复出现以下问题：

**P1 · 协作状态无结构。** 多 Agent 协作的主流实现是"让 Agent 之间聊天"。这带来三个衍生问题：重复通信（prompt stuffing）、上下文污染（一个 Agent 的错误推断影响全链）、以及状态散落在对话历史中无法审计。随着任务复杂度上升，Agent 花费大量 token 重新确认"我们已经知道什么"。

**P2 · 编排即硬编码。** 常见工作流引擎把执行顺序写死在代码或配置中。任务特征、Agent 负载、依赖关系、优先级这些真实调度信号无法进入决策过程。结果是：简单任务被过度编排（付出协调成本却无收益），复杂任务因缺乏弹性而中途卡死。

**P3 · 验证环节被架空。** Agent 输出"看起来合理"就被采纳。缺乏确定性的验证节点、交叉复核、以及对"验证者自身的假通过"的防护。错误在协作链上逐级放大，而系统无法回答"这个结论是怎么来的、凭什么可信"。

**P4 · 失败恢复方式单一。** 失败即重试。重试不区分失败成因——网络抖动、凭据失效、作用域越界、逻辑缺陷被同等对待。结果是有效重试预算被浪费，且"重试 N 次"这种朴素循环无法应对"生成结果与验收标准系统性偏离"这类问题。

**P5 · 长任务不可复现、不可审计。** 缺乏统一的事件流、状态快照与幂等提交协议。进程崩溃后无法恢复，评审者无法复现一次运行的完整轨迹，"为什么当时这么做"这类问题没有答案。

**P6 · 系统与领域耦合。** 为一个具体场景实现的多 Agent 系统，业务逻辑与协作机制缠绕在一起。更换领域意味着重写调度、验证与恢复逻辑，沉淀不下来。

**P7 · 评估自证。** 领域包同时提供场景、判据与工具时，"本领域成功率 100%"是一句无法证伪的话——出题、判卷与答卷来自同一方。缺少与领域无关的、由平台侧持有的中性基准，任何效果数据都不可信。

**P8 · 副作用无重放语义。** 事件日志保证了平台内部写入的幂等，但无法覆盖已经发生在外部系统的写操作。崩溃恢复时"重跑一遍"的朴素假设，对写操作不成立。

## 1.2 目标与非目标

### 1.2.1 目标

| 编号 | 目标 | 可度量结果 |
|---|---|---|
| G1 | 提供多智能体协作的编排、调度、执行与验证内核 | 覆盖五项能力；完整需求见 FR-001–FR-062，按 §12.1 分阶段交付 |
| G2 | 协作状态结构化、可追溯、可回放 | 历史事件与保留对象可重建任意已提交时点；回放不调用模型或写工具（FR-042/043、NFR-009/015） |
| G3 | 调度可解释并具备可验证的适应能力 | 任务优先级选择与 Agent 选型分离；每次派单记录候选与权重；收益通过对照实验验证（FR-011–019） |
| G4 | 验证不可被运行主体绕过 | 确定性门禁、受信证据与内容绑定双签；例外接受独立统计（FR-023/025/034/053–055） |
| G5 | 失败分类处置并可定向修复 | 七类失败、六原语；停止条件区分成功、停滞、预算耗尽和人工介入（FR-022/029–035） |
| G6 | 平台与领域解耦 | 新领域零内核代码变更；受信评测适配器独立发布，不能由 Pack 自评代替（NFR-011/013） |
| G7 | 覆盖设计、开发、测试、部署与运行 | 每阶段有可执行出口标准；测试与隔离能力先于被依赖的功能（§1.8、§12.1） |
| G8 | 沉淀可复用模板与策略 | 版本化分发与适用域匹配；允许有价值的域内复用（FR-057、§9.7） |
| G9 | 效果数据可证伪 | 平台一致性、独立 held-out 效果评测和领域自评分开存储、分开报告（FR-060/061、§10.7） |

### 1.2.2 非目标

| 不做 | 理由 |
|---|---|
| 不做通用大模型推理服务 | 平台通过**模型网关**接入既有推理服务，不自建推理栈 |
| 不做低代码可视化编排画布 | 编排以代码化 DSL 为一等公民；可视化是可选前端视图，不是核心抽象。可视化拖拽编辑列为 P2 |
| 不做跨厂商 Agent 互操作网关 | 内部 Agent 协作走自有协议；跨厂商互操作的收益/成本比在当前阶段不成立（见 §9.1 决策记录 ADR-008，§1.5 展开） |
| 不做模型训练与微调平台 | 平台消费模型能力，不生产模型能力 |
| 不做通用工作流引擎的"全功能"覆盖 | 聚焦 Agent 协作语义（意图、断言、证据、修复），不追求覆盖任意批处理场景 |
| 不做多租户 SaaS 商业化 | 多租户隔离是**架构要求**（FR-044/045），但商业形态不在本期范围 |

## 1.3 关键设计原则

以下原则约束实现。生产不变量必须通过动态故障测试验证，静态 import 或关键词检查仅作辅助。

| # | 原则 | 含义 | 违反后果 |
|---|---|---|---|
| **P1** | **事件是已提交业务状态的唯一历史真相源** | 业务状态与控制账本变化同事务写事件；投影可重建。claim、容量、预算表是事务内的命令约束账本，不是可独立漂移的第二份业务真相 | 无法解释状态或安全恢复 |
| **P2** | **模型不能决定硬门禁通过** | 门禁为确定性代码；模型结论只是待验证建议，语义评价由明确授权的独立评测渠道提供 | 自评放行 |
| **P3** | **给门供证据，运行中不改门** | run 绑定验收与规则快照；生产侧修复不能降低硬约束 | 目标漂移 |
| **P4** | **修生产者，不松验证器** | 人工业务例外使用 `accepted_with_exception`，不计普通验证成功，不消除失败事实 | 失败被伪装成成功 |
| **P5** | **表达力与放行要求分离** | 扩展动作能力不自动放宽判据，判据变更须独立版本与评审 | 判据随功能漂移 |
| **P6** | **安全底线与运行快照不可由执行主体修改** | 内核安全底线受发布流程保护；授权发布者可发布新规则版本，旧 run 保持冻结。紧急拒绝/撤销可立即收紧，不能放宽在途授权 | 隐式关闭防线 |
| **P7** | **区分能力正确率与端到端完成率** | 网络故障不计为模型能力错误，但在完成率、耗时和成本中如实呈现 | 效果数据选择性排除 |
| **P8** | **规则语法安全不等于语义可信** | Pack 提供声明与规则；受信指标只由获授权执行器写入，独立评测不由 Pack 控制。声明式规则不能自动证明领域真值 | 自报指标与规则放水 |
| **P9** | **未知外部效果不自动重做** | 只有具备稳定调用标识、持久发起记录和可靠幂等契约的动作才可安全恢复；记录可能丢失的窗口冻结核对 | 重复外部动作 |
| **P10** | **调度不依赖异步展示投影授权派发** | 单写者负责分片候选计算，claim、容量、预算由数据库原子预占。内存缓存可加速，不能代替全局约束 | 多副本超配和重复认领 |

## 1.4 术语

| 术语 | 定义 |
|---|---|
| **协作状态图 / 三层图** | 平台的核心状态模型。L1 目标层（Goal）、L2 策略层（Intent）、L3 执行层（Task），横切 Artifact / Observation / Anchor |
| **领域包 / Pack** | 领域知识的可插拔单元。提供角色、工具、门禁参数、收敛阈值、场景库，不引入内核逻辑 |
| **Anchor** | 系统不可自改的外部参照（冻结验收标准、held-out 评测集、人工审批记录等） |
| **Fact-family 失败** | 按成因而非表象划分的七类失败（quota/network/scope_denied/canceled/crash/auth/other） |
| **修复原语** | 六种定向修复动作（Rebind/InsertPrereq/Substitute/Rewire/Bypass/Escalate） |
| **门禁 / Gate** | 确定性结构校验节点（Gate-D1 / Gate-V / Gate-R / Gate-P） |
| **投影 / Projection** | 由事件流派生的只读状态视图（协作图、看板、记忆索引） |
| **意图 / Intent** | L2 层节点：一个待执行、有明确支撑事实与成功判据的探索方向 |
| **轮次 / Round** | 同一 L2 意图下的一次修复-重试循环计数 |
| **交接物 / Handoff** | Agent 之间传递的结构化产物或证据引用；**不含自由文本指令** |
| **门禁分层** | 内核门（谓词在内核，不可被覆盖）与领域门（Pack 只提供参数化实例）两层 |
| **声明式规则 / Declarative Rule** | 无副作用、无 IO、无外部调用的表达式（如受限CEL；实际语言版本与允许语法固定），由内核求值器执行 |
| **不确定态 / Indeterminate** | 外部写操作已发起但结果未知的状态；不自动重放，转人工 |
| **内部基准 / Canonical Benchmark** | 由内核持有、与领域无关、由平台侧判定的中立场景集 |
| **领域自评 / Pack Self-Evaluation** | 领域包自带的场景与判定产出的指标；与内部基准物理隔离 |
| **适用域签名 / Applicability Signature** | 模板声明的 kind 覆盖、输入输出契约与成功判据，用于判断能否复用 |

## 1.5 与主流 Agent Harness 框架的关系

本平台定位在"模型 + Harness = Agent"这条技术路线的**协作与验证**环节。明确它与 LobeHub、DeepSeek Harness 等主流框架的关系，是为了让读者知道边界在哪，而不是宣称对标。

### 1.5.1 三者关注面的差异

| 维度 | LobeHub | DeepSeek Harness | Loom（本平台） |
|---|---|---|---|
| 核心形态 | 对话工作台 / Agent 管理界面 | 插件化运行时与调度 | **多 Agent 协作的任务编排与验证内核** |
| 首要用户 | 终端使用者（交互式） | 平台开发者（扩展运行时） | 平台开发者 + 领域包开发者 |
| 状态管理 | 会话历史为主 | 运行时状态为主 | **结构化协作状态图（事件溯源）** |
| 核心能力 | 交互体验、插件生态 | 工具/插件接入、模型调度 | 两级调度、验证门、失败修复、可审计 |
| 产出形态 | Agent 应用 | Harness 插件 | **可投产的平台 + 可插拔领域包** |
| 验证强度 | 不以验证为一等能力 | 部分校验 | **四道内核门 + 领域门 + 双签 + 抽样复核，不可被领域包放水** |

### 1.5.2 我们多做了什么

1. **协作状态结构化**：把 Agent 间交互从"聊天"转为"结构化交接 + 证据链"，可回放、可审计（§4.2.4）
2. **两级调度与决策留痕**：每次派发留存候选者分值明细，回答"为什么派给它"（§4.4.3）
3. **确定性的验证门**：判定逻辑在内核，领域包只能提供参数（§4.5.1、§4.5.5）
4. **失败分类与定向修复**：七类失败家族 + 六种修复原语，替代朴素重试（§4.6）
5. **可审计与可复现**：事件日志为唯一真相源，投影可完整重建（§4.8）


> **关于 A2A 的正面说明**：A2A 协议 v1.0.1 已稳定，可用于跨厂商 Agent 协作。本平台**不实现 A2A 网关**，是因为平台内部的 Agent 协作是"同一控制面内的强协作"（需要共享状态、独占所有权、租约与提交协议），与 A2A 面向的"跨组织弱协作"形态不同；强行套用会引入不必要的信任边界。工具层的跨厂商互操作已由 MCP 覆盖。该判断在 ADR-008 中记录了复议条件。

## 1.7 价值论证

### 1.7.1 待验证的价值假设

多 Agent 协调、独立验证和修复通常增加调用开销；缓存、任务裁剪与避免返工可能抵消部分成本。**尚无项目实测数据，不能把成本倍率或质量提升写成已证实结论。**

| 维度 | 待验证假设 | 验证要求 |
|---|---|---|
| 推理成本 | 复杂协作可能高于单 Agent；探索阶段可用 2–5 倍作敏感性假设 | 相同模型条件下记录全部成功与失败调用、验证与规划开销，不把假设当预算报价 |
| 首次通过率 | 受信门禁与定向修复可能提升独立验收通过率 | 独立 held-out 判据，报告置信区间与失败分布 |
| 人工工时 | 证据摘要可能减少返工，也可能增加裁决负担 | 人工基线与 Loom 都记录实际工时 |
| 可追溯性 | 事件和保留对象应支持已提交轨迹回放 | 投影等值、对象摘要与权限验证 |
| 重复任务 | 模板复用可能降低边际成本 | 按域内、跨域分别比较；不要求每个模板跨域 |

低复杂度任务应允许选择单 Agent 路径。是否启用协作由独立效果与总成本数据决定，不预设协作必然更好。

### 1.7.2 验证口径

价值主张必须可验证，因此对比实验的基线与口径在 §6.3（压测方法）与 §10.7（基准规程）中固定：

| 对照组 | 定义 |
|---|---|
| **B1 人工基线** | 同一批任务由人工使用通用 Agent 工具完成，记录工时与返工次数 |
| **B2 单 Agent 基线** | 单个 Agent + 全量上下文直出，不做编排与验证 |
| **B3 固定串行基线** | 预先编排好的固定顺序工作流，无动态调度、无自适应修复 |
| **Loom** | 本平台完整能力 |

**主指标**：单位成功任务的总成本（含人工工时折算）。
**次指标**：首次通过率、返工次数、单任务墙钟时间、结论可追溯率。

> 结论若为"Loom 在 B2 之上没有增益"，那就是设计失败，应如实报告并回到设计假设重新检视。**平台不设置只允许正面结论的实验。**

# 3. 系统架构

## 3.1 架构总览

平台采用**控制面 / 数据面分离**架构。这是生产环境的必要切分：控制面承载状态与决策，需要强一致与高可用；数据面承载不可信的模型调用与外部工具执行，必须强隔离。

```
┌──────────────────────────────────────────────────────────────────────────────┐
│  控制面 Control Plane （有状态 · 强一致 · 关键路径）                            │
│                                                                              │
│  ┌────────────┐  ┌────────────┐  ┌────────────┐  ┌──────────────────────┐  │
│  │ API Gateway│  │  Orchestr. │  │  Scheduler │  │  Verification Engine │  │
│  │ (REST/SSE) │→ │  三层图服务 │→ │  两级调度  │→ │ 门禁分层+双签+复核   │  │
│  └────────────┘  └─────┬──────┘  └─────┬──────┘  └──────────┬───────────┘  │
│                          │               │                   │              │
│  ┌───────────────────────▼───────────────▼───────────────────▼──────────┐  │
│  │        Event Log (append-only, 唯一真相源) + Projection Engine        │  │
│  └───────────────────────────────────┬──────────────────────────────────┘  │
│                                      │                                      │
│  ┌───────────────────────────────────▼──────────────────────────────────┐  │
│  │  Pack Registry / Loader  ·  Model Gateway  ·  Tool Registry  ·  Policy│  │
│  └──────────────────────────────────────────────────────────────────────┘  │
└────────────────────────────────┬──────────────────────────────────────────┘
                                 │ 任务派发（队列）  │ 心跳/租约
┌────────────────────────────────▼──────────────────────────────────────────┐
│  数据面 Data Plane （无状态 · 强隔离 · 弹性伸缩）                            │
│                                                                              │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐        ┌────────────────────┐  │
│  │ Worker 1 │  │ Worker 2 │  │ Worker N │  ───▶  │  Egress Gateway    │  │
│  │ 沙箱容器 │  │ 沙箱容器 │  │ 沙箱容器 │        │ 策略/限流/审批/审计 │  │
│  └──────────┘  └──────────┘  └──────────┘        └─────────┬──────────┘  │
│                                                            │             │
│                                            ┌───────────────┴───────────┐ │
│                                            │  MCP Servers / 外部 API   │ │
│                                            └───────────────────────────┘ │
└────────────────────────────────────────────────────────────────────────────┘
```

### 3.1.1 为什么这样切

| 决策 | 理由 |
|---|---|
| 控制面集中、数据面分散 | 调度决策需要全局视图（能力画像、负载、依赖），必须集中；而执行是不可信且资源密集的，必须分散隔离 |
| 事件日志独立于图存储 | 图是投影，日志是真相。日志独立 ⇒ 崩溃后可重建；图可换存储而不影响语义 |
| 队列解耦控制面与 Worker | Worker 崩溃、扩缩容、长时间任务都不应影响控制面可用性（NFR-006） |
| 出口网关独立 | 所有外部访问统一收口，是安全边界（P6）与审计的落点 |
| **调度热路径原子授权** | 内存只选择候选；claim、全局容量与预算通过数据库同事务校验预占（P10）。展示投影滞后不能授权派发，多副本内存计数不能替代全局约束 |
| **执行侧与控制面的幂等边界分离** | 平台内部写入由事件日志保证幂等；**外部写操作的幂等由工具端承担**，平台侧只保证"不重复发起"与"不确定态不重放"（原则 P9） |

## 3.3 部署拓扑与实施适配器

**S1 本地开发形态**：Python 内核 + SQLite 持久化适配器 + 内存测试发布器，可在没有 Docker 和模型密钥时执行确定性用例。SQLite 只用于本地验证和演示；不宣称满足 PostgreSQL RLS、多副本生产容量、JetStream、SLO 或外部签名要求。

**S2 集成形态**：PostgreSQL + 事务 outbox 发布器 + NATS JetStream + 多调度器故障桩；生产路径使用同一套领域契约与适配器一致性测试。

**S4 生产形态**：API 无状态副本、按租户/run 分片的调度单写者、PostgreSQL 主备、JetStream 集群、隔离 Worker 与独立出口网关。领导者租期与 fencing 由持久化账本控制；只有当前分片所有者可申请新 claim。共享 Agent 池的容量及预算必须跨分片原子预占。

多租户要求从 S1 的数据契约与拒绝测试开始。生产隔离使用 tenant/run 复合引用、非 owner 应用角色 RLS、对象下载鉴权、独立队列及凭据命名空间；Worker 复用不得跨任务残留凭据或可写工作区。

## 3.4 关键数据流

### 3.4.1 一次任务的完整流程

```
Client ──POST /v1/runs──▶ API GW ──▶ Orchestrator
                                        │ 1. 创建 Goal(L1)，写 Event
                                        │ 2. 派发 Reasoner 会话
                                        ▼
                                  Scheduler 唤醒 Reasoner
                                        │ 3. Reasoner 读投影快照
                                        │ 4. 提议 Intent(L2)，带 from=[支撑Fact]
                                        ▼
                                  Event Log ◀──submit(submission_key)──
                                        │
                        ┌───────────────┴───────────────┐
                        ▼                               ▼
                Scheduler 派发 Task(L3)         投影引擎更新协作图
                        │
                        ▼
                   Worker 领取任务（租约）
                        │ 执行：LLM 调用 → 工具调用（经出口网关）
                        │ 产出 Observation / Artifact
                        ▼
                submit(Artifact/Observation)
                        │
                        ▼
              Verification Engine 门禁判定
                   ├─ 通过 → Intent 达成 → 汇总至 Goal
                   └─ 失败 → 失败分类 → 修复原语 → 回到派发
```

### 3.4.2 回放、恢复执行与灾备流程

1. **历史回放**：仅读取事件与校验过的保留对象，重建指定 seq 的状态；不能领取 claim、调用模型、执行写工具或发出新业务事件。
2. **恢复执行**：先校验链与已签检查点，重建投影和控制账本，取得有效分片租期；按数据库时间回收旧 claim，并经副作用状态表决定哪些步骤可继续。
3. **消息恢复**：事务 outbox 的持久记录由发布器续投；消费者按 event/call 标识去重，不能依赖进程本地队列。
4. **副作用恢复**：有发起与完成记录则复用结果；只有发起记录则按工具幂等契约重试或标未知；在完整性已确认的记录区间内确实没有发起记录才可视为未发起。
5. **灾备丢失窗口**：恢复点至故障点之间可能丢失发起记录的 run，一律设置 `recovery_hold`，冻结外部写并核对独立账本/目标系统，不能因“当前查不到 intent”自动重做。

旧 Worker 的迟到提交和新外部调用均由网关校验 epoch/唯一调用发起权；提交幂等键不代替工具调用去重。细则见 §4.4.6、§4.7.4、§5.5。

### 3.4.3 熔断与人工介入流程

```
修复轮次达到上限 或 置信度低于阈值
   ▼
Intent 状态 → awaiting_human
   ▼
事件记录熔断原因 + 累积证据 + 已尝试的修复原语
   ▼
人工在控制台裁决：接受 / 驳回 / 改判 / 追加指令
   ▼
裁决写入事件流 → 状态跃迁 → 恢复或终止
```

## 3.5 技术选型与取舍

| 层 | 选型 | 备选 | 取舍理由 |
|---|---|---|---|
| **主存储** | **PostgreSQL 16**（事件日志 + 投影 + 关系数据） | Neo4j / Kuzu | 事务保证、运维成熟、单一备份策略。**图不是独立存储**：协作图用递归 CTE + 物化投影表达，避免引入有状态图中间件 |

| **模型接入** | 自建 Model Gateway（兼容 OpenAI 协议） | 直接调各厂商 | 统一降级、熔断、成本核算、缓存前缀复用；也让模型可替换 |

| **前端** | React + TypeScript | Vue | 团队既有能力优先 |
| **图查询（可选）** | Neo4j 适配器（只读） | — | 复杂多跳分析场景启用；默认不引入 |

# 4. 核心设计

## 4.1 协作状态图模型

### 4.1.1 三层定义

```
L1 目标层   Goal          —— 要达成什么（业务语义、成功判据）
     │  拆解
L2 策略层   Intent        —— 打算怎么做（一个可执行、有支撑证据的方向）
     │  展开
L3 执行层   Task          —— 具体由谁做哪一步（可派发的最小单元）

横切：
   Artifact      —— 已产出的结论性产物（代码、规格、报告）
   Observation  —— 执行过程中的观测（原始信号、中间状态）
   Anchor       —— 不可自改的外部参照（冻结判据、held-out 集、人工审批）
```

**层间规则**：

| 规则 | 内容 | 理由 |
|---|---|---|
| **R1 单向拆解** | L1 → L2 → L3；L1 不得直接派发 L3 | 若 L1 能直派 L3，抽象层退化为标签，无法提供调度价值 |
| **R2 证据回流** | L3 产出 Observation 挂到 L2 Intent；L2 达成后其 outcome Artifact 汇总为 L1 子目标完成度 | 每层都有可追溯的证据链 |
| **R3 受控依赖** | L3可通过显式版本化依赖边连接，数据只经类型化证据引用传递；禁止自由消息授权 | 支持DSL depends_on和改图，同时保持可审计有向无环依赖 |
| **R4 判据下沉** | 成功判据定义在 L1，逐层细化不得放宽 | 防止"越往下越松"导致验收失真 |

### 4.1.2 数据模型与事务边界（PostgreSQL）

以下为生产模型契约摘要，完整迁移须在项目中执行并经过 PostgreSQL 集成测试；本地 SQLite 适配器不能替代该验证。所有资源 ID 使用 UUID；资源归属通过 `(tenant_id, run_id, id)` 复合键表达。

```sql
CREATE TABLE run (
  tenant_id UUID NOT NULL, id UUID NOT NULL,
  status TEXT NOT NULL CHECK (status IN
    ('open','running','awaiting_human','stalled','budget_exhausted',
     'succeeded','failed','accepted_with_exception','aborted','recovery_hold')),
  workflow_version TEXT NOT NULL, rule_version TEXT NOT NULL,
  anchor_digest TEXT NOT NULL, graph_revision BIGINT NOT NULL DEFAULT 0,
  last_seq BIGINT NOT NULL DEFAULT 0, last_hash BYTEA NOT NULL,
  PRIMARY KEY (tenant_id, id)
);
CREATE TABLE event (
  tenant_id UUID NOT NULL, run_id UUID NOT NULL, id UUID NOT NULL,
  seq BIGINT NOT NULL CHECK (seq > 0), schema_version INT NOT NULL,
  chain_id UUID NOT NULL, type TEXT NOT NULL, actor TEXT NOT NULL,
  ts TIMESTAMPTZ NOT NULL, payload JSONB NOT NULL,
  submission_key TEXT, request_digest TEXT,
  prev_hash BYTEA NOT NULL, hash BYTEA NOT NULL,
  PRIMARY KEY (tenant_id, run_id, seq),
  UNIQUE (tenant_id, id),
  FOREIGN KEY (tenant_id, run_id) REFERENCES run(tenant_id, id)
);
CREATE TABLE submission_receipt (
  tenant_id UUID NOT NULL, submission_key TEXT NOT NULL,
  request_digest TEXT NOT NULL, response JSONB NOT NULL,
  PRIMARY KEY (tenant_id, submission_key)
);
CREATE TABLE outbox (
  tenant_id UUID NOT NULL, event_id UUID NOT NULL,
  delivered_at TIMESTAMPTZ,
  PRIMARY KEY (tenant_id, event_id),
  FOREIGN KEY (tenant_id, event_id) REFERENCES event(tenant_id, id)
);
CREATE TABLE goal (
  tenant_id UUID NOT NULL, run_id UUID NOT NULL, id UUID NOT NULL,
  title TEXT NOT NULL, acceptance JSONB NOT NULL,
  anchor_digest TEXT NOT NULL, status TEXT NOT NULL,
  PRIMARY KEY (tenant_id, run_id, id),
  FOREIGN KEY (tenant_id, run_id) REFERENCES run(tenant_id, id)
);
CREATE TABLE intent (
  tenant_id UUID NOT NULL, run_id UUID NOT NULL, id UUID NOT NULL,
  goal_id UUID NOT NULL, kind TEXT NOT NULL, status TEXT NOT NULL,
  priority INT NOT NULL DEFAULT 0, round INT NOT NULL DEFAULT 0,
  revision BIGINT NOT NULL DEFAULT 0, coordinator_id UUID,
  PRIMARY KEY (tenant_id, run_id, id),
  FOREIGN KEY (tenant_id, run_id, goal_id)
    REFERENCES goal(tenant_id, run_id, id)
);
CREATE TABLE task (
  tenant_id UUID NOT NULL, run_id UUID NOT NULL, id UUID NOT NULL,
  intent_id UUID NOT NULL, kind TEXT NOT NULL,
  status TEXT NOT NULL CHECK (status IN
    ('pending','ready','dispatched','running','verifying','succeeded','failed',
     'skipped','stale','indeterminate','rejected_by_gate','awaiting_human','canceled')),
  input_spec JSONB NOT NULL, output_spec JSONB NOT NULL,
  input_revision BIGINT NOT NULL DEFAULT 0,
  priority INT NOT NULL DEFAULT 0, epoch BIGINT NOT NULL DEFAULT 0,
  PRIMARY KEY (tenant_id, run_id, id),
  FOREIGN KEY (tenant_id, run_id, intent_id)
    REFERENCES intent(tenant_id, run_id, id)
);
CREATE TABLE task_dependency (
  tenant_id UUID NOT NULL, run_id UUID NOT NULL,
  task_id UUID NOT NULL, prerequisite_id UUID NOT NULL,
  required_revision BIGINT NOT NULL,
  PRIMARY KEY (tenant_id, run_id, task_id, prerequisite_id),
  CHECK (task_id <> prerequisite_id),
  FOREIGN KEY (tenant_id, run_id, task_id)
    REFERENCES task(tenant_id, run_id, id),
  FOREIGN KEY (tenant_id, run_id, prerequisite_id)
    REFERENCES task(tenant_id, run_id, id)
);
CREATE TABLE evidence (
  tenant_id UUID NOT NULL, run_id UUID NOT NULL, id UUID NOT NULL,
  kind TEXT NOT NULL CHECK (kind IN ('input','observation','artifact','execution_report')),
  uri TEXT NOT NULL, digest TEXT NOT NULL, producer TEXT NOT NULL,
  trusted BOOLEAN NOT NULL DEFAULT FALSE, revision BIGINT NOT NULL,
  PRIMARY KEY (tenant_id, run_id, id),
  FOREIGN KEY (tenant_id, run_id) REFERENCES run(tenant_id, id)
);
CREATE TABLE intent_support (
  tenant_id UUID NOT NULL, run_id UUID NOT NULL, intent_id UUID NOT NULL,
  evidence_id UUID NOT NULL,
  PRIMARY KEY (tenant_id, run_id, intent_id, evidence_id),
  FOREIGN KEY (tenant_id, run_id, intent_id)
    REFERENCES intent(tenant_id, run_id, id),
  FOREIGN KEY (tenant_id, run_id, evidence_id)
    REFERENCES evidence(tenant_id, run_id, id)
);
CREATE TABLE artifact (
  tenant_id UUID NOT NULL, run_id UUID NOT NULL, id UUID NOT NULL,
  task_id UUID NOT NULL, content_hash TEXT NOT NULL, uri TEXT NOT NULL,
  severity TEXT NOT NULL, verification_required BOOLEAN NOT NULL,
  verification TEXT NOT NULL, dual_sign TEXT NOT NULL,
  rule_version TEXT NOT NULL, evidence_digest TEXT NOT NULL,
  PRIMARY KEY (tenant_id, run_id, id),
  FOREIGN KEY (tenant_id, run_id, task_id)
    REFERENCES task(tenant_id, run_id, id)
);
CREATE TABLE observation (
  tenant_id UUID NOT NULL, run_id UUID NOT NULL, id UUID NOT NULL,
  task_id UUID NOT NULL, payload JSONB NOT NULL, content_hash TEXT NOT NULL,
  PRIMARY KEY (tenant_id, run_id, id),
  FOREIGN KEY (tenant_id, run_id, task_id)
    REFERENCES task(tenant_id, run_id, id)
);
CREATE TABLE anchor (
  tenant_id UUID NOT NULL, id UUID NOT NULL,
  kind TEXT NOT NULL, ref TEXT NOT NULL, digest TEXT NOT NULL,
  PRIMARY KEY (tenant_id, id)
);
```

命令服务在一个事务中锁定 run 头、校验预期版本、更新控制账本与业务状态、顺序追加事件/回执/outbox。事件不使用数据库 sequence 保证连续性：`run.last_seq` 在行锁内按提交批次递增，回滚不消耗业务 seq。系统级 Pack/策略审计进入专用 control run，不能绕过 run 归属约束。

第一份支撑事实由受权调用者提交的原始输入产生 `evidence.kind=input`，绑定 Anchor；首个 Intent 必须引用该事实。`intent_support` 至少一条由事务末校验或延迟约束触发器保证。模型不得将自生成 Observation 标为受信事实。

完整模型还须包含验证签名、规则快照、容量/预算预留、claim、调用账本、人工裁决、投影游标与签名检查点表；其行为分别以 §4.4–§5.5 为准，迁移未齐备前不得声明生产模型完成。

### 4.1.3 约束、状态迁移与引用

| 对象 | 约束/索引 | 目的 |
|---|---|---|
| event | 主键 `(tenant_id, run_id, seq)`；完整信封摘要；业务角色禁止 UPDATE/DELETE | 序号唯一、可检测篡改 |
| submission_receipt | `(tenant_id, submission_key)` 唯一；请求摘要覆盖操作、资源、版本、参数 | 并发幂等和异参拒绝 |
| 核心资源 | tenant/run 复合外键；RLS、下载与解析鉴权 | 拒绝跨租户/run 引用 |
| task_dependency | 复合外键、自环拒绝、事务内 DFS/拓扑无环校验 | 依赖完整与合法改图 |
| execution_claim | 每个 task 最多一个未释放 claim；epoch CAS；按资源池原子预占 | 独占执行、容量限制 |
| artifact | 内容/证据/规则版本绑定；只有验证服务可更新验证状态 | 签名不可挪用 |

**状态迁移**：Task `pending→ready→dispatched→running→verifying→succeeded`；门禁失败进入 `rejected_by_gate`，执行失败进入 `failed`，依赖失效进入 `stale`，未知外部效果进入 `indeterminate`。重试创建新 attempt 并递增 epoch，不复用旧执行权限。`skipped` 必须有证明下游判据已满足的证据。

Goal/Intent/run 的成功仅由全部冻结验收判据和所需验证通过触发；`stalled`、`budget_exhausted`、`awaiting_human`、`accepted_with_exception` 均不是普通成功。状态转换逐条列在事件 schema 并由命令处理器校验，非法边直接拒绝。

Intent 的 coordinator 是规划协调者，不是其全部 Task 的执行 owner；不同 Task 可有不同 claim 并行。投影可短时落后，但控制命令依据事务状态及版本校验，不能靠投影事后发现半写入。

### 4.2.2 能力画像与调度状态权威

| 状态 | 权威与更新 | 调度读取方式 |
|---|---|---|
| claim、全局池/Agent 容量、在途预算 | 数据库控制账本；认领、预占和释放同事务且写事件 | 候选可用内存缓存，实际派发必须原子校验预占 |
| 分片候选队列、ready 集合 | 当前持有效 fencing 的单写者内存；由事件重建 | 不依赖展示投影授予权限；接管后先重建再派发 |
| 成功率、延迟、失败历史 | 异步历史统计投影，可声明滑动窗口与数据版本 | 可用于排序，滞后不改变安全性；分值记录统计版本 |

乐观内存加减只用于降低竞争，不能替代数据库余量判断。预占失败重选候选，不产生有效 claim。终态或回收通过 reservation 唯一状态迁移保证只释放一次；每 30 秒对账可发现异常，不是正确性机制。领导者接管须持新 epoch；旧领导者和旧 Worker 在数据库与出口网关均被拒绝。

CI 检查调度模块不依赖展示投影客户端；动态测试还须覆盖双副本竞争、投影滞后 60 秒与旧领导者继续运行，证明实际全局容量不超限。历史统计属于允许读取的独立只读画像接口，避免“禁止所有投影”与打分依赖相冲突。

### 4.2.3 知识库与检索链路

| 层级 | 内容 | 隔离机制 |
|---|---|---|
| 会话内 | 当前任务上下文 | 随会话结束销毁 |
| 任务级 | 本次运行产生的中间产物 | 随 run 保留，可归档 |
| 跨任务 | 经验条目（成功模式、失败模式、配方） | **写入即 `quarantined`**，需审核后进入召回 |

**经验条目召回**：按任务特征向量检索，叠加"被引用过且结论正确"的加权；未审核条目不参与召回；`trial` 条目仅在显式试用流量可见，普通召回只取 `active`（FR-004）。**这条约束是防止自愈循环把自己的错误当经验放大的关键。**

**检索链路（完整实现）**：

```
查询 → ① 查询改写（术语归一、别名映射、同义词扩展）
     → ② 混合召回
          · 稠密向量（pgvector，HNSW 索引）
          · 稀疏关键词（Postgres FTS + 中文分词）
          · 结构化过滤（租户/资产类型/时间窗/来源）
          · 三路结果用 RRF 融合
     → ③ 重排（cross-encoder，Top-50 → Top-8）
     → ④ 引用与回链（每条片段带 source_ref + 内容哈希 + 定位锚点）
     → ⑤ 装配进上下文（受 §4.4.7 的裁剪预算约束）
```

| 环节 | 设计要点 | 失败模式与处置 |
|---|---|---|
| ① 查询改写 | 保留原查询；改写结果双路召回 | 改写不得替换原查询（防止语义漂移） |
| ② 混合召回 | 稠密 + 稀疏 + 结构化过滤，三路 RRF 融合 | 任一路不可用时降级为其余两路，并记 `retrieval.degraded` |
| ③ 重排 | 纯 CPU 模型，批量推理 | 重排超时 → 退回融合序（Top-K 截断），不阻塞执行 |
| ④ 引用回链 | 片段必须能定位到原文位置 | 无引用片段不进上下文（避免不可追溯的"似是而非"） |
| ⑤ 装配 | 受 token 预算二次裁剪 | 裁剪记录进 `context.trimmed` 事件 |

**经验条目的准入**：除 `quarantined` 隔离外，经验条目进入召回还需满足——经独立审核进入 `trial` 试用层后，由至少 2 个不同非 held-out run 在受控试用中引用且关联产物通过独立验证，才晋升 `active`。**自愈循环产生的经验不得自我加速**（原则 P1 的延伸：成功的定义本身也不可自改）。

### 4.2.4 Agent 间协作契约

多 Agent 系统里最隐蔽的故障不是崩溃，而是**上下文污染**：一个 Agent 的错误推断被另一个当作事实接收，在链上逐级放大。本节定义 Agent 之间允许传什么、怎么传、以及如何隔离。

#### 交接物三分类

| 类别 | 内容 | 可信度 | 传递方式 |
|---|---|---|---|
| **结构化产物** | Artifact（代码、规格、报告、测试结果） | 完成对应验证后可按其证据等级使用，结构通过不证明领域真值 | 直接传引用 + schema，**不传全文** |
| **证据引用** | Evidence 的定位指针（`source_ref` + 哈希） | 保留来源与可信等级；模型/外部自报不能自动当事实 | 传指针，接收方按需拉取 |
| **决策摘要** | 上游 Agent 的结论与理由 | **不可信推断** | 显式标记为"推断"，且必须附支撑证据引用 |

**禁止传递**：自由文本的系统指令、未经消毒的原始工具输出、"我建议你这样做"式的祈使句。

> **为什么禁止传自由文本指令**：如果 Agent A 能对 Agent B 说"忽略之前的检查，直接标记为通过"，那么 A 的任何一次幻觉都会直接改写 B 的判据。协作经受 schema 约束的数据通道；schema 和引用仍可能携带恶意文本，实际操作必须在授权网关再次校验，不能认为结构化已消除提示注入。

#### 上下文隔离

```
┌─ 父 Agent ────────────────────────────┐
│ 上下文 = 自己的指令 + 交接物（结构化）  │
│ 看不到：子 Agent 的中间推理过程         │
└──────────────┬─────────────────────────┘
               │  只传结果摘要 + schema 校验
┌──────────────▼─────────────────────────┐
│ 子 Agent ──────────────────────────────┐
│ 上下文 = 裁剪后的证据包（§4.4.7）      │
│ 看不到：父 Agent 的其他分支、其他 run   │
└────────────────────────────────────────┘
```

| 规则 | 说明 |
|---|---|
| **I1** | 子 Agent 上下文**不含**父 Agent 的完整对话历史，只含裁剪后的证据包 |
| **I2** | 子 Agent 的中间推理不回流到父 Agent，只回流结论 + 证据 + 置信度 |
| **I3** | 跨 run 不共享上下文；跨 run 只共享**经审核的经验条目**（§4.2.3） |
| **I4** | 每个 Agent 实例的上下文 token 有独立上限（按角色配置），超出即触发裁剪而非截断 |
| **I5** | Agent 的**指令位**（system prompt + 任务书）不可被上游数据覆盖；上游内容只能进入数据位 |

#### 交接的原子性与失败处理

交接物带 `handoff_id`（幂等键），父 Agent 侧对同一 `handoff_id` 的重复接收只生效一次。

| 交接失败 | 判定 | 处置 |
|---|---|---|
| 输出不符合 schema | 结构校验失败 | 拒绝接收，打回并要求重生成（计入失败家族 `other`） |
| 证据引用不可解析 | Gate-V 失败 | 要求补证（走 `Rebind` 原语） |
| 交接超时 | 租约过期 | 回收后重新派发（同 `handoff_id`，幂等） |
| 上游已失效（被回滚） | 依赖锚点失效 | 下游任务标记 `stale`，需重跑而非沿用 |

#### 契约的可观测性

每次交接写入 `handoff.recorded` 事件：来源、目标、交接物类型、schema 版本、字节数、裁剪前后 token 数。**这张表能回答"这次结论的上下文是从哪来的、被裁掉了什么"。**

## 4.3 M2 · 工作流编排

### 4.3.1 定义格式

```yaml
id: feature-delivery
version: 2
input:
  spec: {type: string}
output:
  report: {type: artifact, kind: report}
nodes:
  - id: parse
    kind: spec          # 任务类型 → 第一级路由
    needs: [analyst]
    input: {spec: "$input.spec"}
    output: {spec: "$.spec"}
    budget: {rounds: 3}

  - id: design
    kind: design
    needs: [architect]
    depends_on: [parse]
    input: {spec: "$.parse.spec"}

  - id: case
    kind: case
    needs: [tester]
    depends_on: [parse]
    input: {spec: "$.parse.spec"}
  - id: code
    kind: code
    needs: [developer]
    depends_on: [design]
    input: {spec: "$.parse.spec", design: "$.design.design"}

  - id: verify
    kind: verify
    needs: [validator]
    depends_on: [code, case]
    loop:
      max_rounds: 5
      until: {artifact_verified: "$output.report"}
    on_exhausted: {escalate: human}
```

**DSL示例边界**：示例展示控制结构；运行创建器须从已授权Goal、Anchor及输入证据生成objective/scope/acceptance_refs/evidence_refs五要素，补全各节点输入输出schema与预算后才可经Gate-P派发，不能直接把此节省略字段的示例视为完整生产工作流。

**控制结构支持**：`depends_on` 表达依赖（并行/串行由依赖图决定）；`kind` 决定路由；`loop` 表达迭代；子工作流通过 `workflow_ref` 嵌套。

### 4.3.2 派单完整性（Gate-P）

派发前由确定性代码校验五要素，不调用 LLM，不根据标题连接词推断是否多目标。

| 要素 | 结构字段 | 确定性校验 |
|---|---|---|
| 任务标识 | tenant/run/task ID、输入版本 | 唯一、归属相同且版本有效 |
| 作用域 | `scope` | 属于当前主体获授权范围且未被紧急拒绝 |
| 唯一子目标 | `objective` 对象、`objective_id` | 恰好一个对象，绑定冻结验收项 ID；标题仅供人读 |
| 成功标准 | `output_spec`、`acceptance_refs` | schema 合法，引用可执行的已发布判据，不能降低上层要求 |
| 依据锚点 | `evidence_refs`、Anchor digest | 至少一个有效支撑；初始任务可引用创建 Goal 时的原始输入证据 |

退单进入 `rejected_by_gate` 并留拒绝原因。LLM 可以建议拆分或补全任务，建议必须重新经同一确定性校验，不能直接决定通过。依赖满足、版本、scope、容量与预算还须在实际 claim 事务中复核，避免检查后状态变化。

## 4.4 M3 · 任务调度与执行

### 4.4.1 两级调度

**第一级：任务类型 → 角色族（确定性、可解释、亚毫秒）**

由领域包提供路由表：

```yaml
kind_role:
  spec:    [analyst]
  design:  [architect]
  case:    [tester]
  code:    [developer]
  review:  [reviewer]
  fix:     [fixer]
  verify:  [validator]
```

路由表允许多候选（按顺序偏好），由第二级在其内部择优。

**第二级：角色族内 → 具体 Agent 实例（可配权重，效果待对照实测）**

### 4.4.2 任务排序与 Agent 打分分离

**先选任务**：从依赖就绪、输入版本有效的任务中按租户公平额度、优先级、等待时长/aging 和稳定 task ID 排序；动态更新优先级影响下一次选择，aging 防止低优先级永久饥饿。

**再选 Agent**：技能、授权、模型 tier 与容量是硬过滤；对同一任务的候选实例计算归一化得分：

```text
score(agent, task) =
    w1 * capability_match + w2 * available_capacity_ratio
  + w3 * historical_success + w5 * latency_fit
  + w6 * cost_fit - w7 * failure_streak_penalty
```

task priority 对同一任务的所有候选是常数，不放入候选 Agent 排名。历史统计含版本；权重通过授权策略版本发布，run 绑定快照。记录任务被选择的优先级/aging/公平性理由，以及 Agent 候选过滤原因、分值分解、权重、平分时稳定排序规则。

得分只给出候选，不授予容量；只有 §4.4.5/6 的原子预占成功才可派发。

### 4.4.4 动态预算与共享预留

预算由轮次、token、金额组成；任务复杂度可影响建议预算，但最终不能超租户/run 硬上限。轮次计算取明确整数舍入并限制上下界；所有规划、验证、重试与抽样调用都计费。

金额使用整数最小计费单位或精确 Decimal。网关调用前锁定 run 和任务预算记录，以输入 token、可强制的最大输出/推理 token、锁定价格版本与计费失败策略计算本次最坏成本，原子创建 `reservation(call_id)`：

```text
spent_run + reserved_run + requested_worst_case <= run_cost_cap
spent_task + reserved_task + requested_worst_case <= task_cost_cap
```

预留成功后才获得一次调用权限；结算实际 usage 并释放差额，同一 call_id 不能重复计费结算。结果未知且提供方可能收费时保留预留，不可因超时立即释放后重试。供应商不能提供可强制计费上界时只提供软预算路由，禁止声称 NFR-020 硬封顶。

角色 `max_cost_usd`、工作流预算和租户上限取有效最小值，语义统一为任务级限制；run 上限为共享总账，不是任务上限简单求和。80% 预警不改变每次调用必须预留的硬条件。

### 4.4.5 容量预留

任务必须携带 `channel=business|verification`。`verification_reserve` 是最低保留量，`verification_limit` 是验证通道最大容量，`total_limit` 是资源池总上限；三者不能混用。

```python
def can_dispatch(channel, business_used, verification_used,
                 total_limit, verification_reserve, verification_limit):
    if business_used + verification_used >= total_limit:
        return False
    if channel == "business":
        return business_used < total_limit - verification_reserve
    if channel == "verification":
        return verification_used < verification_limit
    return False
```

该纯函数用于策略与测试；真实派发须在数据库事务中锁定资源池行、再次判断并增加 reservation。容量预占、claim 和派发事件原子提交，失败不占容量。S1 不允许业务借用验证保留；后续若实现可撤回借用，必须先定义抢回协议再开启。

默认 reserve=总容量的20%，允许授权运维收紧到40%；变更记录版本且不突破物理总容量。验证也需模型配额与预算，不可只保留 Worker 槽位。双副本竞争、终态重复上报、租约回收与进程重启均不得导致超配或双释放。

### 4.4.6 分片租期、执行 claim 与 fencing

每个调度分片仅一个有效写者，由数据库行锁/CAS 发放单调递增的 shard epoch；API 副本可扩展，但只有当前写者可创建新 claim。跨分片共享容量/预算仍在统一账本原子预占。

```sql
CREATE TABLE execution_claim (
  tenant_id UUID NOT NULL, run_id UUID NOT NULL, task_id UUID NOT NULL,
  id UUID NOT NULL, worker_id TEXT NOT NULL,
  epoch BIGINT NOT NULL, input_revision BIGINT NOT NULL,
  shard_epoch BIGINT NOT NULL,
  lease_expires_at TIMESTAMPTZ NOT NULL,
  state TEXT NOT NULL CHECK (state IN ('active','released','expired','revoked')),
  PRIMARY KEY (tenant_id, id),
  FOREIGN KEY (tenant_id, run_id, task_id)
    REFERENCES task(tenant_id, run_id, id)
);
CREATE UNIQUE INDEX one_active_claim
  ON execution_claim(tenant_id, run_id, task_id) WHERE state = 'active';
```

认领事务锁 task/资源池/预算行，使用数据库时间判定并使旧 claim 失效，递增 `task.epoch`，写入新 claim、预占与事件。过期 active 行在同一事务先标记 expired，唯一约束不能仅依赖后台清扫。

提交、续租、工具外部调用都校验 tenant/run/task、claim ID、epoch、输入版本、分片 epoch、截止时间和撤销状态。数据库时间为授权依据，节点时钟仅用于展示；心跳建议间隔租期的1/3，授权一到截止时间即失效，不因“再等两次心跳”延长权限。

Intent coordinator 只协调规划版本；同一 Intent 下不同 Task 可并行，互不争抢一个 Intent 执行 owner。每 run 最多一个协调 Reasoner，提议子任务可多 Worker 并行，由协调者以预期 revision 合并。接管前先重建候选视图和对账，旧 Worker 无法重新获得发起权。

### 4.4.7 上下文组装与分层裁剪

上下文组装是调度器的核心组件：它决定 Agent 看到什么，直接决定 token 成本与产出质量。

**输入 → 输出**：

```
输入：任务书 + 上游产物 + 相关 Observation + 经验条目 + 角色指令
输出：有序证据包（evidence bundle），带 token 预算与裁剪记录
```

**四级裁剪链**（按序执行，每级都记录丢弃项）：

| 级 | 规则 | 保留策略 |
|---|---|---|
| **C1 依赖可达性** | 沿依赖图回溯，保留祖先证据 ID、摘要与版本，正文按需拉取 | 必留引用与验收相关摘要；正文参与预算裁剪 |
| **C2 语义相关性** | 按 kind / 资产类型 / 时间窗 / 被引用次数 / 与当前子目标的重合度打分，取 Top-K | 按分数保留，K 由 token 预算反推 |
| **C3 证据强度优先** | 同一主题下，优先保留"有门禁通过记录"的证据，降权未验证与争议件 | 排序，不删除 |
| **C4 token 预算二次裁剪** | 超预算时：先丢低分片段 → 再把长产物替换为摘要+引用 → 最后截断到摘要 | 保留结构，丢细节 |

**始终保留**（任何情况下不裁剪）：
- 任务书五要素（Gate-P 要求）
- Anchor 引用与其摘要
- 上游最近一个已验证产物的引用、内容哈希和必要摘要（若有）
- 失败上下文（触发本次修复的失败证据与已试原语）——**没有失败上下文，修复动作就是在盲猜**

**硬预算边界**：必留引用、判据、失败信息与摘要本身仍超模型窗口时，返回 `CONTEXT_BUDGET_EXCEEDED`，拆分任务或转人工；不静默截掉 Anchor 或硬约束。全图基线超模型窗口时，只用统一 tokenizer 离线计数并标明无法真实全量推理；质量对照另取双方均可执行的冻结场景。NFR-012 的40%仅适用于预注册高冗余场景，小图不强制降幅。

**可审计性**：每次组装写 `context.trimmed` 事件，记录被丢弃片段的 `source_ref`、分数与丢弃级别。**"当时丢了什么"是事后追责与调参的关键**，且能解释"为什么 Agent 漏看了那条证据"。

**基线定义**（NFR-012 的参照物）：**全图注入基线** = 将当前 run 的全部 Artifact + Observation（不含裁剪）直接注入上下文，作为对照组。二者的 token 比值即 NFR-012 的度量对象；基线实现纳入 §10.6 压测项。

### 4.4.8 意图提议的并行化

**问题**：L2 意图提议是 LLM 调用（典型 2–15 s）。若串行，一个需要 20 个意图的 Goal 需要 40–300 s 才能进入 L3，**意图提议本身成为关键路径上的串行热点**。这与 §4.4.5 中"验证通道不能被挤占"是同一类错误的两个面。

**方案**：把意图提议拆为可并行的子任务。

```
Goal
  ↓
Reasoner 拆分（1 次调用，产出"意图种子"）
  ├─ 种子1: kind=design, 目标=..., 约束=...
  ├─ 种子2: kind=case,   目标=..., 约束=...
  └─ 种子3: kind=code,   目标=..., 约束=...
  ↓
并行意图提议（每个种子一次 LLM 调用，可并发）
  ├─ Intent-1 ─┐
  ├─ Intent-2 ─┼→ 去重与合并（Anchor 约束：同一 kind 的子目标不得重叠）
  └─ Intent-3 ─┘
```

| 设计点 | 说明 |
|---|---|
| 种子由 Anchor 约束 | 种子拆分必须落在 Goal 的 `acceptance` 范围内，不得超出判据 |
| 去重合并 | 同 kind 多个种子合并为一个 Intent，或保留为子意图；合并规则在内核 |
| 子目标细化下移 | 具体子目标由 L3 首次执行时细化，进一步缩短 L2 关键路径 |
| 失败隔离 | 某个种子的提议失败不影响其他种子；失败种子走 `other` 家族并进入重试 |

**性能假设**：可并行提议减少串行等待，但协调者拆分、最长子调用、合并与模型配额均计入 NFR-019。P99 ≤15 s 为需实测目标，不能由复杂度记号直接推导；合并须带输入/规则版本与协调者 revision。

## 4.5 M4 · 结果验证与监控

### 4.5.1 门禁分层、受信证据与放行阶段

| 门 | 触发阶段 | 确定性判定 | 失败/等待处置 |
|---|---|---|---|
| Gate-D1 | 输入准备后 | 类型、必填、范围、输入版本与已发布 schema | 退单 |
| Gate-P | claim 前 | 单一结构化目标、冻结成功判据、作用域、支撑事实 | 退单 |
| Gate-V-structure | 产物提交时 | 内容摘要、证据归属、可解析性、证据版本与来源权限 | 拒收或补证；不因此宣称领域正确 |
| Gate-D | 独立执行报告到达后 | 已发布规则读取受信指标；禁止读取模型自报值作为权威测量 | 失败、等待或人工 |
| Gate-V-final | 交付/成功前 | 全部硬门通过，所需签名及抽样复核完成且绑定当前内容/规则/证据 | 保持 pending/disputed/blocked |
| Gate-R | 报告交付前 | 覆盖声明与受信台账实测一致、限制与例外如实披露 | 拒绝交付 |

规则使用受限表达式可降低执行风险，**不能证明规则语义充分**。内核维护通用结构不变量；授权规则发布者维护版本化领域规则，Pack 只能引用获准版本。独立评测适配器由平台评测角色或第三方发布，不允许 Pack 自行写入其判定结果。

`coverage`、测试失败数等受信指标只能由获授权执行器写入 Evidence/执行报告，绑定代码 commit/内容哈希、测试集版本、工具镜像、完整原始结果摘要和产生者身份；模型上报的 `artifact.metrics` 只是建议字段，不可覆盖受信指标。证据对象下载与摘要校验在相同租户/run 上执行。

```python
def gate_v_final(artifact, policy, evidence_resolver, signatures):
    if not evidence_resolver.valid_for(artifact):
        return GateResult(False, "invalid_or_stale_evidence")
    if not artifact.hard_gates_passed:
        return GateResult(False, "hard_gate_failed")
    if artifact.resample_required and artifact.resample_status != "passed":
        return GateResult(False, "resample_incomplete")
    dual_required = policy.requires_dual_sign(artifact)
    required_count = 2 if dual_required else 1
    if not signatures.valid_for(artifact, min_count=required_count):
        return GateResult(False, "missing_invalid_or_stale_signatures")
    if dual_required:
        if artifact.dual_sign != "signed":
            return GateResult(False, "dual_sign_incomplete")
        if not signatures.independent_for(artifact):
            return GateResult(False, "signers_not_independent")
    return GateResult(True, "verified")
```

普通单签路径也必须有至少一份有效验证记录；valid_for须验证最低签数、当前内容/证据/规则绑定、验证者授权、签名有效性与未撤销状态，不能把低风险解释成零签。双签在此基础上另检独立性。

规则装载检查类型、变量来源、函数白名单、引用完整性、表达式深度/节点数及求值时间/内存。禁止 IO、外部调用、反射、随机与未授权数据读取。可折叠的恒真/恒假规则拒绝；不能声称静态分析能识别所有语义放水。求值异常/缺字段/超时均 fail-closed。规则审查、独立受信指标和复核共同构成保障。

### 4.5.2 双签裁决

是否强制双签由内核风险规则、授权策略与冻结规则版本决定；Pack 可以增加验证要求，不能降低底线。severity、`verification_required` 与高风险 kind 的来源必须为控制服务受信元数据，不能采纳模型自行降级标签。

第一签与第二签分别基于相同原始材料独立作答；第二签不接收第一签结论。模型、提供方/模型家族及会话隔离要求写入风险策略；同一实例重复作答不计两位独立验证者。模型 tier 使用受控整数等级映射比较，禁止直接对字符串按字典序比较。

签名记录绑定 `(tenant, run, artifact_id, content_hash, evidence_digest, rule_version, verifier_id, model_version)`，由验证服务写入。任一内容、证据或规则版本变化立即作废旧签。所需两签均有效、硬门通过且抽样完成才置 `verified/signed`；缺签为 pending，不一致为 disputed，通道不可用为 blocked；`single` 仅适用于不要求双签的产物。

第二签能力级别不得低于第一签；满足独立性与 tier 的模型不可用时转人工，不能降档。双签一致只提供约定的复核证据，不保证模型错误完全独立；业务真值仍由受信执行与独立 held-out 评测验证。人工处理遵循 §8.6.3，不能把硬门失败直接改成正常 verified。

### 4.5.3 置信度评估

```
confidence = 采样一致率 × 证据强度
采样一致率 = k 次独立采样中结论一致的比例
证据强度   = f(证据条数, 证据类型多样性, 基准比对的通过情况)
```

置信度低于阈值 → 不走"通过"路径，转入人工或追加采样。

### 4.5.4 监控

- **实时事件流**：SSE 推送，前端时间线展示
- **状态快照**：每 N 个事件或每次状态跃迁生成快照，支持快速恢复
- **异常检测**：失败家族分类 + 异常指标（重试率、熔断率、成本突增、产出停滞）

### 4.5.5 抽样复核与独立评测

复核由内核随机选样，但领域语义判定来自获独立授权的评测适配器。通用结构检查不能声称等价于所有领域规则；没有独立适配器的领域必须标记能力缺口，风险产物转人工，不能假装已完成独立语义复核。

被抽中的产物进入 `resample_pending`，**在结果完成前不可交付或计为普通成功**。其他未被抽中产物可按风险策略继续；不能同时把同一产物的复核称为同步阻断又称为非阻塞。低风险事后质量监测若另行开启，需单独指标和风险窗口，不能冒充交付前复核。

| 项 | 规则 |
|---|---|
| 抽样 | 内部随机源、分风险层；常规默认≥1%，新 Pack 冷启动与高风险提高比例，具体版本随规则冻结 |
| 严重偏差 | 一次高风险错误即暂停该 Pack 相应路径自动放行，P1；复核失败产物始终阻断 |
| 一般偏差 | 冻结窗口内观测偏差率>2%触发P2并暂停对应规则自动放行，人工检查后发布修复规则版本；不再另设“连续两次才暂停” |
| 样本不足 | 报告估计值、样本量与单侧95%区间；不能用少于30例或零偏差直接声明≤2% |
| 冷启动 | 达不到预设置信证据时标记 provisional，高风险100%独立复核；不能依靠低流量逃避检查 |
| 恢复 | 独立评审修复版本、回归通过、对受影响产物追溯后由授权角色恢复；执行 Agent 无权恢复 |

在独立同分布假设下，30例零偏差的单侧95%上界仍约9.50%；零偏差要把该上界压至2%，至少149例。1%抽样下期望约需14,900个通过产物，真实样本相关性还需分层处理。NFR-018 同时报估计与不确定性，不以固定最低样本数替代置信度。

独立适配器与领域规则语义差异须明确记录；抽样衡量其约定判据差异，不能把二者必定语义等价当作前提。

## 4.6 M5 · 反馈循环与优化

### 4.6.1 失败家族

| 家族 | 判据（结构化指纹） | 默认处置 |
|---|---|---|
| `quota` | 模型配额耗尽、限流响应、余额不足 | 熔断该模型 → 切备用 → 降并发 |
| `network` | 连接重置/拒绝/超时、DNS 失败、5xx | **窗口态重试**（换期重入），不计模型能力错误；计入端到端完成率/耗时/成本（P7） |
| `scope_denied` | 目标越界、权限不足、命中排除清单 | 不重试，阻断并留痕 |
| `canceled` | 人工暂停/取消 | 挂起 |
| `crash` | Worker 进程异常退出 | 重启 Worker，保留现场（不改任务状态） |
| `auth` | 凭据失效、鉴权失败 | 刷新凭据或阻断 |
| `other` | 兜底 | 升级人工 |

**领域包可扩展家族，但内核保证 P7 不变量**：网络类失败在任何统计口径中都不计入"能力不足"。

### 4.6.2 六种修复原语与原子 RepairPlan

| 原语 | 动作 | 约束 |
|---|---|---|
| Rebind | 用新参数重跑节点 | 创建新输入版本；旧签名不可沿用 |
| InsertPrereq | 插入前置任务子图 | 同租户/run、前置可达、无环，受目标范围约束 |
| Substitute | 更换 Agent/工具/模型 | 撤销旧 claim；验证不能降档；接口契约保持 |
| Rewire | 改变局部依赖 | 校验无环与受影响节点版本 |
| Bypass | 用已有证据证明当前节点效果已满足 | 不得跳过硬门禁，须记录证明与适用版本 |
| Escalate | 请求协调者全局重规划或人工介入 | 保留冻结验收，不能重写目标函数 |

RepairPlan 包含 plan_id、目标 graph_revision、完整节点/边变化、受影响下游集合、撤销 claim 集合及理由。命令在单事务内锁定 graph/run 版本，校验 CAS、范围、依赖完整性、无环、预算与安全规则，再更新控制状态、追加差异事件/回执/outbox。版本冲突拒绝并重算，不把过时计划静默套入新图。

**回退分四类处理**：

1. 投影回放：读取已记录事件重建旧时点，不改变现场执行。
2. 工作流回退：追加带完整目标版本/差异的 `graph.reverted`，递增图版本并撤销受影响 claim。
3. 结果失效：沿真实依赖图把下游 Task/Artifact 标记 stale，作废签名与验证记录；即使下游已经完成也不能继续用于新成功判定。
4. 外部效果：已发生的写操作不会因图回退撤销。明确工具补偿协议时创建独立可审计补偿动作；未知、不可补偿或补偿失败转人工，保持外部效果状态。

事件可以重建投影状态，**不能自动补偿外部效果**。在途外部动作已越过发起点时，撤销 claim 只能阻止新的发起，必须等待/核对既有动作，不承诺即时撤回已送达请求。

### 4.6.3 成功、停滞与预算终止

成功必须由冻结验收判据全部通过决定；近期没有新产出只能证明停滞。停止自动尝试不等于问题已解决。

```python
def evaluate_stop(acceptance_passed, hard_gates_passed, window, budget, cfg):
    if acceptance_passed and hard_gates_passed:
        return "succeeded"
    if budget.exhausted:
        return "budget_exhausted"
    if (window.new_pass < cfg.min_new_pass
            and window.new_effective_assets < cfg.min_new_assets
            and window.idle_rounds >= cfg.max_idle_rounds):
        return "stalled"
    return "running"
```

窗口 W 为配置固定轮数；new_pass 只计首次满足独立验收的任务；new_effective_assets 先按内容去重，再按预注册的验收进展/证据增量判断有效性。字节哈希仅去除完全相同内容，微调无关文本不能无限推迟停滞。即使有效性无法可靠机械判定，绝对轮次/token/成本上限仍必须终止循环。

阈值 `min_new_pass/min_new_assets/max_idle_rounds/W` 由授权策略版本发布，具有明确上下界，例如 idle 为1–20轮、W为2–40轮；具体范围按任务类评审，不能仅有下限。执行主体不可改在途阈值。stalled 默认进入 awaiting_human 或 failed，绝不映射到普通 done。

分别报告 L1 冻结验收成功率、L2 意图成功率、L3 验证成功率；例外、停滞、取消与基础设施失败分别展示。分母不同时不直接计算“层级衰减”作为净收益。

### 4.6.4 熔断

触发条件（任一）：
- 修复轮次达上限
- **token 额度或金额额度触顶**（§4.4.4 三元组预算）
- 置信度低于阈值且追加采样后仍不达标
- 连续 N 次同家族失败
- 同一 Artifact 连续被同一门禁拒绝达 K 次（避免死循环烧钱）

处置：Intent → `awaiting_human`，事件记录熔断原因、累积证据、已尝试的原语、已消耗成本。**熔断不吞掉证据**——所有尝试都留在事件流里，供人工快速裁决。

**熔断后的资源与时效**：

| 项 | 规则 |
|---|---|
| 租约 | `awaiting_human` **不持有执行租约**（否则挂起的 run 会长期占用 Worker 配额） |
| 人工 SLA | 默认 4 小时（SLA可按授权运维策略配置）；超时未处理 → P2 告警 + 自动降级路径 |
| 自动降级 | 超时后按 Pack 声明的 `on_exhausted` 执行（默认：标记 `failed` 并保留全部证据，不再自动重试） |
| 成本 | 熔断发生时立即停止该 Intent 后续的模型调用（网关侧拒绝） |
| 恢复 | 人工裁决后重新授权、预留预算与容量、取得新claim；副作用按§4.7.4核对，不能仅靠提交幂等键重跑 |

### 4.6.5 自适应路径

| 自适应对象 | 机制 | 记录 |
|---|---|---|
| Prompt | 失败类型 → Prompt 策略映射；可基于历史成功率选择 | `repair.applied` 事件含原语、策略、prompt 摘要 |
| 工具选择 | 同一任务在不同轮次可选不同工具 | 同上 |
| 工作流路径 | Rewire / Bypass / InsertPrereq 改图 | `intent.rewired` 事件含边的变更前后 |

### 4.6.6 Anchor 与不可自改约束

内核最低安全要求由受审代码发布；Goal acceptance、held-out 版本和领域规则通过授权发布形成内容寻址快照。执行、规划和优化 Agent 均无更新当前 run 快照的权限。规则变更产生新版本；降低要求不能作用于在途 run，修改验收需新建 Goal/Anchor 并重验。

紧急拒绝清单、凭据撤销与资源关闭可即时收紧在途操作，变更有发布主体、版本、原因与影响范围事件。即时收紧不代表允许运行主体重新打开被拒绝路径。

自评与独立 held-out 的分歧率只在同一任务集、同一版本与同一分母上计算；held-out 不用于提示词、调参或经验条目。修复路径只能调整生产侧输入、工具、上下文和图，不持有规则发布、验收修改或独立评测写权限。

## 4.7 支撑能力 · 工具与外部系统集成

### 4.7.1 MCP 接入

**协议要点（当前规范为无状态核心）**：
- 无 `initialize` 握手；无 `Mcp-Session-Id`
- 每个请求自带协议版本、客户端身份与能力声明 → 可直接落在负载均衡后的任意实例
- Streamable HTTP 请求须带 `Mcp-Method` 与 `Mcp-Name` 头，便于网关按方法/工具名路由与限流
- 长期任务不在协议层维持会话，需由调用方显式传递 handle
- 客户端须校验签发者（RFC 9207 `iss`）

**Server 清单**（自建，均可在无 LLM 环境下单测）：

| Server | 暴露工具 | 类别 | 说明 |
|---|---|---|---|
| `repo-search` | `search_code`, `read_file`, `list_tree` | **代码检索** | 跨文件检索、片段读取 |
| `test-runner` | `run_tests`, `get_report` | **代码执行** | 在沙箱内执行测试与脚本，返回结构化结果 |
| `linter` | `lint`, `explain` | **代码检索** | 静态检查与规则解释 |
| `sql-reader` | `query`, `describe` | **数据库** | 只读 SQL 查询；写操作需显式开启并走审批 |
| `web-retrieval` | `search`, `fetch` | **搜索引擎** | 外部检索；返回内容按不可信数据处理（消毒层） |
| `scientific` | `eval`, `plot` | **科学计算** | 数值计算与绘图；沙箱内执行 |

> 这六类对应企业级 Agent 平台必须覆盖的**代码检索 / 代码执行 / 数据库 / 搜索引擎 / 科学计算**五类外部能力（FR-036~FR-040）。Server以薄适配方式实现，可复用经过固定版本与来源核验的协议SDK或沙箱接口；执行器须经隔离/权限验证，不因现成可用而直接获得控制面权限。

**安全约束**：MCP Server 视为第三方代码执行面。命令执行器白名单（拒绝 `npx`/`uvx`/`sh`/`python` 等通用执行器直接拉取）、版本固定（禁止未 pin 的包拉取）、出网经出口网关。

**执行性能**：`test-runner` 与 `scientific` 属于高频工具，冷启动容器的开销不可忽略。执行器采用**常驻进程池 + 工作区快照复用**（见 §6.1 性能预算中的沙箱启动项），而非每次调用新建容器。

### 4.7.2 工具注册中心

```sql
CREATE TABLE tool (
  id           TEXT PRIMARY KEY,
  tenant_id    UUID NOT NULL,
  kind         TEXT NOT NULL,       -- mcp | builtin | api | function
  server       TEXT,                -- mcp server 标识
  name         TEXT NOT NULL,
  schema       JSONB NOT NULL,      -- 参数 schema
  version      TEXT NOT NULL,
  idempotent   BOOLEAN NOT NULL,    -- 幂等性标注：重复调用是否安全（FR-059）
  supports_idempotency_key BOOLEAN NOT NULL DEFAULT FALSE,  -- 是否支持 Idempotency-Key 透传
  requires_approval BOOLEAN NOT NULL DEFAULT FALSE,
  health       TEXT NOT NULL,       -- healthy | degraded | unavailable
  last_error   TEXT,
  updated_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

**健康检查**：定期探活；`unavailable` 的工具从路由中剔除，并在派单时提前失败（不把超时留给 Worker）。

**`idempotent` 标注是必填字段**，缺失时工具注册被拒绝。语义：

| 标注 | 含义 | 崩溃恢复时的处置 |
|---|---|---|
| `idempotent = true` | 重复调用不增加额外副作用（只读结果可随时间变化，不要求响应字节相同） | 可安全重放 |
| `idempotent = false` | 重复调用会产生额外效果（如发消息、创建工单） | **不自动重放**，转人工（§4.7.4） |
| `supports_idempotency_key = true` | 工具端接受稳定call_id并在约定作用域、参数绑定和有效期内原子去重 | 可重放，但必须携带**同一**幂等键 |

> 未标注为幂等的工具默认按 `idempotent = false` 处理。**默认取向是保守的**：平台宁可漏做一次并转人工，也不重复做一次。

### 4.7.3 出口网关

所有外部访问（模型、MCP Server 调用的外部资源、外部 API）经统一出口：

- 域名/IP 白名单 + 解析后校验（防 DNS 重绑定：解析一次、连接时校验实际 IP）
- 端口固定（禁 CONNECT 到任意端口）
- 元数据地址、链路本地、保留网段硬黑
- 每租户/每工具速率限制与并发上限
- 请求/响应留痕（脱敏后）
- 可挂审批门：高风险工具调用进入人工审批队列

### 4.7.4 外部副作用发起、确认与恢复协议

每次逻辑动作使用稳定 `call_id`，不随 Worker 重派、网络重试或平台提交的输出哈希变化。登记工具时须说明副作用类别、幂等性、键作用域、参数绑定、并发去重、结果查询及去重有效期；不能只信任第三方自报注解。

**发起流程**：

1. 出口校验租户/run/task、有效 claim/epoch、输入版本、作用域、紧急拒绝与预算；原子取得 `call_id` 唯一发起权，写完整 `tool.intent` 及调用账本。
2. 发起记录达到部署声明的持久化等级后才允许实际外部请求；不可重放动作要求同步持久化或独立可靠账本，并验证恢复覆盖范围。
3. 由可信出口执行单次发送。对非幂等写禁用 HTTP 客户端/代理的透明自动重试。执行 Worker 不能绕开出口持有外部写凭据。
4. 收到确认后，同事务记录 `tool.done`、实际效果标识与结果摘要；结果未知保持 indeterminate，所依赖下游挂起。部分生效独立标记 partial。

| 已知状态 | 恢复动作 |
|---|---|
| intent+done，内容与归属完整 | 取回记录结果，不重复发起 |
| 仅intent，工具动作本身幂等 | 在当前授权、版本与恢复策略允许时重试；复用call_id，不假定响应相同 |
| 仅intent，非幂等但有可靠去重键 | 仅在参数/作用域一致、去重期限仍有效时复用同call_id；否则转人工 |
| 仅intent，无安全重放契约 | indeterminate，冻结依赖，人工核对 |
| 完整记录区间内无intent | 经新claim/预留及权限校验后首次执行 |
| 灾备可能丢失近期intent/调用账本 | recovery_hold；核对外部系统或独立账本，不能视作从未发起 |

人工可确认已生效、确认未生效、标记部分生效；“未生效”必须记录核对方式与证据，恢复执行另发授权而非直接在页面重试。旧 Worker 无权发起新动作；已经送达的请求不能依靠 claim 撤销取消，其结果须追踪。

平台不承诺跨任意外部系统 exactly-once。NFR-022 的零重复边界是：在唯一出口、稳定call_id、完整持久记录与约定工具契约成立时，不由平台自动恢复重复发起不可安全重放动作。未知窗口宁可暂停核对；不能声称知道外部必然只执行一次。

### 4.8.2 完整事件信封、分链摘要与检查点

按 `(tenant_id, run_id)` 分链；同一run在事务中锁定run头，连续分配seq并同步计算事件哈希。不同run可并行。先以实测判断摘要计算成本；v2.1 不采用“事件先落地再修改原行补hash”的方案。

```python
def event_hash(event):
    envelope = {
        "hash_version": 1,
        "tenant_id": event.tenant_id, "run_id": event.run_id,
        "id": event.id, "chain_id": event.chain_id, "seq": event.seq,
        "schema_version": event.schema_version,
        "type": event.type, "actor": event.actor,
        "ts": event.ts_utc_canonical,
        "payload": event.payload,
        "submission_key": event.submission_key,  # null参与规范编码
        "request_digest": event.request_digest,
        "prev_hash": event.prev_hash.hex(),
    }
    return sha256(b"loom:event:v1:" + canonical_json(envelope)).digest()
```

canonical_json 采用跨实现一致的 UTF-8、字段排序和数值表示；禁止 NaN/Infinity，时间统一UTC规范形式，金额采用整数单位避免浮点歧义。链起点使用约定全零摘要并绑定租户/run；hash自身不纳入信封。业务角色对event无UPDATE/DELETE权限。

签名服务异步追加独立 checkpoint，认证租户、run、seq、当前根、hash版本、签名算法/密钥ID和结束标记；事件行保持不可变。运行中定期签名而非只在结束时，默认每1000事件或60秒（可收紧），结束必须签最终根。外部只追加存储按检查点锚定；锚定延迟与尚未锚定区间显式可见。

校验完整信封摘要、连续seq、检查点签名及预期末seq/结束标记，检测字段变化、跨run复制、删除、重排和已认证链尾截断。只有未锚定尾部且外部无预期根时，不能仅凭内部hash证明不存在全尾重写；报告这一边界。密钥轮换保留验证材料。

跨run因果关系用受摘要保护的 caused_by_run_id/event_id；不使用墙钟时间推断全局因果序。链内串行，跨链校验并行；10,000 events/s 为需压测的目标。

|---|---|---|
| 协作图、看板、记忆索引 | 查询、展示、检索 | 事件持久游标驱动；重复消费只生效一次，可从事件与保留对象重建 |

# 5. 可靠性与正确性

## 5.1 幂等提交、事务 outbox 与可靠消费

```text
请求：tenant + submission_key + operation + resource + expected_version + args
1. 规范化完整请求并计算request_digest。
2. 进入数据库事务，按固定次序锁run/资源账本。
3. 查询回执：相同键同digest返回旧回执；同键异digest拒绝。
4. 校验命令、版本、归属，原子修改业务/控制状态。
5. 同事务追加完整事件、回执、outbox；提交。
6. 持久发布器读取未确认outbox，等待JetStream publish ack后记录投递状态。
7. 消费者按event_id和持久游标去重，先提交处理结果再ack。
```

并发同键由唯一约束最终裁决；冲突事务回滚后读取并核对已提交回执，不能把唯一键异常当随机500。完整摘要覆盖操作类型、资源、输入版本和参数，避免不同操作误共用键。

数据库提交成功但尚未发布时进程退出，outbox仍在；发布成功但确认状态未写回可重投，消费方保证一次生效。相同命令重试直接返回回执不会丢掉先前持久outbox。NATS的至少一次交付不替代数据库到消息系统的桥接。

无幂等键仅限明确允许的系统事件，规范哈希编码null；带外部副作用的命令必须有稳定call_id。RepairPlan跨多个变更仍是单事务命令；平台提交去重不覆盖外部系统效果。

## 5.2 失败处置矩阵

| 家族 | 是否重试 | 重试策略 | 是否计入正确性统计 | 是否升级人工 |
|---|---|---|---|---|
| quota | 是 | 切模型 → 降并发 → 熔断 | 否 | 长时间不可用时 |
| network | 是 | 窗口态重入（换期） | **否** | 超出窗口预算 |
| scope_denied | 否 | — | 否（计为策略拒绝） | 是（需人工授权） |
| canceled | 否 | — | 否 | 否（人已介入） |
| crash | 是 | 重建 Worker + 重投（幂等键相同） | 否 | 连续崩溃 |
| auth | 视情况 | 刷新凭据 | 否 | 刷新失败时 |
| other | 视情况 | 按原语修复 | 是 | 达熔断条件 |

## 5.3 降级与容错

| 依赖不可用 | 降级策略 |
|---|---|
| 主模型供应商 | 按路由切备用 → 降档模型 → 熔断该模型 |
| 备用模型也不可用 | 任务挂起（不消耗预算），等待恢复 |
| 投影引擎滞后 | 控制面读事件表兜底（慢路径），并告警。**注意：调度热路径不依赖投影**（§4.2.2），因此投影滞后不影响调度正确性 |
| NATS 不可用 | 保留持久outbox并按退避续投；数据库可用时命令可按配额受理，积压超过阈值停止新派发并告警；不依赖本地队列防丢 |
| Postgres 主库不可用 | 自动切换备库；不可用时控制面只读降级 |

### 5.3.1 执行降级与验证降级的分界

**执行通道可以降档，验证通道不可以。**

| 通道 | 主模型不可用时的处置 | 理由 |
|---|---|---|
| **执行通道** | 切备用 → 降档模型 → 熔断 | 降档只影响产出质量，产出仍须过门禁才能被采纳 |
| **验证通道** | 切**同 tier** 备用 → 熔断并转人工 | 降档会让"验证通过"的判据强度随负载静默下降，且无记录 |

**约束的具体形式**：

```python
def select_validator(candidates, required_tier):
    # required_tier = 首签模型的 tier
    tier_rank = {"standard": 1, "strong": 2}
    eligible = [c for c in candidates
                if tier_rank[c.model_tier] >= tier_rank[required_tier]]
    if not eligible:
        raise VerificationChannelUnavailable()   # 熔断 + 转人工，不降档
    return weighted_pick(eligible)
```

| 规则 | 说明 |
|---|---|
| 层级不降 | 第二签 `model_tier ≥` 第一签 `model_tier`；同 tier 内部可自由切换 |
| 记录 | 每次验证签记 `verification.tier` 事件，记录使用的模型与 tier |
| 指标 | `verification.downgraded_sign_rate`——**必须恒为 0**，非 0 即 P2 告警（§8.4） |
| 熔断 | 同 tier 全部不可用 → 该 Intent 转 `awaiting_human`，不自动放行 |

> **这条边界的价值**：如果验证可以降级，那么"系统在高负载时验证变松"这件事会被完全隐藏，直到某天出现一个本该被拦住的错误结论。**指标恒为 0 的强约束把这个问题变成了可观测、可告警的事实。**

## 5.4 Anchor 与规则版本的存储固化

| 对象 | 存储与权限 | 变更语义 |
|---|---|---|
| 内核安全底线 | 代码发布、双人评审 | 运行主体不能改；发布可收紧，不隐式降低在途要求 |
| Goal acceptance/内容型Anchor | 内容寻址只追加对象+数据库digest | 不UPDATE；改变验收需新Goal/版本并重验 |
| 领域判据/阈值/排除清单 | 授权发布的签名版本快照 | 可发布新版本，run固定旧快照；Pack执行身份无发布权限 |
| 紧急拒绝/凭据撤销 | 独立安全通道，有版本与审计 | 可立即收紧在途操作；解除需授权，不视为Agent自愈动作 |

所有修改在途Anchor或降低硬约束的写接口均拒绝并审计。不能仅用Python字典中的True值或“编译期”标签证明不可改；必须由数据库角色、对象权限、命令授权和真实拒绝测试保证。

## 5.5 灾备、重建与副作用安全

PostgreSQL WAL连续归档+每日全量、保留对象按内容寻址和版本管理；检查点在独立只追加存储保留。一般业务日志RPO≤5min是部署目标，不自动适用于不可重放动作的发起账本。

恢复流程：校验备份/检查点→隔离环境重建日志与对象→按同一截止点重建投影及命令账本→标记可能丢失记录的时间窗和run→冻结相应外部写→核对独立调用账本/外部效果→取得新分片epoch→逐run解除恢复挂起。若没有足够证据确认记录完整，保持recovery_hold，不能按“无intent”自动执行。

不可安全重放动作发起前，调用账本须达到约定同步持久性；主备切换若不能证明这一前提，必须冻结并人工核对。恢复时旧Worker凭据/epoch失效，但已送达外部请求仍需追踪。

每月在隔离环境演练：投影等值、outbox续投、claim重建、重复消息去重、动作已执行但响应丢失、故障前发起记录丢失、旧Worker存活。验收分别记录“既有业务事件无重复”“新增恢复审计事件合法”“无平台自动重复发起不可重放动作”；恢复审计会新增事件，不能要求总事件数完全不变。

RTO≤30min须声明事件数、对象体量、硬件和恢复方式；大体量run可分段快照恢复，但不能跳过完整性与未知副作用检查。事件、Evidence/Observation、Artifact及签名检查点默认联合保留180天；90天后可冷归档但仍可取回验证，无法取回时明确标记replay_incomplete。

# 6. 性能与容量

## 6.1 性能预算

| 路径 | 预算 | 目标 |
|---|---|---|
| 调度决策（选 Agent） | ≤ 5 ms | 候选计算可用内存；实际认领含数据库原子校验，二者延迟分开报告 |
| 图写入（投影更新） | ≤ 100 ms P99 | 批量写 + 异步物化 |
| 事件写入 | ≤20 ms P99（待压测） | 事务内完整信封摘要+outbox；跨run并行，签名检查点异步追加 |
| 端到端派发（决策 → Worker 收到） | ≤ 200 ms P99 | 含队列投递 |
| 上下文组装与裁剪 | ≤ 50 ms | 分层裁剪（§4.4.7）+ 结果缓存 |
| 意图提议（Goal → 首个可派发 Task） | ≤ 15 s P99 | 并行提议（§4.4.8），NFR-019 |
| 沙箱启动（工具执行器） | ≤ 200 ms | 常驻进程池 + 快照复用，避免冷启动容器 |
| 门禁判定（含领域门规则求值） | ≤ 50 ms | 内核求值器 + 复杂度上限 |
| 审计链校验 | ≥ 10,000 events/s | 分链并行校验，NFR-021 |

**全图注入基线**（NFR-012 的参照物）：把当前 run 的全部 Artifact + Observation 不经裁剪直接注入上下文。压测时同时测量基线与裁剪后两种情形的 token 数，比值即 NFR-012 的度量对象。基线实现纳入 §10.6 压测项，**不使用未经实现的估计值作为度量基准**。

**非目标**：模型推理时间不计入平台延迟预算（由模型网关单独观测）。但**意图提议的推理时间计入**——因为它位于关键路径上（§4.4.8）。

## 6.2 容量模型与数据保留

生产目标参考3个API/调度副本、PostgreSQL主备及3节点JetStream。目标值需以实测环境说明验证，不适用于本地SQLite演示。

| 资源 | 目标与口径 |
|---|---|
| 正在执行Worker槽位 | 总计200，含验证预留；排队任务不占执行槽位 |
| run/就绪队列 | 可有500个未终止run，每run平均20个就绪/排队任务，即约10,000排队任务；同时执行仍≤200 |
| 事件写入 | 单分片峰值2,000 evt/s，压测持续30min；平均负载与峰值占空比另行记录 |
| 协作图 | 初始验收100万节点；记录run分布、最大单run及图深度 |
| 保留期 | 事件、Evidence/Observation、Artifact、规则快照及检查点联合180天，热/冷分层但可取回验证 |

若2,000 evt/s持续180天，将产生31,104,000,000条事件；不能据此仍假设单库小数据量。容量评审须提供平均/峰值事件大小、索引倍数、压缩、对象体量、备份成本、分片和恢复吞吐。单run热点通过状态批次/合理分解控制，分链只提升跨run并行，不能消除链内串行。

队列深度持续超执行槽位2倍触发扩容评估；容量扩展受预算和验证预留下限约束。事件P99持续超过目标先定位锁/索引/磁盘，再考虑分片；不能用分片掩盖单run顺序约束。投影滞后只影响展示，控制账本仍原子校验。

## 6.3 压测方法

| 层级 | 场景 | 产出 |
|---|---|---|
| 微基准 | 调度打分、上下文组装、投影更新 | 延迟分布 |
| 组件级 | 事件写入、队列吞吐、投影重建 | 吞吐与延迟 |
| 端到端 | 完整任务流（真实模型调用） | 端到端延迟、成功率、成本 |
| 容量 | 阶梯加压至 200 并发 Worker | 拐点与瓶颈定位 |
| 混沌 | 注入 Worker 崩溃、模型超时、队列分区 | 恢复行为与数据一致性 |
| 回归 | 基准场景集 | 成功率、回归差异 |

**基线对照**：业务效果统一为B1人工使用通用Agent、B2单Agent、B3固定串行工作流和Loom；广播调度可作附加消融，不替代人工基线。平台微基准不要求人工执行，但业务效果必须相同任务、模型资源与成本口径；分别报告总成本、完成率和条件正确率。

## 6.4 成本模型

| 成本项 | 计量 | 控制手段 |
|---|---|---|
| 模型推理 | token × 单价 | 分级路由（便宜档优先）、缓存前缀复用、**成本闸门**（下述） |
| Worker 计算 | 容器时长 | 空闲回收、任务合并、解释器常驻池 |
| 存储 | 事件 + 对象存储 | 保留期策略、Observation 归档 |
| 人工介入 | 裁决工时 | 熔断阈值调优（减少无效熔断）、§8.6 的证据摘要缩短裁决时间 |
| 验证开销 | 复核调用 token | 分级验证：仅高风险结论双签；低风险单签 |

### 6.4.1 成本硬闸门与软预算

调度器决定任务/运行额度；Model Gateway是所有模型调用必经点，以原子预算预留而不是事后求和授予权限（§4.4.4）。数据库锁/CAS覆盖run共享总账与任务子账，两个并发请求不能消费同一余量。

每次调用绑定call_id、模型/价格版本、输入token、强制最大计费量、预留和结算。支持可靠上界的路由必须满足 `spent + reserved <= ceiling`；结果未知保留其最坏预留，查询清楚后再结算。规划、Reasoner并行子任务、独立验证、重试、复核与收费失败都计入。价格变更产生新版本，不追溯重算历史费用。

供应商无法强制输出/推理token计费上限或取消后计费不可界定时，只能声明软预算与估算误差，不能将其纳入NFR-020硬封顶承诺。预算不足在调用前拒绝；已发起调用不能保证通过断流停止计费。80%预警只是观测，不替代预留。

验收包括两个并发任务争最后额度、重复结算、超时未明、追加验证、stream中断和模型路由切换；所有历史费用与在途负债可审计。

### 6.4.2 成本可见性

每个 run 输出 `cost_usd` 分解（按模型、按角色、按轮次、按门禁）。这是"成本可解释"的基础，也是领域包定价与 §1.7 价值论证的数据来源。

**单次成功任务成本**（`cost_per_success`）是比"单次任务成本"更有意义的指标——它把成本与产出联系起来，是 §1.7 主指标的直接数据源。

# 7. 安全与合规

## 7.1 威胁模型

| 编号 | 威胁 | 影响 | 缓解 |
|---|---|---|---|
| T1 | 提示注入经外部内容进入编排/记忆/状态 | 决策被劫持 | 外部内容一律标记为不可信数据，不进入指令位；指令与数据分离；工具出参经消毒 |
| T2 | 跨 Agent 提示注入（一个 Agent 的产出被另一个当作指令） | 链式污染 | Agent 间只传结构化产物与证据引用，不传自由文本指令；产出统一经消毒层 |
| T3 | 工具投毒（工具描述含恶意指令） | 工具调用被诱导 | 工具描述视为不可信；工具调用参数经 schema 强校验；敏感工具走审批 |
| T4 | 权限提升（Agent 尝试越权） | 越权操作 | 工具调用在出口网关按凭据鉴权；能力最小化；作用域门 |
| T5 | 凭据泄漏 | 密钥外泄 | 凭据在 Worker 侧按租户挂载、进程级剥离；日志与事件脱敏；出口禁元数据地址 |
| T6 | 审计链被篡改 | 事后无法追溯 | hash chain + 外部锚定；审计视图只读 |
| T7 | 沙箱逃逸 | 宿主机沦陷 | 容器 + gVisor + 只读根 + 无特权 + 出网受限 |
| T8 | 拒绝服务（Agent 无限循环烧钱） | 成本失控 | 预算熔断 + 轮次上限 + 成本上限 + 租户配额 |
| T9 | 领域包恶意行为 | 内核被污染 | Pack 沙箱加载；只经注册表交互；无内核代码变更（CI 强制） |
| **T10** | **领域包判定放水**（提供宽松规则让自身产物通过） | 整个可信度体系失效 | 判定逻辑在内核（原则 P8）；领域门规则声明化 + 装载期静态分析；**抽样复核**（§4.5.5）；偏差超阈值自动降级并告警 |
| **T11** | **崩溃重放导致外部重复写** | 外部系统数据损坏 | 工具幂等性标注（§4.7.2）；四阶段副作用协议；不确定态**不自动重放**（§4.7.4）；NFR-022 强约束 |
| **T12** | **调度决策基于滞后状态** | 派发到满载 Agent；验证预留失效 | 热路径状态权威化 + CI 静态断言禁止读投影（§4.2.2） |

## 7.2 信任边界

| 域 | 可持有内容/权限 | 不得推导的保证 |
|---|---|---|
| 控制面可信服务 | 命令校验、规则版本、账本事务、独立验证写权限 | 数据进入图不代表语义真实；各服务仍最小权限 |
| 声明式Pack | 类型化角色、路由、规则引用、场景与模板 | 不能靠schema证明规则充分，不能写受信指标或评测真值 |
| Worker/模型/检索数据 | 提议、代码/报告、引用与外部数据 | JSON字符串/代码/摘要同样可能携带注入，不因结构化变可信 |
| 工具执行镜像 | 隔离进程/容器中的具体工具执行 | 不进入控制面进程，不持有全库或跨租户凭据 |
| 出口/模型网关 | 校验授权、scope、epoch、call_id、预算并实施外部调用 | 不接受模型自报授权，不承诺撤回已送达请求 |

模型建议与操作权限分离：输入消毒、结构化数据、来源标签减少攻击面；最终状态变更、外部写与敏感读取都须按真实主体和资源再次鉴权。签名、证据摘要、受信执行器和独立评测分别解决不同问题，不互相替代。

领域规则发布者、Pack开发者、执行器发布者、独立评测持有者和审计角色分离。可执行第三方代码不得作为“薄工具”随manifest在控制面import；注册表不是安全沙箱。

## 7.3 权限模型

| 层级 | 机制 |
|---|---|
| 租户 | RLS 行级隔离 + 独立队列分区 + 独立凭据命名空间 |
| 主体 | OIDC 认证；服务账号 / 用户 / Agent 三类主体 |
| 角色 | RBAC（admin / operator / developer / auditor / viewer） |
| 资源 | 图节点级授权（可对单个 Intent/Task 设置可见性与可操作性） |
| 动作 | 工具调用级授权（按工具 × 参数范围 × 目标域） |
| 人工 | 高风险动作走审批队列；审批人不可是发起者 |

**授权判定位置**：出口网关（对外部动作）+ 调度器（对图操作）。两处都做，因为二者都可能被绕过（一个绕过另一个仍会成功）。

### 7.3.1 RLS、审计与对象访问

业务数据库角色非超级用户、非表owner、无BYPASSRLS；核心表启用且必要时FORCE RLS，租户上下文由已认证服务设置，连接池归还前清理。SELECT与WITH CHECK分别约束读写，复合外键阻断跨租户/run引用；测试必须使用真实业务角色。

审计默认使用**没有BYPASSRLS的独立只读角色**，RLS允许该角色读取已授权audit_scope表定义的租户集合；独立只读副本隔离查询负载，不因此扩大可见范围。若另设灾难性break-glass特权通道，应有独立服务级强制授权、短期凭据、双人审批和外部审计，不能声称由RLS限制已绕过RLS的角色。

跨租户审计查询、范围授予和导出都记录主体、目的、范围、时间、命中量和结果摘要；只读副本不能本地写审计，操作记录送入独立可靠审计入口。导出需audit:export权限。对象存储采用授权下载入口或短期签名URL，生成前验证tenant/run，解析证据时复核摘要及归属，不能仅靠不可猜测ID保护数据。

验证两租户交叉资源引用、对象下载、claim复用、审计范围扩大、池连接上下文残留和owner角色绕过等路径。

## 7.4 沙箱与执行隔离

| 项 | 策略 |
|---|---|
| 文件系统 | 只读根 + 任务级可写工作区（专用卷）；**符号链接不按"真实路径复核"判定**——复核与使用之间存在 TOCTOU 窗口 |
| 路径安全实现 | 使用 `openat2(RESOLVE_BENEATH)` 或等价的挂载 namespace 约束，路径解析在**内核层**完成并与打开操作原子绑定；不能实现时退化为"可写区限定在专用卷 + 禁止硬链接 + 禁止跨卷挂载" |
| 进程 | 非 root、禁止提权、seccomp 限制系统调用 |
| 网络 | 仅允许经出口网关；默认拒绝 |
| 资源 | CPU/内存/时长上限；超限杀死并归类为 `crash` |
| 凭据 | 仅注入任务所需；子进程环境剥离；不写入事件流 |
| 隔离级别 | gVisor（默认）/ Kata（强隔离场景）/ 裸进程（仅受信开发环境） |
| 执行器复用 | 高频执行器（代码执行、科学计算）采用**常驻进程池 + 工作区快照复用**，池按信任域隔离；任务结束清空可写区/凭据/环境和进程状态，跨租户不得复用未重置实例，避免每次调用冷启动容器（见 §6.1 沙箱启动预算） |

> **为什么不用"真实路径复核"**：复核时读取链接目标，再与允许前缀比较，最后按该路径打开——这三步之间，链接可以被替换。这不是实现瑕疵，是检查与使用之间的固有竞态。正确做法是让内核在打开时原子地完成"解析 + 约束检查"（`RESOLVE_BENEATH`），或干脆消除越界可能（专用可写卷）。

## 7.5 审计与合规

- **审计链**：事件流 + **按 run 分链的 hash chain**（§4.8.2），独立检查点签名与周期外部锚定
- **操作留痕**：人工裁决、策略变更、Anchor 变更、领域包加载、领域门规则降级全部留痕
- **历史回放**：给定run_id、日志截止点与保留对象/规则版本，可重建已提交轨迹，回放禁止外部调用；重新调用模型不承诺种子相同即同轨迹
- **数据保留**：事件、Observation/Evidence、Artifact、规则快照和检查点联合保留180天；90天后可转冷存储但仍可取回校验，删除须显式缩短可回放范围
- **导出**：提供按租户/时间/主体维度的审计导出（CSV/JSON），用于合规交付。导出经独立审计通道（§7.3.1），导出行为本身进审计链
- **不确定态可查**：全部外部副作用的不确定态可独立检索与导出（§4.7.4）

## 7.6 领域合规

领域包可声明合规要求，由内核强制（**领域包不能降低内核的强制项**）：

| 类别 | 声明 | 内核强制 |
|---|---|---|
| 授权门 | 任务启动前必须核验的授权要素 | 缺任一要素则 run 无法创建 |
| 作用域 | 允许访问的目标域 | 出口网关强制；越界直接拒 |
| 默认只读 | 写操作需显式开启 | 运行时默认 dry-run |
| 排除清单 | 不得访问的目标 | 内核硬拒绝+授权发布的版本化清单；执行主体不能改，紧急拒绝可立即收紧 |
| 脱敏 | 输出必须过脱敏规则 | 报告交付前强制执行 |
| 报告门 | 报告必含的声明项 | 缺项拒绝交付 |

> 这套机制是内核级的**合规扩展点**：任何领域包接入时即获得"默认安全"的运行姿态，而不必自行实现一遍。

## 8.2 追踪

OpenTelemetry 语义贯穿：`run_id` → `intent_id` → `task_id` → `agent_id` → `tool_call`。
跨 Agent 的调用链通过 `intent_id` 关联，形成一棵可下钻的调用树。模型调用额外记录：模型名、token 分项、缓存命中、耗时。

## 8.3 日志

三流分离：
- **应用日志**（人读，结构化键值）
- **事件日志**（机器读，结构化，append-only）
- **审计日志**（合规读，含 hash chain）

日志中**禁止**出现：模型密钥、用户凭证、完整提示词中的敏感段、未经脱敏的外部响应体。

## 8.4 告警与处置

| 等级 | 条件 | 自动动作 |
|---|---|---|
| P1 | 控制面不可用、事件/检查点校验失败、平台重复发起不可重放动作、一次高风险复核错误、越权修改Anchor成功 | 冻结相关run/Pack自动放行、呼叫值班并启动事件处置 |
| P2 | 投影滞后>60s、outbox持续积压、预算账本异常、验证tier违规、一般复核偏差率>2%、人工处理超SLA | 暂停受影响路径自动放行并通知值班；复核规则按§4.5.5恢复 |
| P3 | 成本接近预算、低风险队列延迟、上下文裁剪量或人工负担异常 | 工单与趋势评估 |

“要求双签却只签一次仍放行”必须由硬门直接阻断，不等待占比达到5%才处理。样本不足显示provisional及风险策略，不能误记为零偏差达标。累计计数告警使用窗口增量/速率，避免历史一次失败导致永久触发。

## 8.6 人工控制台

熔断与争议最终要落到人身上。控制台的设计目标只有一个：**让人在 3 分钟内做出一个负责任的裁决**。

### 8.6.1 三个待办视图

| 视图 | 内容 | 排序依据 | 目标处理时长 |
|---|---|---|---|
| **待裁决（争议）** | 双签不一致的产物 | 严重度 × 置信度缺口 | < 30 min |
| **待裁决（熔断）** | 达到熔断条件的 Intent | 剩余 SLA（最紧急优先） | < 4 h |
| **待裁决（副作用不确定）** | 外部写操作状态未知 | 外部系统影响面 | < 1 h |

### 8.6.2 证据摘要视图

每个待裁决条目呈现**一屏可判**的摘要，而不是让操作者自己去翻事件流：

```
┌─ Intent: 修复跨模块鉴权缺陷 ───────────────────────┐
│ 目标    : Goal#a1f2 · 验收判据 3/3 未达成            │
│ 状态    : 熔断（第 3 轮修复后）                     │
├─ 失败分类 ─────────────────────────────────────────┤
│ 家族    : other / 断言不匹配（连续 2 次）           │
│ 已试原语: Rebind ×2, InsertPrereq ×1（均失败）     │
├─ 关键证据 ─────────────────────────────────────────┤
│ 失败断言: expected 403, got 200                   │
│ 证据引用: obs#8821 (日志片段, 已验证)              │
│ 基准比对: 用例 TC-114 未通过                       │
├─ 置信度 ───────────────────────────────────────────┤
│ 采样一致率 0.33（3/9）  证据强度 中                 │
├─ 建议动作 ─────────────────────────────────────────┤
│ ① 改判为"需人工修复"并生成工单                     │
│ ② 追加指令：目标服务为 /api/v2，断言基于旧路径     │
│ ③ 按业务例外接受残余风险（仍非验证成功，硬安全拒绝不可覆盖）               │
└─────────────────────────────────────────────────────┘
```

### 8.6.3 裁决动作与约束

| 动作 | 效果 | 约束 |
|---|---|---|
| **正常验收** | 仅在全部冻结判据、硬门与所需验证通过后置 verified/succeeded | 人工不能覆盖失败记录 |
| **业务例外接受** | 标记 accepted_with_exception，保留未过判据与风险 | 独立授权/理由/期限；高风险双人复核；不计普通成功，不解除不可放宽安全拒绝 |
| **驳回** | Intent 转 `failed`，保留全部证据 | 需填写理由 |
| **改判** | 修改结论并重新走验证 | 修改后的产物重新过全部门禁，**不跳过** |
| **追加指令** | 作为新的上下文注入下轮执行 | 指令进数据位，不覆盖判据（§4.2.4 I5） |
| **标记不确定态已生效/未生效** | 处置外部副作用（§4.7.4） | 必须核对外部系统后操作；记录核对方式 |

**权限与责任**：
- 裁决人**不得是**该 run 的发起者或执行者（职责分离）
- 裁决动作写入 `human.adjudicated` 事件，含裁决人、理由、当时的证据快照哈希
- 高风险裁决（接受高严重度产物）需**双人复核**后才生效
- 裁决 SLA 超时 → 自动降级路径执行（§4.6.4）+ P2 告警

### 8.6.4 可用性要求

| 项 | 要求 |
|---|---|
| 打开延迟 | 视图首屏 < 1.5 s |
| 裁决提交 | < 300 ms 反馈，异步执行实际动作 |
| 移动端 | 只读视图可用（值班巡检场景） |
| 离线 | 可离线保存草稿；恢复网络后必须重新拉取证据/状态版本、校验权限与预期revision，再按幂等键提交，旧草稿不自动授权 |
| 审计 | 裁决全流程留痕，不可删除 |

## 9.2 Pack 清单

```yaml
  budget:

    cap: 20
    complexityFactor: 0.4
    costBase: 2.0                   # 金额预算基线（USD）
    costCap: 8.0                   # 金额硬上界，不可被任务覆盖
    byKind: {verify: 2, code: 6, review: 1}
  assets:                          # 资产图节点类型
    types: [repo, module, service, endpoint]
  coverage:
    surfaces:  [需求解析, 编码, 测试, 文档]
    boundaries: [单模块, 跨模块, 端到端]
  failureMap:                      # 失败 → 修复原语
    assert_fail:   {primitive: Rebind,      hint: 检查入参与期望值}
    compile_error: {primitive: InsertPrereq, hint: 检查依赖与构建配置}
    spec_drift:    {primitive: Escalate,     hint: 重新对齐规格}
    timeout:       {primitive: Rebind,      hint: 缩小任务粒度}
  compliance:                      # 合规扩展（内核强制，领域包不可降低）

```

`gates`声明内核门要求，装载器与内核底线取更严格有效值，`requireDualSign: false`不能覆盖内核强制双签；`ruleSetRef`只引用已经独立授权发布的规则版本，不允许Pack装载时将未审批内联表达式直接激活。示例中的digest与签名路径是占位，必须替换为真实验证通过的产物，不能直接用于生产加载。

以下是**独立规则发布流程**提交的RuleSet示例，不属于Pack可自改的运行数据；发布者不能同时作为该规则的自评执行者。发布器规范化spec产生摘要，再由受权审批者签名，规则注册表验证发行权限、签名、digest与版本后允许Pack引用。原始表达式来源可以由Pack作者提出，但执行主体不能自行批准。

```yaml
apiVersion: loom/v1
kind: RuleSet
metadata:
  name: software-dev-core
  version: "1"
spec:
  evaluator: restricted-cel-v1
  trustedInputSchemas: [execution-report/v1, report-evidence/v1]
  rules:
    - id: coverage_threshold
      appliesTo: [code]
      expr: "trusted_report.metrics.line_coverage >= 0.80"
    - id: no_unexplained_failures
      appliesTo: [code]
      expr: "trusted_report.test_summary.unexplained_failures == 0"
    - id: acceptance_traceable
      appliesTo: [report]
      expr: "artifact.claims.all(c, c.evidence_ref != null)"
```

表达式由固定版本求值器执行，变量来源与类型先校验。表达式无副作用不等于语义充分；受信指标不能由模型字段覆盖，证据引用还需归属/版本/内容检查。规则发布签名与产物验证签名是不同用途，不可相互替代。Pack装载成功不等于业务语义或效果已经证明。

## 9.3 扩展点清单

| 扩展点 | 领域包提供 | 内核职责 |
|---|---|---|
| 角色定义 | 角色 YAML | 注册、版本化、热加载、能力画像维护 |
| `kindRole` 路由表 | 映射表 | 确定性路由 + 候选集合 |
| 能力分类 | 能力 → kind | 与画像关联，供打分函数使用 |
| 门禁参数 | 阈值与字段清单 | **判定逻辑在内核，不可被包修改** |
| 领域门规则 | **声明式表达式**（无代码） | 内核表达式求值器 + 装载期静态分析 + 抽样复核（§4.5.1、§4.5.5） |
| 收敛阈值 | 阈值 | 公式（不可被包修改）+ 取值范围下限约束（§4.6.3） |
| 预算 | 基线、上界、复杂度因子 | 动态计算与熔断 + 成本闸门（§6.4.1） |
| 资产类型 | 节点类型 | 资产图投影、锚点管理 |
| 覆盖象限 | 面 × 边界定义 | 覆盖统计与盲区计算 |
| 失败映射 | 家族 → 原语 | 原语执行、成功率反哺 |
| 合规声明 | 授权要素、只读、脱敏、排除清单 | **强制执行，领域包不可降低** |
| 场景 | 场景 YAML | 场景加载、基准执行、指标统计（**自评，独立于内部基准**） |
| 工具 | 工具实现（薄） | 工具注册、幂等性标注、健康检查、出口管控 |
| 工作流模板 | 模板 YAML + 适用域签名 | 模板注册、发布、版本化、复用统计（§9.7） |
| 调度策略 | 权重集 / 路由表 / 预算参数 | 策略注册、导出、应用（§9.7） |

> **本表最重要的一行是"领域门规则"**。它把原本可以为任意代码的扩展点，收窄为"无副作用的表达式"。**扩展点收窄本身就是安全边界**（原则 P8）——比"要求 Pack 自觉"可靠得多。

## 9.4 Pack 装载与隔离

装载顺序：校验manifest/apiVersion→核验发布者与内容摘要→校验角色/路由/schema→规则语法与资源预算检查→核验被引用规则版本已授权发布→校验阈值/预算范围和内核底线→注册隔离工具服务端点与健康/幂等契约→注册self_evaluation场景与模板→写pack.loaded。失败无部分注册生效。

manifest只含数据，不import第三方Python模块；工具以隔离服务/镜像运行，经受控RPC调用，不持有内核数据结构或全库凭据。工具执行器发布与规则/评测发布权限分离。Pack命令仅走submit，所有归属、版本、范围、预算与门禁在可信服务校验。

热加载是注册新版本供新run使用；在途run固定角色、规则与模板快照。紧急撤销受影响工具/凭据可立即阻断在途动作；恢复需授权发布，不能由Agent改配置。卸载保留被在途run引用的内容寻址快照，不能删除回放材料。

持续复核统一按§4.5.5：被抽样产物先pending，严重错误P1立即冻结，一般偏差>2%触发P2并暂停相应规则自动放行；不再采用“仅告警仍放行”或“连续两次才暂停”的另一口径。独立评测适配器缺失时标明缺口并采用人工验证，不宣称通用内核具有领域等价判定能力。

## 9.5 版本与兼容

| 变更类型 | 兼容策略 |
|---|---|
| Pack 补丁版本 | 直接升级；在途运行绑定旧版本（FR-010） |
| Pack 次版本 | 需通过内核一致性测试；灰度加载 |
| Pack 主版本 | 需迁移脚本；内核侧提供弃用期（默认 2 个发布周期） |
| 内核版本 | 事件hash/schema版本固定；解析兼容通过版本化upcaster处理，不能改写历史认证字段；删除需弃用期 |

**内核对 Pack 的兼容承诺**：内核的 `apiVersion: loom/v1` 在该主版本生命周期内保证向后兼容。

### 9.6.3 `security-audit`（参考实现 B）

| 项 | 内容 |
|---|---|
| **目标场景** | 在**明确授权**的前提下，对指定范围内的资产做授权安全评估，产出含证据的评估报告 |
| **角色** | 范围分析师 / 评估执行者 / 证据整理者 / 复核者 / 报告编写者 / 合规审查者 |
| **kind 覆盖** | `scope` `assess` `collect` `verify` `report` `compliance` |
| **工作流** | `authorized-assessment`（含合规门前置）、`evidence-review`、`report-only`（只读复核） |
| **合规声明** | 授权门四要素（目标 / 授权依据 / 有效期 / 排除清单）缺一则 run 无法创建；作用域限定在授权范围内；**默认只读**，写操作需显式开启并逐次审批；排除清单为授权发布且run冻结的版本，内核硬拒绝不可放宽；报告交付前强制脱敏 |
| **领域门规则** | 范围内资产覆盖率 ≥ 声明值；每条结论必须有可复现证据；高严重度结论必须有独立第二签；报告中不含排除清单内目标的任何信息 |
| **收敛阈值** | `minNewPass: 2` / `minNewAssets: 1` / `maxIdleRounds: 2` |
| **场景构成** | 18 个，全部在**仿真靶场**内运行（不指向任何真实外部目标），含正常流程、越界尝试、授权缺失、排除清单命中四类 |
| **预期指标** | 越界访问被拦截率 100%；授权缺失时 run 创建被拒率 100%；报告脱敏漏检率 0 |

> **安全域的口径纪律**：该领域包的对外表述统一为"**授权安全评估**"，默认仿真与只读，真实写操作需显式开关与逐次审批，作用域与排除清单由内核强制。**这不是产品策略，是合规要求。**

### 9.6.4 两个参考实现的作用

1. **验证内核的领域无关性**：同一内核服务差异极大的两个领域（软件研发 vs 安全评估），不改动任何内核代码
2. **提供接入样板**：新领域开发者可参照其 manifest、角色定义、规则表达式与场景结构

**不作为任意领域通用性的证明**：装载机制和一致性测试只证明约定扩展契约，两个参考Pack在实际交付后提供有限领域的运行证据；未实现前保持计划状态。

> **重要边界**：参考实现自带的场景与指标属于**领域自评**（§10.7），其与独立判据的差异由授权评测适配器复核持续度量。**参考实现的效果数据不能单独作为平台有效性的证据**，须与平台一致性及独立held-out效果分表呈现，不能据自评外推业务收益。

## 9.7 工作流模板与调度策略资产化

平台的长期价值不在于"一次任务跑通"，而在于**跑通一次之后，下次能少花力气**。本节定义沉淀机制。

### 9.7.1 模板

模板 = **工作流定义 + 角色集合 + 门禁参数 + 预算 + 失败映射 + 适用域签名**。

```yaml
apiVersion: loom/v1
kind: WorkflowTemplate
metadata:
  name: feature-delivery-standard
  version: 3
  pack: software-dev
  description: 标准特性交付流程
spec:
  workflow: ./workflows/feature-delivery.yaml
  roles: [analyst, architect, tester, developer, reviewer, fixer, validator]
  gates: {D1: ..., V: ..., R: ...}
  budget: {base: 14, cap: 20, costBase: 2.0, costCap: 8.0}
  failureMap: ./failure-map.yaml
  applicability:            # 适用域签名
    kinds: [spec, design, case, code, review, fix, verify]
    inputSchema: ./input.schema.json
    outputSchema: ./output.schema.json
    successCriteria: ./success.yaml     # 期望的成功判据形态
    constraints:
      - requires_repo: true
      - max_files_touched: 50
```

**适用域签名的作用**：让复用方**在采用前就能判断能不能用**。内核在模板实例化时用签名做匹配检查：不匹配的模板被拒绝并说明差在哪（缺少 kind 覆盖 / 输入 schema 不兼容 / 超出约束），而不是运行到一半才失败。

**模板的生命周期**：

| 操作 | 说明 |
|---|---|
| 发布 | `template.published` 事件；模板带版本与来源 Pack |
| 实例化 | 派生运行绑定模板版本；模板后续变更不影响在途运行 |
| 继承与覆盖 | 实例可覆盖预算与权重，但**不可覆盖门禁谓词与合规声明** |
| 统计 | 模板被实例化次数、成功率、平均成本、平均轮次（用于淘汰劣质模板） |

### 9.7.2 调度策略

调度策略是**与模板正交**的可复用单元：一个模板可以配多个策略，一个策略可跨模板使用。

| 组成 | 内容 |
|---|---|
| 权重集 | §4.4.2 Agent打分的w1/w2/w3/w5/w6/w7；任务优先级在队列策略 |
| 路由偏好 | `kindRole` 的候选顺序调整 |
| 预算偏好 | 各类 kind 的轮次与成本系数 |
| 收敛偏好 | 收敛阈值（受内核下限约束） |
| 模型偏好 | 各类 kind 的模型档位偏好与 tier 要求 |

**策略导出格式**为独立的 YAML，可脱离 Pack 分发。**策略同样带适用域签名**（适用哪些 kind、什么任务规模），避免"把大任务的策略套到小任务上"这类错配。

### 9.7.3 复用度量

| 指标 | 定义 | 目标 |
|---|---|---|
| 模板复用率 | 新建工作流中来自模板库的比例 | ≥ 50%（NFR-017） |
| 策略命中率 | 实例化时成功套用既有策略的比例 | 统计项 |
| 模板劣汰 | 成功率显著低于同族中位数的模板被标记 | 自动标记 + 人工复核 |
| 跨域可移植性 | 同一模板在 2 个以上领域包中可用的数量 | 衡量模板抽象层次是否过高 |

> **跨域可移植性是一个刻意设置的指标**：模板可以有价值地在同一领域复用；跨域可移植性是附加指标，不作为域内模板无效的依据。**这个指标能防止模板库退化成各领域工作流的堆砌。**

## 10.2 必测不变量与审查回归

| 不变量 | 必测行为 |
|---|---|
| P1 业务历史与账本一致 | 同一截止点重建投影/控制账本等值；所有授权状态变更有同事务事件 |
| P2 确定性门禁 | Gate-P/V/D/R不调用LLM决定硬门真值；模型建议不能直接verified |

| P6 不可自改 | 执行主体不能改Anchor/规则发布；紧急撤销只能即时收紧 |
| P7 统计口径 | 网络不计能力错误，但完整展示完成率、延迟、成本和失败分布 |

| P9 副作用恢复 | 旧Worker、响应丢失、记录丢失窗口不触发不可安全重做；未知挂起 |
| P10 调度权威 | 双副本/旧leader/投影滞后60s下实际容量和claim仍满足原子约束 |
| 严格双签 R01 | pending/disputed/blocked/single均不能满足强制双签；内容/证据/规则变化使签名失效 |
| 完整审计 R04/R05 | type/actor/tenant/run/seq等逐字段篡改、空幂等键、重排、截断检测；长run检查点恢复 |
| 事务outbox R06 | 提交后发布前退出可续投；发布后未标记重投仅一次生效；并发同键语义一致 |
| 容量/预算 R07–R09 | 并发争最后余量仅合法预占成功；重复释放/结算无效；未知计费保留预留 |
| 回退 R11 | 图版本CAS、无环、下游stale/签名作废、在途撤销、补偿失败可见 |
| 租户 R12 | 真实业务角色、交叉ID、对象URL、claim与审计范围越权均拒绝 |
| 停滞 R13 | 验收失败+空闲进入stalled/人工，不成功；无意义字节变更不能无限空转 |
| 上下文 R20 | 必留预算溢出显式拒绝/拆分；试用经验有独立入口；held-out不进入记忆 |
| 优先级 R24 | 更新优先级改变任务先后；aging防饥饿；同任务候选Agent不受常量优先级项干扰 |

静态检查是补充，不能用“未import投影”或“无领域关键词”替代以上动态正确性测试。S1先交付其已实现范围用例，S2/S4再分别验收分布式、真实生产安全与SLO；未实现项明确标pending，不能用跳过测试记为通过。

每条 FR 至少一个可执行用例，映射进 §2.4 追踪矩阵。**测试用例以 FR 编号命名**，保证追踪完整性可机械校验。

## 10.4 工具与 MCP 测试

- 每个 MCP Server 在**无 LLM 环境下**可独立测试
- 协议符合性：请求头、版本协商、错误语义
- 安全：命令执行器白名单、版本 pin 校验、出网限制

## 10.5 领域包一致性测试

同一套参数化测试套件对**所有已加载 Pack** 执行：

1. 角色定义 schema 合法
2. `kindRole` 覆盖该 Pack 声明的全部 kind
3. 门禁参数完整（缺项 → 失败）
4. 领域门规则通过静态分析（无禁用函数、引用完整、复杂度在限内、无自由文本正则）
5. **可折叠的恒真/恒假规则被拒绝**（如 `expr: "true"`、`expr: "1 == 1"`）；不声称识别任意语义弱化规则
6. 收敛阈值合法且在内核允许范围内
7. 失败映射覆盖全部失败家族
8. 合规声明完整（授权要素/排除清单/脱敏规则存在）
9. 加载/卸载不改动内核代码路径（静态 diff 断言）
10. 该 Pack 的场景集可跑通且产出合法产物
11. **该Pack具备已授权独立评测适配器或明确的人工复核路径**；不假设通用内核与领域语义等价
12. 该 Pack 的模板的适用域签名可被内核匹配与拒绝逻辑处理

## 10.6 性能与可靠性验证

- 每次发布跑完整压测矩阵，比对基线（基线数据存库，回归 > 10% 告警）
- **全图注入基线必须实现并参与压测**（NFR-012 的度量对象，§6.1）
- 每周混沌演练：Worker 崩溃、模型超时、队列分区、DB 主备切换、**投影滞后 60 s**
- **故障注入必须包含"外部写操作中途崩溃"场景**，验收标准含"重复外部写 = 0"（NFR-022）
- 每月灾备恢复演练 + 投影等值性校验 + 副作用判定校验（§5.5）

## 10.7 三套评测、ground truth 与对照实验

### 10.7.1 物理和发布权限隔离

| 套件 | 持有者与用途 | 能支持的结论 |
|---|---|---|
| canonical平台一致性 | 平台测试角色；状态机、调度、claim、预算、门禁、回放、幂等与副作用桩 | 机制是否满足约定；不能单独证明业务质量或经济收益 |
| independent_effectiveness独立效果 | 独立评测角色/第三方；冻结held-out任务、受信工具结果及业务验收 | 分层业务成功率、总成本、人工工时；用于效果声明 |
| self_evaluation领域自评 | Pack开发者；可用于调参的域内场景 | 开发反馈；不作为独立效果证据 |

三套独立存储、访问权限和报表，不合并平均。独立领域评测是独立发布的适配器/数据资产，不将领域语义硬编码进内核；新领域可以零内核修改接入，但必须提供独立判据或标明无法自动判真。

### 10.7.2 ground truth 与防泄漏

真值来自已知正确提交/官方答案、双人独立人工标注或可执行构造性断言，记录来源、版本、范围和适用条件。标注者不参与同场景调参；两人分歧经第三方仲裁并记录一致性，κ<0.6的主观场景先返工不入冻结集。测试执行报告绑定代码、镜像、测试集与完整结果摘要。

held-out由独立评测者持有，不进入提示词、调参、经验条目或训练回流；泄漏样本从独立集移除并换版。模型、工具、提示词/上下文、规则与基准版本均记录。事件回放可重建已提交历史；重新调用模型只做统计复现实验，不承诺种子相同即同轨迹。

### 10.7.3 统一对照与指标

业务效果对照B1人工使用通用Agent、B2单Agent、B3固定串行流程、Loom；可附加广播/无修复/无动态调度等消融。任务按复杂度分层，统一模型资源/可用工具/墙钟限额和费用口径，重复采样报告置信区间。

主指标为全部尝试的模型、工具、运行计算、验证、失败与人工成本除以独立验收成功数；成功为0时报告不可定义/无穷及原始总成本，不隐藏失败。另报端到端完成率、条件正确率、首次通过、返工、墙钟时间和例外接受率。网络故障不归为模型能力错误，但仍在端到端分母、耗时和费用中展示。

### 10.7.4 报告与复现

平台一致性、独立效果和自评各自分表，标明版本、任务规模、样本、置信区间、失败/超时/拒绝及人工介入。对外业务效果声明只引用独立效果集；不能以平台状态机测试或Pack自评代替。负收益也报告并调整适用任务，不能预设Loom必胜。

## 10.8 鲁棒性测试

**鲁棒性 ≠ 可靠性**。可靠性是"正常条件下不出错"，鲁棒性是"异常条件下仍能工作"。本节定义四类注入与保持率指标（NFR-016、FR-062）。

| 注入类 | 注入内容 | 期望行为 | 失败则说明 |
|---|---|---|---|
| **A 需求歧义** | 模糊需求、缺失关键约束、自相矛盾的需求 | 系统**触发澄清或标记低置信**，而非硬跑并给出确定性结论 | 缺少不确定性表达机制 |
| **B 工具故障** | 工具超时、返回脏数据、返回幻觉字段、返回格式错误 | 归入正确失败家族；触发差异化处置；不污染图 | 失败分类不精确（P7 风险） |
| **C 模型降级** | 主模型不可用、返回质量下降、限流 | 执行通道降档；**验证通道不降档**（熔断转人工） | 验证降级边界未落实（§5.3.1） |
| **D 极端规模** | 1000 意图 / 5000 任务的图；单 run 500 个产物 | 裁剪生效、收敛正常、无栈溢出、无 OOM、调度延迟不劣化 | 裁剪与调度不 scaling |

### 10.8.1 保持率指标

```
鲁棒性保持率 = 注入条件下的任务成功率 / 无注入时的任务成功率
```

| 注入类 | 目标保持率 |
|---|---|
| A 需求歧义 | ≥ 85%（此类指标单独定义为正确识别歧义并请求澄清，不与正常业务完成率直接作比） |
| B 工具故障 | ≥ 90% |
| C 模型降级 | ≥ 85%（执行通道降档后） |
| D 极端规模 | ≥85%，且调度延迟劣化≤20%；基线与注入组使用相同资源预算 |

### 10.8.2 每次注入必须记录

- 注入点、注入时刻、注入参数
- 系统的实际处置路径（哪个失败家族、哪个原语、是否升级人工）
- 最终结果与消耗成本
- **是否有不该发生的副作用**（图污染、重复外部写、越过门禁）

最后一项是重点：鲁棒性测试不只看"最终成功没有"，还要看**过程中有没有留下脏状态**。

# 11. 部署与交付

## 11.1 环境

| 环境 | 用途 | 规模 | 数据 |
|---|---|---|---|
| local | 开发 | docker compose 单机 | 合成数据 |
| ci | 集成/压测 | 共享集群 | 合成数据 |
| staging | 发布前验证 | 生产 1/3 | 脱敏生产样本 |
| prod | 生产 | 按 §6.2 | 真实 |

**禁止**在非授权环境运行任何指向外部目标的领域场景。

## 11.2 发布策略

| 变更类型 | 流程 |
|---|---|
| 内核变更 | 契约测试 + 集成 + 压测 → staging 灰度 1 个副本 → 观察 30 min → 全量 |
| 领域包变更 | 一致性测试 → staging → 独立灰度 → 可单独回滚 |
| 数据模型变更 | 向后兼容（新增字段可选）；破坏性变更走两阶段（双写 → 迁移 → 清理） |
| 事件 schema 变更 | 事件体新增字段向后兼容；删除需弃用期且投影端同步 |

**回滚**：内核与 Pack 独立回滚；在途运行绑定其启动时的版本，回滚不影响其在途执行。

## 11.3 CI/CD

```
提交 → 静态检查（类型 / lint / 领域中立性 / **调度器不 import 投影客户端**）
     → 单元测试（覆盖率门禁）
     → 契约测试
     → 领域包一致性测试（所有 Pack，含领域门规则静态分析）
     → 集成测试（testcontainers）
     → 基准套件（canonical + independent_effectiveness + self_evaluation，分表产出）
     → 鲁棒性套件（四类注入）
     → 构建镜像 + 生成 SBOM + 签名
     → staging 部署 → 端到端 + 压测冒烟 + 全图注入基线比对
     → 生产灰度 → 全量
```

**静态检查中的架构断言**（失败即阻断合并）：

| 断言 | 对应原则 |
|---|---|
| 内核不依赖领域专用判定实现，关键词检查仅辅助 | NFR-011 |
| 领域包引入的内核代码变更 = 0 行 | NFR-013 |
| 调度器模块不 import 投影客户端 | P10 |
| 门禁判定函数不调用 LLM | P2 |
| 执行主体不能写规则发布与在途快照，授权策略发布与紧急收紧有版本及审计 | P6 / CN-005 |

**产物供应链**：镜像固定 digest；生成 SBOM；镜像签名；依赖锁定版本并定期安全扫描。

## 11.4 配置、规则与运行快照

| 类型 | 存储/变更主体 | 在途语义 |
|---|---|---|
| 基础设施与内核底线 | 代码/部署清单；受审发布 | 不由执行主体修改；兼容发布 |
| 验收Anchor | 内容寻址只追加对象、digest | 当前Goal不变，修改创建新Goal/版本 |
| 领域规则/阈值/清单、角色/路由、预算/权重 | 授权发布者签名的Pack/策略版本 | 新run采用；旧run固定快照，不能因热加载隐式放宽 |
| 紧急拒绝、凭据撤销、容量收紧 | 独立安全/运维通道，版本+原因+审计 | 可立即收紧在途动作；恢复须授权，不能由Agent自行解除 |
| 敏感配置 | Secret管理 | 轮转、最小权限、事件不含明文 |

采样率和限流变化需明确是否只作用于新run或立即收紧。所有历史规则、模型价格、工具镜像和事件schema版本作为可回放材料保留；回滚二进制不能删除仍被在途run引用的版本。

## 12.4 决策档案

下列档案与§9.1唯一索引一致。每项“待实测”不能被文档修订替代；实现偏离须更新此处及追踪表。

### ADR-001 · 事件历史与同事务控制账本

- 背景：业务投影与安全授权状态不能分别漂移。
- 决策：已提交业务历史以事件为准，claim/容量/预算/调用账本与事件同事务更新并可恢复。
- 后果：需要明确事务边界、幂等回执和重建对账；不宣称所有授权都只读异步日志。
- 复议：跨分片事务成本不可接受时评估分区边界，不能降低安全不变量。

### ADR-002 · Pack与工具的权限隔离

- 背景：注册表约定不能约束同进程第三方代码。
- 决策：manifest为数据，可执行工具在隔离服务/镜像；Pack无内核写和受信评测写权限。
- 后果：增加RPC和供应链管理，避免工具import进入可信控制面。
- 复议：出现经证明需要新扩展点的需求时评审，不开放任意内核写。

### ADR-003 · 规则、证据与独立评测分层

- 背景：无副作用语法不能证明语义或自报指标真实。
- 决策：内核结构门确定性，领域规则授权版本化，指标由受信执行器产生，语义效果由独立适配器/held-out判断。
- 后果：新领域须有独立判据或明确人工路径；内核不硬编码领域真值。
- 复议：规则语言表达力不足时增加受审能力，不能把Pack自评直接视为独立评测。

### ADR-004 · 完整事件分链与独立检查点

- 背景：仅payload哈希不能保护事件含义；异步修改原事件破坏不可变模型。
- 决策：按run同步事务摘要完整信封，签名/锚定在独立检查点异步追加。
- 后果：链内有序、跨run并行；签名前尾部保护边界显式报告。
- 复议：实测摘要成为瓶颈后评审批量或其他认证结构，先保留完整性语义。

### ADR-005 · 单写者与数据库原子预占

- 背景：多副本内存计数30秒对账无法防止当时超配。
- 决策：调度分片单写者；claim/共享池容量/预算以持久化CAS或行锁授权。
- 后果：数据库参与派发热路径，必须测锁竞争；内存只计算候选。
- 复议：规模要求分片时先明确全局资源归属，不退回未协调计数。

### ADR-006 · 外部发起权与未知窗口冻结

- 背景：提交幂等键和旧Worker提交拒绝不能阻止外部重复效果。
- 决策：稳定call_id、唯一可信出口、发起账本先持久化；未知结果/可能丢日志窗口冻结核对。
- 后果：不承诺任意外部exactly-once，人工负担需测量；可安全重试依赖工具真实合同。
- 复议：全部工具具备可靠去重和查询后，可调整恢复策略而不扩大未证明保证。

### ADR-007 · DSL与模板优先

- 背景：需要可diff、可版本化和可审阅的工作流。
- 决策：DSL为核心，视图可选；模板与调度策略正交资产，域内复用同样有效。
- 后果：工程用户优先，不以跨域复用数量否定有用模板。
- 复议：非工程用户需求显著时再建设画布，保持DSL语义一致。

### ADR-008 · 本期不实现A2A网关

- 背景：当前目标是单控制面强协作，暂无明确跨组织弱协作需求。
- 决策：不实现A2A网关；工具互操作由独立MCP适配层提供。
- 后果：不直接接第三方A2A Agent；固定协议版本与兼容测试。
- 复议：出现具体跨组织协作需求后评估信任、授权与状态同步成本。

### ADR-009 · PostgreSQL生产主存储与SQLite开发适配器

- 背景：事件、关系约束与原子预占需可靠事务；开发环境可能无Docker。
- 决策：生产以PostgreSQL为主，不引入独立图数据库；本地SQLite只验证契约，生产特性另测。
- 后果：需共享适配器一致性套件；SQLite通过不表示RLS/HA/SLO通过。
- 复议：复杂多跳分析可用只读适配器；不能新增业务真相源。

### ADR-010 · 事务outbox与至少一次投递

- 背景：数据库提交后直接bus.publish存在进程崩溃丢消息窗口。
- 决策：事件、回执、outbox同事务；持久发布器等确认；消费者持久去重。
- 后果：允许重复消息但只生效一次；队列不可用时账本积压与背压可见。
- 复议：改CDC等方案时必须证明相同提交/投递恢复语义。
