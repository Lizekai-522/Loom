# monsoon-harness 完整施工方案：五种形态的取舍、跨机契约与批次判据

本文档回答一个问题：怎样把 Realtime-Venus（RV）二次开发、以 rakazo 为基座，做出 monsoon-harness（ms）——一个既能单独作为全天候 agent 运行、又能与 Loom 组合并把任务外包给中心 Loom 的分布式前端。

文档分两部分。前一部分是五项待拍板问题的调研与决策记录，每项给出证据、结论、理由与推翻条件。后一部分是从头到尾的完整施工方案：目标形态、组件边界、数据与身份模型、跨机契约、能力插件层、批次划分、验收判据与风险处置。

阅读顺序建议：先读第一章的五项决策，再读第二至第五章建立拓扑与模型认知，第六至第九章是四个专题的展开，第十章之后是施工与验收部分。附录给出证据索引。

## 第一章 决策记录

本章的每一节按同一结构展开：问题是什么、调研看到了什么、结论是什么、为什么这样选、什么条件下应当推翻它重做。决策一旦写入本章，后续章节按此执行，不重复论证。

### 1.1 执行位置的默认策略

**问题**：ms 有本机执行域与远端执行域两处可以真正跑任务。派活时默认走哪一处，要不要由系统按负载与健康状况自动选择。

**调研**：rakazo 侧的计算机模型里有三类信号，但只有一类够得上健康信号。占用与栅栏信号是完备的：`Computer` 上有 `state`、`runningSince`、`executionRunId`、`executionBotId`、`executionLeaseExpiresAt`、`executionFence`、`controlHolder`、`controlLeaseExpiresAt`【8】。这些字段回答的是“谁占着这台机器、占到什么时候、栅栏号是多少”，不回答“这台机器还有余力吗”。

容量信号是缺席的。`Computer` 与 `ComputerRun` 两个模型里没有队列深度、CPU 占用与内存水位【8】。并发占用信号是有的：执行租约是一张独立表，按计算机与 bot 唯一、带到期时间，按计算机计数可得当前占用数【8】。但占用数不是容量——它回答“现在有几个在跑”，不回答“还能不能再塞一个”，后者要内存与 CPU 的水位。

官方文档对容量的描述是定性的：一台计算机可以承载上百个 bot 配置，同时活跃桌面数由内存、CPU、进程容量与本地调试端口数决定（`docs/computer-runtime.md:23`）【2】。

这里要补一处订正：容量上限并非完全不可观测。文档给了一个可配置的显式封顶——桌面栈的并发上限可以设成一个正数，超过上限的请求直接被拒并返回明确错误，默认不设（`docs/computer-runtime.md:23`）【2】。也就是说“可配置的准入上限”这件事 rakazo 已经做了，缺的是“按实际容量自动定上限”所需的水位数据：内存与 CPU 的占用没有暴露出来，默认不设上限时的真实容量因此无法观测。按机器健康与负载自动路由仍然缺少一手依据，但理由要收窄到这一条，而不是笼统地说容量不可观测。

健康信号只有一条，且指向的对象不是用户机器：`docs/computer-runtime.md:143-145` 写明“停止心跳十分钟的 worker 会被标记为中断”，这说的是服务端 worker 进程，不是用户侧机器【2】。另外 `providerRef` 在文档里被明确定义为“加速路径，不是持久数据”，机器被替换后同一个引用会指向新机器【2】。按机器身份做路由，前提是机器身份稳定，这个前提当前不成立。

rakazo 自身也不做自动路由。它的计算机归属是显式作用域：`Computer.scope` 默认取 `team`，取值对应“工作区共享的团队计算机”与“单个 bot 独占的私有计算机”，由 `scopeKey` 唯一绑定到具体计算机上（`docs/computer-runtime.md:17`）【2】。`Bot` 模型上有 `computerId` 与 `computerSwitching` 两个字段，把执行位置的选择落在 bot 身上，而不是落在每次任务派发上【8】。

**结论**：采纳双执行域并存、由 Space 策略显式指定、不做自动路由。补充两点用户未提及的约束。

第一，执行域的绑定粒度是 bot 级，不是单任务级。`Bot.computerId` 与 `Bot.computerSwitching` 的存在说明 rakazo 把“这个 bot 在哪台机器上跑”当作 bot 的一种属性【8】。因此 ms 的“Space 策略显式指定”要落在 Space 到 bot 的默认配置层：Space 声明一个默认执行域，新建的 bot 继承它，管理员可以逐个 bot 覆盖。不在每次派发时现选执行域。

第二，Space 上目前没有承载执行域策略的字段。`Space` 模型里有审批策略（`ActionApprovalRule`、`ActionAutoReviewPreference`）、能力安装（`CapabilityInstall`）、密钥与凭证等结构，但没有执行域偏好【8】。这一项需要新增字段或复用既有结构，第 6.2 节给出具体落法。

**理由**：自动路由需要可信的机器健康与负载信号，这两项目前没有一手依据。在没有可观测容量的前提下做自动路由，选错的代价远高于不选——路由结果无法复盘，无法解释“为什么这次跑在那台机器上”，而排查一个显式配置只需要看一个字段。

**推翻条件**：当且仅当以下条件同时成立，才重启自动路由的设计。计算机侧要暴露可采集的容量信号，至少包含内存水位与 CPU 水位，并写入 `ComputerRun`——活跃任务数已经有了，但那是占用数不是容量；机器身份要稳定到可以长期引用，`providerRef` 需要变成持久标识或引入稳定的实例标识；执行位置需要从 bot 级下沉到任务级，且下沉后的切换成本可接受。在此之前，自动路由保持在方案范围之外。

### 1.2 ms 的用户体系范围

**问题**：ms 沿用 rakazo 的 Better Auth、Organization、Space 三层模型，还是先做单用户精简版。

**调研**：rakazo 的身份链路已经成型，且成型的方式对分布式形态有利。`packages/db/src/scope.ts` 里的 `requireMembership` 按用户查找成员关系，未指定空间时取默认空间，未找到成员关系则抛出 `IsolationError("No personal space")`【12】。返回的 `Actor` 含 `userId`、`spaceId`、`email` 与 `isDeploymentOwner`【12】。

隔离判定由 `scoped` 承担：记录的 `spaceId` 与主体不符即抛 `IsolationError`，记录带 `userId` 时还要与主体的 `userId` 相符【12】。异常消息固定为 `Resource not found`，不区分“不存在”与“无权访问”，这条语义在多租户场景下值得保留。

计算机的隔离维度与之对齐：`Computer` 同时带 `spaceId` 与 `userId`【8】。工作区维度决定可见性，用户维度决定独占性。

部署侧的用户管理有一处需要记住的事实：`DeploymentSettings` 有 `signupsEnabled`、`signupAllowlist`、`signupPolicyInitialized` 三个字段控制自助注册【8】，而 `Actor.isDeploymentOwner` 在代码里硬编码为 `false`【12】，部署所有者这一概念没有对应的角色表。

**结论**：采纳沿用 Better Auth 与 Organization、Space，不做单用户精简版。补充三点用户未提及的内容。

第一，“不做精简版”不等于“必须开自助注册”。最省事的做法是保留完整模型、只收紧部署策略：把 `signupsEnabled` 置否，用 `signupAllowlist` 指定允许进入的用户，其余模型原样保留【8】。这样第一天就有真实的用户与审计主体，而没有欠下“将来要补多用户”的债。删模型省下的是几百行代码，补回来时动的是审计、隔离与凭证三条链路。

第二，ms 本机不持有用户口令。本机注册到服务端走设备令牌，与 rakazo 现有的用户设备客户端同一条路：`packages/adapters/src/user-device-client.ts` 描述的是“本机主动向外建立 WebSocket、服务器永不反向连接、握手携带设备令牌”【10】。这与 ms 的拓扑方向天然一致——ms 在用户机器上，中心在服务器上，主动出网的一方必须是本机。

第三，审计主体沿用 rakazo 的既有落点：`Run.userId` 记录发起人，`Event` 挂在 `spaceId` 下，`SpaceMember.role` 区分成员角色【8】。ms 侧不需要另造审计主体模型。

**理由**：多机并发提交在第一天就需要工作区归属与审计主体这两样东西。单用户版本省下的工作量会在第一个真实并发场景里如数还回来，且还回来的位置比省下的位置更贵——审计链与隔离判定都是在数据写入路径上的，改一次要动全部写入点。

**推翻条件**：若部署形态确定为“单人自用、单机单 Space、无共享部署”，且团队明确不做第二用户，那么可以保留 Organization 与 Space 两层模型、把 `SpaceMember` 降为单成员记录，但**不建议删掉 `Space` 层**——`scoped` 的隔离判定、幂等键的租户边界、凭证的空间归属都挂在这一层，删掉之后还要加回来。

> **〔2026-11-01 变更，见修订前言拍板五〕** 本节结论按其自身推翻条件部分触发：Phase 1 采用 Loom 式具名主体 + 设备令牌（本机单用户），多用户协作由中心租户承担；Space/成员概念保留并映射 Loom tenant，Better Auth、Organization、通行密钥不进 Phase 1。`scoped` 隔离语义与"不泄露存在性"错误消息照常吸收。

### 1.3 fork 的粒度

**问题**：fork 整个 rakazo 仓库并在其上引入形态开关，还是挑选部分包重写。

**调研**：先看包之间的依赖关系。`packages/core` 只依赖 `packages/contracts`；`packages/db` 依赖 `contracts`、`core`、`adapter-kit`、`logging`；`packages/adapters` 依赖 `adapter-kit`、`contracts`、`core`、`db`、`logging`；`apps/api` 依赖上述全部再加 `auth` 与 `memory`；`apps/web` 只依赖 `contracts`、`core`、`logging` 与三个 UI 包，不依赖 `db`【11】【15】【16】。

这是一个分层有向无环图，没有环——核心层只依赖契约层，数据层依赖契约层、核心层、适配器契约层与日志，适配层再往上【43】【44】。这意味着“共用底层、重写上层”在依赖层面没有障碍，`contracts` 与 `core` 可以被 ms 与中心两侧同时使用。

再看 rakazo 内部已有的分布式资产。`packages/adapters` 的导出面里同时存在两类东西：一类是云端 provider 适配（Docker、E2B、Daytona、Boat、CreateOS），另一类是用户设备客户端与宿主机服务（`./user-device-client`、`./host-computer-server`）【11】。用户设备客户端的连接方向恰好与 ms 的拓扑相同：本机主动连出，服务器不反向连，握手带设备令牌，每次请求前过授权回调，收到吊销即停机，断线不重试并用全抖动重连【10】。这是拓扑倒置这件事上最值得直接继承的一块资产。

再看不可继承的部分。`docs/computer-runtime.md:13` 写明“Pi 运行在 rakazo 的 API/worker 进程里，并不安装到 E2B 里执行”【2】。这正是需要拆开的地方：ms 要求 agent 运行时落在用户机器上，中央只留编排与审计。

**结论**：采纳整仓 fork 并在 fork 上引入“中心形态”与“本机形态”两个开关。补充两点用户未提及的内容。

第一，整仓 fork 不等于整仓都要改。依赖图给出的分层可以直接当施工顺序：`contracts`、`core` 与 `adapter-kit` 三层两侧共用，`db`、`auth`、`adapters` 是中心侧的重点改造对象，`web` 与 UI 包是 ms 客户端侧的重点改造对象。前三层几乎不动。

其中 `adapter-kit` 这一层比我原先估计的重要：它是 provider 契约层的所在地，`db` 与 `adapters` 都依赖它【11】【12】。ms 对能力的任何扩展都应落在这个包里，而不是新开一个包。

第二，fork 的第一个动作是钉住来源。`packages/adapters/package.json` 里 Pi 的依赖锁在 `@earendil-works/pi-agent-core` 1.3.0【11】，`apps/web/package.json` 与 `apps/api/package.json` 的依赖版本也各不相同【15】【16】，这些版本号是复现的前提。当前主干 commit SHA 尚未取到（沙箱到 github.com 的 TLS 握手失败、GitHub API 触发速率限制），批次零的第一件事就是取回 SHA 与 tag，写进锁文件，方案正文不引用未核实的版本号。

**理由**：租户、行级安全、契约与审计事件是重写成本最高的部分，而这四项恰好是分布式形态的必需品。隔离判定函数 `scoped` 与 `requireMembership` 已经写好且语义正确【12】，租户边界、凭证归属与审计链都挂在这套模型上。重写它们等于把已经正确的东西再写错一次。

**推翻条件**：若 fork 后发现 `packages/adapters` 的云端 provider 适配与设备客户端之间存在大量互相引用、无法切分，则退化为“fork 整仓但整仓只保留中心侧能力，本机侧另起包”，此时 fork 的收益下降但 `contracts`、`core`、`db`、`auth` 四层仍值得保留。

> **〔2026-11-01 变更，见修订前言拍板四〕** 本节结论被取代：不整仓 fork，改走**概念吸收 + Python 重写**（路线 A）。事实依据：rakazo 实测 76 万行 TS/TSX（非测试 35.3 万），fork 等于继承全量构建与上游合并；与 ms 直接相关的核心层非测试代码约 4.6 万行，其概念面（租户模型、adapter-kit 契约形状、连接治理、宿主沙箱、审批规则）已全部登记进吸收清单。rakazo 快照钉 `d13ef7a`，Apache-2.0 许可登记进 THIRD-PARTY-NOTICES。rakazo 自身的结构弱点（上帝工厂、平面单体、进程耦合等 20 项）已列为 ms 设计约束。

### 1.4 RV 的二开深度

**问题**：把 RV 的委托协议门与工作状态机抽成 ms 的能力插件、把 RV 执行器接到插件后端，还是 fork RV 的进程内注入层。

**调研**：先核对 RV 的边界清单。`harness/README.md` 的“Frontend and backend integration”表列出五处扩展点：对话模型（`VenusOmniServingPort`，定义在 `harness/bridge/serving.py:464`）、任务执行（`GeneralAgentPort`，`harness/agents/contracts.py:80`）、路由与润色（`PlannerBackend`，`harness/llm/backends.py:12`，以及委托契约 `DelegateBackend`，`harness/core/backend.py:16`）、客户端播放（`PlaybackPort`，`harness/bridge/host.py:95`）、领域能力（`AgentSkill` 与 `SkillRegistry`）【31】。

这五处确实都是进程内的 Python Protocol，扩展方式是实现协议再由调用方装配。装配入口只有两个函数：`harness/factory.py:8` 的 `build_harness(setup)` 与 `harness/factory.py:21` 的 `load_harness(path)`【31】。setup 由调用方传入，所以“构造注入而非插件发现”这个判断在装配层面成立。

但“抽成插件”的工作量被高估了一部分，原因是 RV 侧已经具备插件语义的基本形状：注册、参数契约与校验。`harness/skills.py:19` 定义 `AgentSkill` 协议；`harness/skills.py:82` 的 `SkillRegistry` 提供 `register`、`for_capability`、`require`、`manifests` 四个入口【31】。`harness/skills.py:120` 的 `routing_contracts` 逐个能力输出 `name`、`description` 与 `arguments_schema`，其中参数模式缺省时兜底为 `{"type":"object","properties":{},"additionalProperties":False}`【31】。`harness/skills.py:34` 的 `validate_routing_arguments` 负责校验调用参数【31】。RV 官方 README 的边界表在“Domain capabilities”那一行给出的扩展说明是：注册能力描述、已校验的参数与执行器【31】。

但有一处必须纠正过来：RV 的 `AgentSkill` 是**规划侧契约**，不是执行侧契约。它只有能力标识、能力集、可选的清单，以及一个 `plan(planner, arguments)` 方法，返回一个字典；清单里带的是规划指令与路由模式【31】【41】。真正干活的是宿主注入的 planner——能力路由时由 planner 决定调用哪个能力【41】。所以 RV 侧的执行面在任务执行端口与委托契约两处，不在 skill 里。

也就是说，RV 已经做到了“注册加参数契约加校验”这套插件该有的语义形状。缺的不是注册表，是**执行面的归属**与**跨进程的发现与传输**。

还要补一个来自 rakazo 侧的发现，它的现成程度比 RV 侧更高。rakazo 的 `@rakazo/adapter-kit` 已经是一套完整的 provider 契约层：每个 provider 都有 `describe()` 返回适配器描述（含契约版本、适配器版本与能力集），连接器 provider 分工具发现与执行两步，调用与回传分别是调用体与事件流（日志、结果、错误三类），每次调用携带一份适配器上下文（操作标识、追踪标识、租户标识、用户标识、bot 标识、运行标识、取消信号、已连接的外部账号）【34】【35】。注册靠适配器注册表，按插槽名管理十八类 provider【36】。

也就是说 rakazo 侧不但有注册表，还有调用协议、事件流与跨进程上下文。这直接改变工作量的判断：能力描述与跨进程上下文这两样，原先打算为 ms 自造，现在都不需要自造。

还有一处需要单独处置：工作状态机。RV 的工作状态落在本地 SQLite 文件里，恢复时不重放已执行的动作。把执行器移到插件后端、进程边界改变之后，工作状态文件不能跨进程共享，需要把状态机移到服务端或改为事件流——这是一块独立工作，不是协议改造能顺带解决的。

**结论**：采纳“委托协议门与工作状态机抽成 ms 的能力插件、执行器接插件后端、不 fork 进程内注入层”这个方向，但把工作拆成三块，并修正我此前对工作量的判断。

第一块是契约落点，已经有现成答案：沿用 rakazo 的 `@rakazo/adapter-kit` 契约层，不另造接口【34】【35】【36】。这套契约层已经定好能力怎么声明（适配器描述含契约版本，工具声明含名称、说明与入参模式）、调用怎么表达（调用体含工具名、参数与执行标识）、回传怎么流（事件流三类）、每次调用带什么上下文（适配器上下文）。注册用适配器注册表的插槽机制，能力类落连接器插槽，agent 运行时落运行时插槽。

这套契约层顺带提供了三样东西：契约版本，用于判定“契约版本不匹配即拒绝连入”；参数契约，即工具声明的入参模式，可由 RV 的 `routing_contracts()` 输出直接映射；副作用声明，即工具声明的只读标记与批量动作声明——只读标记的语义是“标为否即强制审批，标为是也不放松基于名称的门禁”，批量动作声明让批量工具里的每个动作单独受审批规则与读写检查判定【35】。

副作用声明这一项要补一句限定：RV 侧的能力清单里没有这两个字段，`routing_contracts` 只输出名称、说明与入参模式【31】。所以只读标记与批量动作声明需要 ms 侧按能力逐个补，不能指望从 RV 自动映射。缺省语义也要写死：未声明只读标记的能力按写操作处理，一律强制审批。

第二块是 RV 执行器的接入形态，这块比上一版估计的大。能力声明部分成本低：把 `routing_contracts()` 的输出转成工具声明，名称、说明与入参模式三项一一对上【31】。执行面部分成本高：RV 的 `AgentSkill` 只有 `plan(planner, arguments)` 一个方法，执行由宿主注入的 planner 承担【41】。适配层因此要新增两样——一是 planner 注入，把 ms 侧的执行器作为 planner 传给 skill；二是“路由决策到具体执行”的衔接，把 planner 的路由结果接到真实执行器上，并把过程事件转成事件流【34】。

这条也改写了宿主归属的判断：进程外插件的宿主侧包装器本身可以用 TypeScript 实现成连接器 provider，并在内部用 MCP 与 Python 侧说话——两种做法不是互斥的，而是同一件事的两层。因此 adapter-kit 的契约在 MCP 线上不直接参与，只有宿主侧的包装层参与；“不另造接口”这句话只对进程内路径成立。

第三块是跨进程传输层新建，这仍然是本项工作的主体。契约层已经定好要传什么，缺的是把这份契约从进程内调用变成跨进程请求-响应与事件流。

关于工作状态机：它不进能力插件，走服务端状态存储。原因是它的语义是“这个任务执行到哪一步、哪些副作用已经发生”，这属于需要跨进程共享且需要崩溃恢复的状态，不是能力描述的一部分。

**理由**：不 fork 进程内注入层的理由是构造注入无法跨进程：ms 的本机 agent 与中心 Loom 是两个进程，注入只能发生在本机进程内，一旦能力要由中心侧提供（例如某个只在服务器有凭证的操作），构造注入就无路可走。provider 契约把“谁执行”从调用点解耦出去。

沿用既有契约层而不是自造的理由还有一条：自造协议意味着 ms 与 rakazo 生态分家，进程外插件要写两套适配器，契约版本要维护两套。沿用则意味着 RV 的能力描述、rakazo 的连接器生态、ms 的本机宿主三者用同一份协议。

**推翻条件**：若 ms 的 Phase 1 里所有能力都只在本机进程内执行、不存在跨进程提供的能力，且确定 Phase 2 也不会引入，那么可以保留构造注入、跳过传输层新建。但这个条件与“ms 与 Loom 组合”的目标直接冲突，因此只在 ms 完全退化为单机单进程时成立。

> **〔2026-11-01 变更，见修订前言拍板七〕** 执行面落点修订：契约形状（ConnectorTool/ConnectorCall/Event/AdapterContext、18 插槽）照常吸收为 Python 契约，但 RV 执行器改为 **Python 同栈直连**（进程内或子进程），MCP 传输保留给真正的第三方插件；Pi（TS SDK）不进 Phase 1。批次五"RV 执行器接入与 planner 适配"仍是最重子项，但省去跨语言桥接。

### 1.5 独立形态的等待期人类在场

**问题**：ms 单独运行时，流程走到需要人工确认的节点，是否保留等待期人类在场；若保留，承诺口径怎么写。

**调研**：先看行业里这类承诺靠什么兑现。Duet 的形态是“有自己的云电脑、关掉应用后工作继续、批准延迟回传”，但它的前提是任务跑在 Anthropic 的云端机器上【25】。OpenAI 的 dots 同样给每个 dot 配一台专属云电脑，主动研究阶段只读，任务完成需要人确认【26】；它的权限分档与留存策略另有专门分析【27】，与另一种常驻形态的横向对比也说明“云端常驻”不是这个品类唯一可行的形态【28】。dsh 的日程包是“会话内提醒、冷会话恢复、没有外部通知通道”【20】。

三者共同点是：等待期能继续，靠的是执行环境常驻在别处。

再看 ms 本机形态的约束。本机形态里，agent 运行时就在用户机器上进程里；进程终止、机器休眠、用户注销都会让运行时消失。Loom 侧的挂起语义是确定的：进入等待期时任务状态转为待人工、租约被置空、运行状态同步转为待人工（`src/loom/execution.py:191-192`）【30】。租约过期后的回收是确定性的：没有未结算副作用的任务回到待领取并递增 epoch，有未结算副作用的任务转入待人工裁决、不自动回池（`src/loom/store.py:289-306`）【30】。也就是说“挂起”在 Loom 侧不是一个持续占用的状态，而是一次让出。

rakazo 自己的处理也说明同一件事：机器人请求人工接管后，非计费型云端机器会为这台机器保活三十分钟以便登录页还在等待，计费型机器靠请求重置空闲计时器（`docs/computer-runtime.md:40`）【2】。保活是云端机器才有的能力。

**结论**：保留等待期人类在场，但把口径改写得更准确一点。

用户给的口径是“人不需要离开对话就能让流程继续”。这个口径抓对了主体，但漏了一个约束：真正的约束是**进程存活**，不是对话开着。机器睡眠、用户注销、进程崩溃都会让流程停下，而对话窗口可能还亮着。所以口径建议改成：

**“本机进程存活且对话可达期间，流程可以因人工确认而继续；进程终止、机器休眠或连接中断时，流程停在待人工，恢复后由人重新触发，不自动续跑。”**

配套要写明不可承诺清单，共三条：人不在时任务继续跑（本机形态不具备这个前提）；跨会话保持对话上下文（等待期结束后上下文不自动延续）；后台推送批准提醒（不做任意出网回调，见第 8.4 节）。

**理由**：承诺口径一旦写得比事实宽，后面每一次误报都要用人力去解释。把约束写准，比承诺得漂亮重要——尤其是这类形态最容易被拿去和 Duet、dots 比较。

**推翻条件**：若 ms 后续在本机引入常驻的调度守护进程（开机自启、机器睡眠唤醒后自动恢复），可以把“进程存活”这一条放宽为“守护进程存活”，但“人不在时任务继续跑”这条仍然不成立——除非执行器本身移到远端执行域，那时承诺由组合形态承担，不由本机形态承担。

### 1.6 五项决策的相互依赖

五项决策之间不是并列关系，有两条依赖链需要写明，否则施工时会出现顺序错误。

第一条是 Q1 与 Q2 的依赖。执行域策略挂在 Space 上，用户体系范围决定 Space 里有没有多个真实主体。Q2 的结论是保留完整模型，所以 Q1 的策略有地方落；反过来如果先做单用户精简版，执行域策略就只能挂到部署级，退化成全局配置，多工作区场景无法各自指定。

第二条是 Q3 与 Q4 的依赖。fork 粒度决定 ms 的能力插件落在哪个包里；RV 二开深度决定插件接口的形状与传输层的位置。Q3 的结论是 `packages/adapters` 里设备客户端与云端 provider 需要切分，Q4 的结论是能力插件直接落在 `packages/adapter-kit` 的 provider 契约层。两者合起来的落点是：`packages/adapter-kit` 承接契约扩展与新的 provider 实现，`packages/adapters` 切分出本机宿主与进程外插件传输层，`packages/adapters` 的现有切片（云端 provider 适配）保持不动。

## 第二章 目标形态与拓扑

### 2.1 三方关系

ms 的目标形态里有三方：人、ms 实例、Loom 中心。三方的关系决定了整个方案的形状。

ms 实例运行在人的机器上，持有对话界面与本机执行能力。Loom 中心运行在服务器上，持有编排、审计与租约。两者之间是“本机主动出网、中心不反向连”的连接方向，理由在 1.3 节已述【10】。人在场时，ms 与人对话；任务需要中心能力时，ms 把任务提交给 Loom；Loom 需要人工确认时，通过 ms 把问题递给人。

这个方向与 rakazo 的原方向相反。rakazo 是“中心持有 agent 运行时，用户机器是它操作的执行域”【2】，而 ms 是“用户机器持有 agent 运行时，中心是编排与审计”。方案里所有涉及跨边界的改动都源于这次倒置。

后文有三处与“中心”相关但含义不同，需要先分清：编排中心指运行 Loom 的那台服务器，是跨机契约的另一端；中心形态指 ms 自己以 `MS_ROLE=orchestrator` 运行时的那套装配，此时 ms 与 Loom 跑在同一台机器上，跨机契约退化为进程内调用但字段与语义不变；中心侧执行器指远端执行域里承接任务的那台执行位置，与编排中心不是同一台机器（详见第 6 章）。

### 2.2 五种运行形态

ms 的目标形态可以分成五种。它们共享同一份代码，差别在装配与开关。

| 形态 | agent 运行时位置 | 中心侧 | 人的位置 | 典型场景 |
|---|---|---|---|---|
| 独立 | 本机 | 无 | 本机对话窗口 | 单人自用，全天候 agent |
| 组合 | 本机 | Loom 在线 | 本机对话窗口 | 与团队共享编排与审计 |
| 分布式 | 每台机器一份 | Loom 在线 | 各自本机 | 多机并发提交任务 |
| Loom 自立 | 中心 | Loom 自己 | 浏览器或桌面端 | 不装 ms，直接用 Loom |
| 降级独立 | 本机 | 中心失联 | 本机对话窗口 | 中心不可用时的本地退行 |

前三种形态都以 ms 为主体，区别在于中心侧是否在线以及是否有多台实例。第四种形态的主体是 Loom 自己，ms 不是它的组成部分。第五种是第三种的降级分支。

表中五行的差别集中在三处：运行时位置、中心是否参与、人在哪里。这三处决定了后面每一章的配置项。

### 2.3 形态之间的切换规则

形态不是用户手动选的开关，而是由部署配置与运行状态共同决定。这条规则需要写死，否则会出现“本机同时连着中心、又被当成独立形态调度”这类歧义。

判定顺序是三步，都在“编排中心可达”这个前提之下。

第一步看编排中心登记的 ms 实例数，按空间统计：一台即组合形态，多台即分布式形态。这个计数必须来自中心而不是本机——每台 ms 只知道自己的注册，读自己的计数永远得 1，会永远停在组合形态。

第二步看执行域策略：Space 声明的默认执行域决定新任务跑在哪台机器上。

第三步看形态降级：编排中心不可达时进入降级独立，任务只在本机排队，不提交。

Loom 自立形态不在这条判定链上。它是用户主动选择的另一条入口——不装 ms、直接用 Loom 的界面——与 ms 是否在线无关。把两者放进同一条判定链会出现“编排中心不可达所以进降级独立、但 Loom 也不可用所以进 Loom 自立”这种互斥。

降级独立不是失败模式，它是一个设计过的形态。中心失联时 ms 仍然可对话、可在本机执行任务、可排队，恢复后由人决定是否补交。这一点在第 4.4 节有对应的存储设计。

## 第三章 现状基线

本章把三个代码库的一手事实固定下来，后续章节直接引用这些事实而不重复论证。所有结论都带文件与行号。

### 3.1 rakazo 的可继承面

rakazo 是 ms 的基座，它的分层结构、可继承资产与禁区如下。

| 层 | 包 | 在 ms 中的定位 | 处置 |
|---|---|---|---|
| 契约层 | `packages/contracts` | 两侧共用 | 保留，仅扩展 |
| 契约层 | `packages/adapter-kit` | 两侧共用，承接能力契约 | 保留并扩展 provider 契约 |
| 核心层 | `packages/core` | 两侧共用 | 保留 |
| 数据层 | `packages/db` | 中心侧主体 | 保留隔离判定，扩展空间 |
| 适配层 | `packages/adapters` | 需要切分 | 拆成云端 provider 与本机客户端两半 |
| 认证层 | `packages/auth` | 中心侧主体 | 保留，关闭自助注册 |
| 应用层 | `apps/api`、`apps/web` | 中心侧与客户端侧 | 改造成双形态装配 |
| 设施层 | `infra/sandboxes`、`infra/compose` | 中心侧 | 保留，隔离降级执行域；批次五涉及插件宿主 |

表中八行的处置依据是 1.3 节得到的依赖图：契约层、核心层与 provider 契约层不依赖数据层与适配层，因此可以两侧共用；适配层同时含两类互不相容的连接方向，必须切分。

可继承的三块资产值得点名。

第一块是用户设备客户端的连接治理。它实现了本机主动向外建立 WebSocket、服务器永不反向连接、握手携带设备令牌、每次请求前过授权回调、收到吊销消息即停机、断线不重试、重连使用全抖动【10】。这组治理规则正是 ms 需要而 rakazo 中心侧不具备的：ms 的本机在 NAT 后面，中心不能主动连本机。

第二块是行级隔离判定。`requireMembership` 与 `scoped` 两个函数构成了完整的租户隔离判定链，异常语义为不泄露存在性的 `IsolationError("Resource not found")`【12】。

第三块是审批策略的挂载方式。`ActionApprovalRule` 按 `spaceId` 生效，`ActionAutoReviewPreference` 在 Space 与 User 两级都有【8】。这是 Q1 结论里“Space 策略显式指定”在 rakazo 侧现成的表达范式。

不可继承的部分有四类，3.2 节逐类展开：把 agent 放在中心的运行时结构、Team bot 的目录级隔离假象、宿主机执行域的缺失容器边界、以及把 Pi 绑死在中心进程里的依赖位置。

### 3.2 rakazo 的四类禁区

第一类是 Team bot 目录不是安全边界。官方文档写明“每个工作区默认配一台团队计算机，机器人共享它的文件与已安装工具；每个团队机器人从 `bots/<bot-id>/` 起步，刻意共享的工作放在 `shared/` 里。这些目录组织工作，但不是安全边界：每个团队机器人能访问整个团队工作区”【2】。需要隔离时应当用私有计算机或独立计算机（`docs/computer-runtime.md:34`）【2】。ms 的本机执行域必须按这个口径设计：目录级约定不构成隔离声明。

第二类是宿主机执行域没有容器边界。`SandboxProvider` 的后端列表里包含 `desktop` 与 `fake`，前者跑在宿主机上（`docs/computer-runtime.md:8`）【2】；而容器才是安全边界（`docs/computer-runtime.md:34`）【2】。ms 若在用户自己的机器上跑，不具备容器边界这件事必须显式告知用户并写进风险清单。

这条要分成三个强度不同的命题分别写，混成一句会把其中一个完全没被覆盖的风险面藏起来。

命题一，成立但只防逃逸。rakazo 已有配套实现：沙箱类型在环境值是 docker 且计算主机标记为本机时切换成宿主机类型；宿主机 provider 把可访问的文件根限制在用户主目录；命令执行有独立的放行检查【38】。ms 沿用这一档。它防的是逃出主目录，不防主目录内的破坏——把整个主目录加密是一次完全在界内的写。界内的完整性靠审批门与不可逆确认来治理那些已声明的写。

命题二，未被覆盖。插件进程本身以用户身份运行，不受上面任何约束。它可以直接开文件、发网络请求。装一个能力插件等于装一个软件。这是 Phase 1 的信任模型而不是缺陷，但它必须被明说，不能用命题一的措辞盖过去。

命题三，只覆盖一半。只读标记覆盖本地写，不覆盖网络出向。声明只读但可联网的工具，可以读文件并外传。

三条各自的处置见 6.1 节、7.2 节与 12.1 节。

第三类是 Pi 绑在中心进程。`docs/computer-runtime.md:13` 明确 Pi 运行在 API/worker 进程里，并不安装进沙箱机器【2】。ms 要把 Pi 运行时搬到用户机器。

这一处的改造面比直觉小，但原因是 rakazo 侧已经把 Pi 包在接口后面：agent 运行时是一个 provider，接口只有描述、运行与中止三个方法，能力集声明流式、压缩、工具与脚本四项；实现文件本身按职责拆成会话记录、工具宿主、模型解析、流式回传、错误映射、回退策略、子 agent 等若干模块【34】【39】。搬运行时主要是搬这些模块加一个本机宿主，不是重写一个整体运行时。

第四类是 supervisor 的宿主权限。官方文档写明 API 进程拿不到不受限的 docker socket，supervisor 掌握生命周期（`docs/self-host.md:80`）【3】。中心形态保留这个结构；本机形态不引入 supervisor。

### 3.3 Loom 的现状与缺口

Loom 是编排与审计中心，它当前的形态与 ms 需要的能力之间存在具体缺口。

现状的正面部分有四项。租约与栅栏机制完备：领取任务时带 worker 标识与租约时长，提交产出时带 epoch 栅栏与幂等键，两者合起来保证同一任务不被重复完成（`src/loom/api.py:529-541`）【30】。挂起与回收语义确定（`src/loom/execution.py:191-192`、`src/loom/store.py:289-306`）【30】。事件链可校验（`src/loom/store.py:621-632`）【30】。计划批准有修订号与摘要双重校验（`src/loom/api.py:335`、`src/loom/workflow.py:399-410`）【30】。

缺口集中在九项，下表列出每一项的现状依据与批次归属。

| 缺口 | 现状依据 | 性质 | 批次 |
|---|---|---|---|
| 事件出口无游标 | 全量返回（`src/loom/store.py:615-618`） | 需新增 | 三 |
| 租约续期无路由 | 仅存储层有（`src/loom/store.py:376`） | 需新增 | 三 |
| 计划读取缺读接口 | 修订号只在写路径返回（`src/loom/workflow.py:290-293`） | 需新增 | 三 |
| 域包模板无参数契约 | 模板只有标识与节点图（`src/loom/domain_packs.py:81`） | 需新增 | 三 |
| 机器批准路径存在 | 旧式密钥派生 developer（`src/loom/auth.py:91`） | 需关闭 | 三 |
| 存储仅 SQLite | `src/loom/store.py:1-5` | 需重写 | 三 |
| 缺运行预设与插件内核 | 能力靠硬编码 | 需新增 | 五 |
| 独立形态无入口 | 无单点派活入口 | 需新增 | 二 |
| 本机侧无 provider 宿主 | 契约层已备（`packages/adapter-kit`）但无本机宿主 | 需新增 | 五 |

表中九项的性质分三类：需新增的是接口或字段，缺件的是从未存在过的能力，需关闭的是一条不该存在的路径。存储那一项性质最重，它不是加一个接口而是换一层存储实现。

### 3.4 RV 的可复用面

RV 是 ms 的能力来源，它的五处扩展点已在 1.4 节列出【31】。除此之外还有三样东西值得继承。

第一是委托的运行时形状。RV 的运行时由委托捕获、派发与回传三段构成【32】。这个三段式与 ms 的跨机契约天然同构：捕获对应提交、派发对应领取，回传对应提交产出。

第二是工作状态的恢复语义。RV 的工作状态落本地 SQLite，恢复时不重放已执行的动作【31】。这个“不重放”的语义在分布式形态下是必需的：ms 重启后不能重复执行已经有副作用的动作。

第三是能力注册表的形状，已在 1.4 节详述。

不可直接继承的是进程内注入层本身，理由同 1.4 节。

## 第四章 总体架构

### 4.1 组件清单

ms 的完整形态由九个组件构成。下表给出每个组件的运行位置、职责与形态开关。

| 组件 | 运行位置 | 职责 | 中心形态 | 本机形态 |
|---|---|---|---|---|
| ms 客户端 | 本机 | 对话界面、提交任务、轮询回执 | 启用 | 启用 |
| ms 调度器 | 本机 | 队列、定时触发、派活入口 | 启用 | 启用 |
| ms 执行器 | 本机 | 领取任务、跑能力插件、回传产出 | 可选 | 启用 |
| 能力插件宿主 | 本机 | 加载能力插件、转发调用 | 可选 | 启用 |
| Loom API | 中心 | 目标、计划、批准、事件的权威来源 | 启用 | 禁用 |
| Loom worker | 中心 | 调度器唤醒、计划执行 | 启用 | 禁用 |
| 租户与鉴权 | 中心 | 用户、空间、令牌、行级隔离 | 启用 | 禁用 |
| 审计事件存储 | 中心 | 事件追加、链校验 | 启用 | 本地替身 |
| 本机状态存储 | 本机 | 队列、触发器、本地审计 | 启用 | 启用 |

表中九行里有三行的开关是“可选”或“禁用”，这是本机形态与中心形态的主要差别。

### 4.2 两个形态开关

方案不引入“模式”这个运行时概念，而是用两个正交的装配开关控制。

第一个开关是 `MS_ROLE`，取 `client` 或 `orchestrator`。取 `client` 时进程内不启动编排侧组件，保留客户端、调度器、执行器、能力插件宿主与本机状态存储；取 `orchestrator` 时进程内启动完整的服务面。默认取 `client`。执行器与能力插件宿主属于客户端角色——本机形态下它们是必需的，这与 4.1 节的组件清单一致。

第二个开关是 `MS_EXECUTION_DOMAIN`，取 `local` 或 `remote`。取 `local` 时执行器在本机进程内运行能力插件；取 `remote` 时执行器不启动，任务只提交给中心执行。默认取 `local`。

两个开关正交，组合出四种装配。其中“`orchestrator` 加 `remote`”这一种在 Phase 1 不使用，原因是中心侧执行域在 Loom 侧需要独立的执行器注册与栅栏协调，与 ms 的本机执行器不是同一套协议。

关于 Q1 的结论落到代码上：执行域的默认选择来自 Space 策略，`MS_EXECUTION_DOMAIN` 只决定本机默认是否参与执行，不覆盖 Space 的逐 bot 覆盖。

### 4.3 进程模型与生命周期

ms 的本机侧由三个进程构成，各自的生命周期与故障域不同。

ms 客户端是常驻进程，负责对话界面与与中心的连接。Phase 1 它只用 HTTP：对话走请求-响应，事件的完整读取走带游标的轮询。

实时通道在 Phase 1 明确不引入，理由是与 11.8 节 G3 同源：G3 断言不存在中心到 ms 的投递通道，而 WebSocket 是双向通道，两者不能并存。要引入实时通道，得先改写 G3 的口径，这件事放到 Phase 2 重议，重议时两处一起改。

从 rakazo 用户设备客户端继承的是连接治理规则而不是它的传输方式【10】：本机主动出网、服务器不反向连、握手带设备令牌、每次请求前过授权回调、收到吊销即停机、断线不重试、重连使用全抖动。这七条约束的是连接行为，与用 HTTP 还是 WebSocket 无关，所以 Phase 1 全部成立（1.3 节）。

ms 调度器是常驻进程，负责本机队列与定时触发。它在本机 SQLite 上维护两张表：一张是待触发任务队列，一张是触发规则表。调度器重启不丢内容，规则以数据库为准而不是以内存为准。

ms 执行器是按需进程，跑在能力插件宿主里。它从调度器领任务、加载对应能力插件、执行、回传。它是三者中唯一可以随时被杀死的，被杀后任务回到待领取队列。

三者的崩溃影响面分别是：客户端崩溃只影响对话，调度器崩溃只影响自动触发，执行器崩溃只影响在跑的任务。中心失联时三者都降级但不退出。

### 4.4 中心失联时的本机行为

中心失联不是异常路径，是设计过的降级路径，需要四个明确的行为。

第一，任务留在本机队列不提交。调度器照常按时钟触发，但产物写入本机待交队列而不是提交接口。

第二，本机审计照常追加。审计事件有本机替身存储，采用与 Loom 相同的信封形状（见第 5.5 节），中心恢复后按幂等键补交。

第三，对话能力不降级。本机的能力插件仍然可用，人可以继续在本机干活。

第四，客户端在界面上明确显示中心失联态，不静默。失联判定用连续轮询失败计数加连续成功后的恢复计数，避免网络抖动造成误判。

## 第五章 数据与身份模型

### 5.1 三层工作区的对照

“工作区”这个词在三个代码库里指三样不同的东西，这是方案里最容易出错的地方。下表做对照，并给出映射。

| 层 | 所在库 | 载体 | 隔离判定 | ms 中的角色 |
|---|---|---|---|---|
| 租户 | rakazo | `Space` | `spaceId` 相等 | 顶层归属与审计分区 |
| 工作目录 | RV | 本地目录 | 进程边界 | 本机能力插件的工作区 |
| 会话空间 | Loom | `tenant` | 凭证携带的租户号 | 跨机契约的分区键 |

对照表说明了三层之间的语义差别，也给出了映射：Loom 的 `tenant` 对应 rakazo 的 `Space`，RV 的工作目录是本机概念，不参与跨机隔离。

映射的实现方式是显式的，不靠命名巧合。ms 客户端启动时从中心拿到自己所属的 `spaceId`，把它与 Loom 侧使用的租户号一一对应并写入本机配置。契约里的分区键一律用这个映射后的值，不在代码里假设两个系统的 ID 空间相同。

### 5.2 用户、设备与实例的登记

ms 需要三类身份登记，三者都要落到既有模型上。

用户沿用 rakazo 的 `User` 与 `SpaceMember`【8】。用户在 Better Auth 里注册或被邀请，成员关系决定他能看到哪些空间。

组织层在 Phase 1 保留结构但不建逻辑：组织模型保留在数据层，权限判定不读取组织级角色——隔离、审计与执行域策略全部挂在空间上。管理员界面的范围因此是空间级加部署所有者页，不存在组织管理员页。这一项的重启条件是中心出现多组织托管，或者组织级共享资源（组织级凭证、组织级模型路由）成为真实需求；任一条件成立就回到 13.2 节重议。

设备沿用 rakazo 的 `UserDevice`【8】。ms 客户端在本机首次启动时生成设备密钥，向中心注册为该用户名下的一台设备，注册请求携带设备令牌与本机标识。

ms 实例是设备的一个属性，不单独建表。一个 ms 实例的标识由三段拼成：机器标识、实例序号、启动世代。机器标识来自本机生成的持久随机值，实例序号区分同机多实例，启动世代在每次重新注册时递增，用于让中心识别“同一台机器上的旧实例”。

这个递增有一个尾巴要处理：身份文件里的旧世代主体只增不减，机器重启或重装几次之后，同一台机器会留下一串历史主体。处置办法写死——高世代主体注册成功后，中心吊销同一台机器上的旧世代主体。吊销走既有机制（令牌被吊销即停机），不需要新协议，但必须落在注册流程里，否则历史主体会一直留在可用范围内。

这个标识体系直接决定幂等键的生成规则，见 5.4 节。

### 5.3 主体、令牌与双主体模型

ms 在中心侧注册两个具名主体，而不是一个主体拿两枚令牌。原因是一手事实：认证注册表要求 `(tenant_id, subject_id)` 唯一，同一主体第二次登记会让整个身份文件加载失败（`src/loom/auth.py:101-102`）【30】。

两个主体的划分是：`<实例>:operator` 负责提交目标与计划、读取计划与进度、组装批准请求；`<实例>:worker` 负责领取任务、提交产出。

批准这件事要拆成两半：做决定的是人，组装请求的是实例。所以 operator 主体不再持有计划批准能力——它只负责读出计划与进度、把批准卡片送到人面前、把人签过字的请求递上去。批准能力只授给用户会话主体（见下），端点层那道“主体必须是具名人类”的判定保留作第二道防线。

这个调整要落到角色集上：当前 operator 角色集里含计划批准能力（`src/loom/auth.py:22`）【30】，必须从角色集里移除；移除之后 operator 主体调批准接口会被能力检查直接拒掉，与 G6 的断言一致。

执行器主体还要拿一项能力。控制类端点（暂停、恢复、终止）要求控制能力（`src/loom/api.py:214`）【30】，而这个能力当前只在 operator 角色集里，worker 角色集只有读、领取与提交三项（`src/loom/auth.py:22-23`）【30】。ms 的执行器要发起人工介入就必须能调暂停，所以 worker 角色集要加上控制能力。终止动作要单独收紧：ms 的 worker 主体只允许暂停与恢复，不允许终止——终止是人的决定。

角色集的这两处改动与“关闭 legacy developer 机器批准路径”放在同一个批次项里，因为它们改的是同一张权限表。

这里有一处必须分清的概念：provider 层传递的 bot 标识，与 rakazo 的 `Bot` 模型行不是一回事。前者是调用上下文里的一个字符串，标识“这次调用属于哪个 agent 实例”；后者是数据库里的一行，承载名称、指令、模型选择与所属空间。ms 的两个主体在 provider 层用两个不同的 bot 标识表达，落不回 `Bot` 表的行——ms 的本机实例不需要在中心注册成一个对话 bot。写代码时不要把这两者混用：6.2 节新增的执行域字段挂在 `Bot` 模型上，管的是 rakazo 侧的 bot；ms 自己的执行域选择走 Space 策略与本机配置，两条路径不交叉。

这里有一个必须一并处理的事实：Loom 现状存在机器批准路径。旧式租户密钥派生 developer 角色（`src/loom/auth.py:91`），developer 的权限集里含 `plan.approve`（`src/loom/auth.py:25`），批准接口只校验能力而不校验是不是人（`src/loom/api.py:335`），而审计函数对 developer 主体返回空对象（`src/loom/api.py:207-208`）【30】。三者叠加的后果是批准事件的 actor 落空，被兜底成一个非具名的字面量（`src/loom/workflow.py:439`）【30】。这与“不做自动批准”的既有拍板直接冲突，必须由批次三关闭。

关闭方式有两条且都要做：其一，禁止 legacy 密钥派生 developer，developer 角色的下发路径改为显式人工授权；其二，批准接口增加“主体必须是具名人类”的判定，审计函数对非人类主体不再返回空对象而是记录拒绝。

第二条需要一个能实现的主体定义，否则它落不了地。双主体模型里的两个主体都是实例主体，人在 ms 客户端里点批准时，如果仍然用实例主体发请求，中心记下的 actor 就不是人。这里要补一条人类身份通路：ms 客户端用设备令牌换一个绑定到用户本人的会话令牌，人在界面上操作时用这个令牌签署请求，中心把批准事件的 actor 记为该用户的标识。

“具名人类”的可判定定义有三条：主体标识能解析到一个用户记录并有成员关系；该主体的凭证不是实例主体派生出来的；该主体带的是用户会话而不是设备或实例令牌。三条同时成立才算人类主体，缺一条都按机器主体处理。判据见 11.8 节的 G6。

双主体模型与 rakazo 的 provider 层是合得上的。适配器上下文的构造方式就是取租户标识、用户标识、bot 标识与操作标识四样，打包成一份带取消信号的上下文【37】。也就是说 rakazo 的 provider 调用在设计上就携带租户与用户这两个维度，ms 的双主体划分不需要另造承载面——`<实例>:operator` 与 `<实例>:worker` 落到 provider 层就是两个不同的 bot 标识加同一个租户标识。

### 5.4 幂等键与栅栏

幂等键的租户内全局共享是一手事实：幂等记录表的主键是租户与键的组合（`src/loom/store.py:77-79`）【30】。这个事实有两个后果。

后果一，多机并发的正确性依赖键不相交。键不相交时，“同一任务不被重复完成”的保证成立；两台机器生成同一个键时，后到者要么拿到前一台的缓存结果被当成重复提交，要么因参数不同直接冲突。

后果二，键必须自带机器专属前缀。ms 的键格式是四段：机器标识、run 标识、任务标识、尝试序号。尝试序号在同一任务的多次尝试间递增，其余三段保证跨机不碰撞。

栅栏沿用 Loom 的 epoch 机制。领取任务时中心递增 epoch 并返回，提交产出时必须带回领取时拿到的 epoch，不匹配则拒绝。这是多执行器并发下的第二道防线，与幂等键互补：幂等键挡重复提交，epoch 挡过期执行器。

### 5.5 事件信封与审计

ms 的审计事件采用与 Loom 相同的信封形状，字段为模式版本、事件标识、租户标识、运行标识、链标识、序号、时间戳、类型、主体、载荷、提交键、前序哈希与当前哈希。这个形状与 rakazo 的事件表结构几乎同构【8】，与 Loom 的事件表也一样【30】。

本机降级时写入本机替身存储，采用同一形状但不做链校验。

补交的语义写死：本机链有独立的链标识，中心为它单独建一条链，中心校验的是**链内连续性**——序号连续、前序哈希匹配本链的前一条——而不是把它接进中心原有链的哈希链。本机链与中心链之间不要求哈希衔接，因为两边的哈希各自在本链上算出来，跨链对齐没有可校验的依据。

事件的主体与载荷全部由服务端赋值，客户端没有写入口。这一点决定了“ms 如何把发起人写进审计”这个问题没有直接答案，解法见下一节。

### 5.6 发起人归集

事件载荷不接受客户端指定，所以发起人不能作为载荷字段写入。可行的办法是约定式归集：ms 提交目标时，在目标描述文本的头部插入固定前缀 `requested-by:<用户标识>`，中心侧在归集任务时按该前缀解析出用户标识。

这个办法的取舍要说清楚：它不进入结构化字段，所以审计链上的结构化部分不含发起人；它依赖描述文本不被改写，描述一旦被编辑归集就失效。

因此归集不做成离线批处理，而是**在目标创建的那一刻同步解析并入库**：创建接口收到带前缀的描述时当场解析出发起人，写进中心的派生表，解析失败当场返回可读的错误。这样描述被编辑的暴露窗口最小——从“事后可能失效”缩到“创建时即刻生效”。解析失败要显式报错而不是静默丢弃；派生表允许出现空值，但不允许出现无法解释的行。

替代方案是把发起人放进目标标识的字段结构里。这需要中心侧改输入模型，代价是每个目标携带一个额外的身份字段并且它会进入审计链——对 Phase 1 来说改动过大，约定式归集够用。

归集这条链的落点是两处：客户端在提交时写前缀（批次二），中心侧把解析结果落成派生表（批次三）。两处都要在验收里出现，见 11.6 节的 E3。

### 5.7 凭证归属

凭证分三类，归属规则不同。

模型凭证有两个来源，按形态分。

组合形态下模型凭证跟随空间：中心持有并按空间分发，ms 不长期持有原始密钥，需要调用模型时向中心申请短时会话凭证。

独立形态与降级形态下模型凭证由本机持有：用户把自己的密钥配在本机，ms 直接用它调模型，不经过中心。这条路径是必需的——独立形态的定义就是不连中心（2.2 节），降级形态的定义是中心失联仍然可用（4.4 节），两者都没有中心可以申请凭证。用户在机器上放自己的密钥，与把密钥放在任何一台自建服务的机器上是同一件事，信任模型没有变化。

这条约束落在验收上：独立形态的本机派活入口要在本机模型配置就位的前提下才可用（11.4 节的 C1）。

机器凭证跟随执行域。远端执行域的机器凭证在中心侧管理，本机执行域的机器凭证在用户机器上，用户自己决定放不放。

用户凭证跟随人。密码、通行密钥等只在中心侧保存，本机不持有。

跨机调用不传原始凭证，只传中心签发的、带作用域与到期时间的令牌。

## 第六章 执行位置与执行域

本章是 1.1 节决策的展开。内容覆盖两个执行域的定义、Space 级策略的表达方式与落库位置，以及将来重启自动路由需要满足的条件。

### 6.1 两个执行域的定义

ms 的执行域有两个，区别在于“谁持有能力插件宿主”。

| 维度 | 本机执行域 | 远端执行域 |
|---|---|---|
| 插件宿主位置 | 用户机器上的 ms 进程 | Loom 中心侧 |
| 能力来源 | 本机安装的能力插件 | 中心侧登记的能力插件 |
| 凭证位置 | 用户机器 | 中心 |
| 隔离边界 | 宿主机，无容器边界 | 中心侧的容器或沙箱 |
| 离线可用 | 是 | 否 |
| 任务领取方式 | 本机执行器领取 | 中心执行器领取 |

表中六行的差异会传导到三处设计：凭证归属（第 5.7 节）、隔离声明（第 3.2 节的禁区一与二）、以及任务领取的协议路径（第 8.1 节）。

本机执行域没有容器边界这件事需要向用户明说。rakazo 的文档明确“计算机容器才是安全边界；团队机器人共享操作系统用户、工作区、浏览器配置与 shell 权限，屏幕租约协调的是工具调用而不是容器内互不信任的进程”【2】。ms 在用户自己的机器上执行本机任务时，用户进程本身就是边界，这意味着能力插件在用户机器上具有该用户的权限。这个事实要写进部署向导与风险清单，不做淡化处理。

但边界不等于空白，而且这一节要按三条强度不同的命题分别交代，处置力度不一样（命题的划分见 3.2 节）。

第一条，宿主中介的约束成立但只防逃逸。rakazo 已经有“用户自己的机器当执行域”这一档：计算主机可以标记为本机，沙箱类型在这种情况下切换到宿主机 provider，宿主机 provider 把可访问的文件根限制在用户主目录，命令执行有独立的放行检查【38】。ms 沿用这一档。它防逃逸不防界内破坏，界内靠审批门与不可逆确认治理已声明的写。

第二条，插件进程本身以用户身份运行，不受上面任何约束。Phase 1 不解决这一条，处置是如实告知加披露：装一个能力插件等于装一个软件。

第三条，只读标记覆盖本地写不覆盖网络出向。处置是给工具声明加一个联网声明，未声明的一律按可联网处理。声明进安装确认界面与审计事件，定位是披露不是门禁——只读加联网有大量正当用途（网页检索就是其中一种），强制审批会把可用性打穿。披露加留痕是这个档位下诚实的强度。

宿主中介这一层另有两项处置，都属于批次五：凭证路径绊线与联网声明的落地，细节在 7.2 节与 10.8 节。

远端执行域在 Phase 1 的定位是“中心侧执行器”，即 Loom 自己已有的执行路径，不新增协议。它在 Q1 的结论里被保留，主要是为了让 Space 策略有一个非本机的取值，为将来“本机执行域不可用时的退路”留出位置。

### 6.2 Space 级策略的表达方式

执行域策略落在两个字段上，都是新增。

第一个字段在 `Space` 模型上，名为 `defaultExecutionDomain`，取值为 `local` 与 `remote`，默认 `local`。它是新建 bot 的默认执行域。

第二个字段在 `Bot` 模型上，名为 `executionDomain`，可空，值为 `local` 与 `remote`。为空表示继承 Space 的默认值，非空表示覆盖。

这个形态与 rakazo 现有的两处结构对齐。其一是 bot 与计算机的绑定方式：`Bot.computerId` 指向一台具体的 `Computer`，`Bot.computerSwitching` 控制是否允许切换【8】。ms 的 `executionDomain` 与它语义相同——执行位置是 bot 的属性。其二是 Space 级策略的挂载方式：`ActionApprovalRule` 按 `spaceId` 生效，`ActionAutoReviewPreference` 在 Space 与 User 两级都有【8】。执行域策略沿用同一挂载方式。

两个字段都需要迁移脚本。rakazo 的迁移在 `packages/db` 里管理，ms 的 fork 沿用同一机制；这里不引入新的迁移框架。

这两个字段的读写方也要写明，否则会变成没人写的死字段。写入方有两个：空间管理界面与对应的接口，负责设置空间的默认执行域；bot 管理界面负责设置单个 bot 的覆盖值。读取方有三个：派活时决定新任务进哪个执行域、执行器注册时决定自己服务哪个域、界面展示时显示实际执行域及其来源（继承还是覆盖）。读取方缺一不可——尤其是界面那一个，它让覆盖行为可解释。

需要说明的是，Space 字段不构成安全边界。`defaultExecutionDomain` 只决定新 bot 的初始归属，不阻止管理员逐个 bot 覆盖，也不阻止运行期调整。真正的隔离由 `scoped` 判定与令牌作用域承担【12】。

### 6.3 生效执行域的三处显示

执行域的生效值要在三个地方给用户看，三处职责不同、口径必须一致。

| 界面 | 职责 | 显示内容 |
|---|---|---|
| 派活入口 | 显示优先面 | 生效执行域、来源徽标、一行后果提示 |
| bot 详情 | 编辑面 | 生效执行域、来源徽标、覆盖开关 |
| 空间管理 | 分歧面 | 空间默认值、当前覆盖它的 bot 清单 |

三处显示的内容分两类。生效执行域与来源徽标三处都有——徽标区分“继承”与“覆盖”，继承指跟随空间默认值，覆盖指该 bot 自己设过。后果提示只有派活入口有，因为它承担的是最后一次拦截：派活入口是任务真正下发前的那一屏，人在这里还能拦住“任务跑去了不该去的机器”。

空间管理这一面是分歧面，解决的是“管理员设了默认、忘了三台 bot 在覆盖”这个盲区——默认值的下面直接列出覆盖它的 bot 清单。

工程要求只有一条：**三处的生效域由同一个函数计算**。Phase 1 没有自动路由，生效域是纯静态函数（继承规则见 6.2 节），没有理由算出两个答案。函数放在契约层，界面只消费它的结果。

后果提示的措辞受一条硬约束：必须引用 6.1 节修订后的三条边界命题，不能沿用“边界止于用户主目录”这种笼统说法。界面口径与安全口径必须同源，否则部署向导说一套、派活界面说另一条。本机域的后效文案是三条命题的压缩表述——本地写受声明与审批约束、插件进程本身不受约束、网络出向由联网声明约束；远端域的后效文案是“不依赖本机在线，受中心并发位约束”。

### 6.4 不做自动路由的操作化版本

1.1 节给了自动路由的推翻条件，6.4 节把它变成可执行的前置动作：即便 Phase 1 不做自动路由，也应当采集足够的运行数据，使得将来能够复算“自动路由是否更优”。

需要在每次派活时记录四个字段：实际使用的执行域、目标机器标识、该机器上的活跃任务数、该次任务的端到端耗时。这四个字段写入本机审计事件，中心同步后落库。

有了这四个字段，将来可以复算两件事：同一台机器上的任务耗时分布是否有显著差异（差异大则负载不均衡，自动路由有收益），以及耗时与活跃任务数是否相关（相关则活跃任务数可以作为负载代理信号使用）。

不采集这四个数据的代价是：将来要评估自动路由时没有任何历史数据可用，只能重新上线采一轮。这是一次性的额外成本。

## 第七章 能力插件层与 RV 二开

本章是 1.4 节决策的展开。内容覆盖 RV 五处边界的重新归类、能力插件的契约落点、两套宿主模式、参数契约与模板标识的绑定方式、跨进程传输的失败处理，以及工作状态机的处置。

### 7.1 RV 边界的重新归类

RV 的五处扩展点按“在 ms 里的归属”重新归置。其中“路由与润色”在实现上分成规划器与委托契约两段，所以下表是六行。这个归置决定了哪些直接继承、哪些改造、哪些移到中心侧。

| RV 边界 | 位置 | ms 中的归属 | 处置 |
|---|---|---|---|
| `AgentSkill` + `SkillRegistry` | `harness/skills.py:19`、`:82` | 能力插件接口 | 直接继承注册表形状 |
| `GeneralAgentPort` | `harness/agents/contracts.py:80` | 本机执行器的默认实现 | 保留进程内，作为内置执行器 |
| `DelegateBackend` | `harness/core/backend.py:16` | 委托协议门，中心侧实现 | 拆成两段：捕获在中心、派发在执行域 |
| `PlannerBackend` | `harness/llm/backends.py:12` | 路由与润色能力 | 降为能力插件的一个实例 |
| `VenusOmniServingPort` | `harness/bridge/serving.py:464` | 对话模型服务 | 走中心侧凭证，不进插件层 |
| `PlaybackPort` | `harness/bridge/host.py:95` | 客户端播放适配 | 留在客户端，属前端能力 |

表中六行的处置有一个共同判据：凡是需要持有长期凭证或需要跨进程共享状态的，进中心侧；凡是纯计算且可在毫秒级完成的，进本机插件层。

`DelegateBackend` 的拆分需要说明。原协议有四个方法：计划、执行、口语化、关闭【31】。拆分后，计划与口语化留在中心侧（它们需要上下文与凭证），执行落到执行域（它需要能力插件与工作区），关闭变成两处各自的清理。

### 7.2 能力插件的契约落点

ms 的能力插件不另造接口，沿用 rakazo 的 `@rakazo/adapter-kit` 契约层【34】【35】【36】。这套契约层回答三件事：能力怎么声明、调用怎么表达、回传怎么流。

能力声明有两样。适配器描述含标识、契约版本、适配器版本与能力集四项；工具声明含名称、说明与入参模式，另有四个可选字段：只读标记、批量动作声明、路由信息与联网声明【35】。路由信息是进程内的路由元数据，不暴露给模型。

联网声明是 ms 在契约层扩展的一项，adapter-kit 现有定义里没有它【35】。取值是布尔，未声明一律按可联网处理——声明缺失时取更保守的一侧。它的用途是披露：安装确认界面显式显示这一项，调用审计事件也记录它。它不是门禁，联网能力不因此被拦下。

宿主中介这一层要配套两项，都属于批次五。凭证路径绊线：对既知凭证路径（SSH 配置目录、云凭据目录、证书私钥目录、浏览器凭证库）的中介访问一律拒绝并记审计事件，显式上报、不许静默跳过。联网声明的落地：安装与调用两处都按声明把联网能力披露给使用者，并写进审计事件。

要写明的是：绊线是绊线不是边界。它降低误触概率，防不住插件进程直接读文件——那是命题二的范畴。只读标记的语义是“标为否即强制审批，标为是也不放松基于名称的门禁”；批量动作声明让一个批量工具里的每个动作单独受审批规则与读写检查判定，批准其中一个动作不等于批准其余动作【35】。

调用表达用调用体，含工具名、参数、执行标识与可选的连接标识与路由信息；回传表达用事件流，三类事件分别是日志、结果与错误【35】。

每次调用携带的上下文由适配器上下文定义，含操作标识、追踪标识、租户标识、用户标识、可选的 bot 标识与运行标识，一个取消信号，以及已连接的外部账号列表，另外还有屏幕租约标识、屏幕保温标记与取消时收尾三个字段【35】。这组字段里除取消信号外都是可序列化的，跨进程要传的就是它们，ms 的传输层不需要自己定义上下文。

取消信号是唯一的例外，它不可序列化，跨进程时被映射成一次取消调用（见 7.6 节）。另外要注意上下文构造与字段全集不是一回事：上下文构造只取租户标识、用户标识、bot 标识与操作标识四样，其余字段由调用方按需补【37】；跨进程要传的是字段全集，不是构造时取的那四样。

注册用适配器注册表，按插槽名管理十八类 provider，插槽包括运行时、沙箱、记忆、家目录、产物、机密、任务、实时、通知、模型、连接器、连接鉴权、执行者、语音、网页、浏览器、云端 agent 与自动审阅【36】。ms 需要的两种 provider 形态都落在这套插槽机制里：能力类落连接器插槽，agent 运行时落运行时插槽。

### 7.3 宿主形态与语言边界

插件宿主分两种形态，这个二分由语言边界决定：rakazo 与 ms 客户端是 TypeScript 栈，RV 是 Python 栈。

进程内插件用 TypeScript 实现，宿主是 ms 进程本身，直接函数调用，无序列化开销。能力清单由宿主在启动时枚举。

进程外插件用任意语言实现，宿主通过标准输入输出通道与它通信，协议选 MCP。理由是 rakazo 已有同构机制：`Space` 上挂 `mcpServers`，`Bot` 上挂 `botMcpServers`，能力安装有 `CapabilityInstall` 与 `CapabilityInstallSpace`【8】。沿用 MCP 意味着 ms 不自造一套能力协议，进程外插件的生态可以直接复用。

RV 的 Python 执行器按进程外插件接入，通过 MCP 承载它的 `AgentSkill` 能力，包装成一个连接器 provider 实现：工具发现返回能力清单，执行返回事件流【34】。

RV 侧的能力参数契约直接映射到工具声明的入参模式。RV 的 `routing_contracts` 输出名称、说明与 `arguments_schema`，缺省时兜底为 `{"type":"object","properties":{},"additionalProperties":False}`【31】；这三项与工具声明的三个对应字段一一对上，不需要额外的转换器。

这个二分带来一个额外好处：语言边界不再是设计约束。将来要接入其他语言的执行器，宿主侧不需要改动。

### 7.4 参数契约与模板标识的绑定

这是 Q1 拍板的第一条约束“模板标识必填、自由文本只作参数值”在 ms 侧的具体落法。

Loom 侧的域包模板只声明标识、标题与节点图，没有参数契约（`src/loom/domain_packs.py:81`）【30】。模板查询端点会连同模板标识一起返回已解析的工作流定义（`src/loom/domain_packs.py:172-181`）【30】。而目标与计划的输入体里都没有模板标识字段（`src/loom/api.py:57-62`、`src/loom/api.py:65-68`）【30】。

ms 的解法是在适配器契约层之上再维护一张映射表，把模板标识映射到能力名与参数契约。注册表在 ms 客户端启动时构建，来源是本机已安装插件通过工具发现返回的能力清单，加上中心下发的模板清单。

委托链因此是四步：ms 拿到模板标识，查注册表得到能力名与参数契约，用模板查询端点取回已解析的工作流定义，按参数契约校验自由文本参数，把校验后的参数连同定义提交为计划。

代价要写清楚：模板标识不进入 Loom 的审计链。审计只能追到包版本与节点图，追不到“用了哪个能力”。要让标识本身进证据链，需要给 Loom 的域包模板模型补参数字段，这属于 Phase 1 之后的可选项。

校验必须拒绝而非降级。参数校验失败时，委托请求返回明确的校验错误，不允许把校验失败当成空参数继续提交——这条对应第一条既有拍板里“Adapter 只做 Schema 校验加机械映射”。

### 7.5 工作状态机的处置

RV 的工作状态落本地 SQLite，恢复时不重放已执行的动作【31】。这个语义在分布式形态下必需，但文件不能跨进程共享。

处置方式是把它移到中心侧，但**不另立一套账本**。Loom 侧已经有事件、产物、预留与副作用四张表，构成现成的账本【30】。做法是在这套账本上补字段而不是新建表：给副作用记录补一个“是否可重放”的标记，给预留记录补“属于哪次尝试”，任务当前阶段从事件流读。副作用表的粒度是每次工具调用一行【30】，所以标记挂在调用粒度上，与批次动作的每个动作单独判定是对齐的。

这里还有一个必须补的缺口，见 8.1 节：外部执行器要能在动作开始前把副作用意图登记到中心，否则中心账本里根本没有这行，恢复时无法判定该不该重放。

副作用标记来自工具声明的只读标记与批量动作声明【35】，落在中心侧的副作用账本上（见上段）。只读标记为否的动作在账本里永久留痕，恢复时永不重放；批量动作声明里的每个动作单独留痕，批准其中一个不豁免其余；只读标记为是且无批量子动作的动作可以直接重放。

RV 的委托执行器里已有一处重复执行防护（`harness/bridge/execution.py:855-856`）【31】。这个防护在新架构下由中心侧状态表统一承担，插件侧不再需要各自实现。

本机侧保留一个只读缓存，用于断连时展示进度，不作为恢复依据。

### 7.6 跨进程传输的失败处理

进程外插件的通信会失败，失败处理要预先定好，否则每个插件会各自发明一套。

| 失败情形 | 判定 | 处置 |
|---|---|---|
| 插件进程启动失败 | 启动后无握手 | 任务留在待领取，事件记录启动失败 |
| 握手超时 | 超过握手时限 | 同上 |
| 单次调用超时 | 超过调用时限 | 取消调用，任务标记为可重试 |
| 插件中途退出 | 通道断开 | 任务回到待领取，按状态表判断能否重放 |
| 插件返回非法结果 | 事件流给出错误事件而非结果事件 | 任务标记为待人工，不重试 |

表中五种情形的共同原则是：可重试与不可重试要分开判定，判定依据是状态表里的副作用标记，不是错误的类型。

超时的取值需要与 Loom 的租约时长对齐。租约上限是一小时，默认三十秒（`src/loom/store.py:308-339`）【30】。插件调用时限必须显著小于租约，否则租约先到期而插件还在跑，会产生“任务被回收但插件仍在执行”的错位。方案取调用时限为租约的三分之一，并要求执行器在租约剩余时间不足调用时限时提前放弃领取。

取消的信号通路需要新建，不能当成现成的。适配器上下文里带的是一个取消信号【35】，它在进程内可以被动触发；但连接器 provider 的接口只有描述、工具发现、执行这三步，没有取消动作【34】。唯一现成的中止口是 agent 运行时的中止方法，挂在运行时插槽上，服务的是运行整体而不是单次能力调用【34】。

因此跨进程的能力调用要能被取消，需要补一条通路：在执行通道上增加一个取消动作，携带执行标识；宿主收到后终止对端调用并让事件流给出错误事件【35】。这条通路在 Phase 1 可以简化——能力调用的取消可以退化为“停止等待并丢弃结果”，不要求对端真正中断——但接口位置要留出来，否则后补要改协议。

## 第八章 与 Loom 的跨机契约

### 8.1 Phase 1 契约面

契约面收窄到 Loom 已经具备的能力，只新增三处改造。下表列出十六个动作。

| 动作 | 接口 | 方向 | 备注 |
|---|---|---|---|
| 发现可领工作 | `GET /v1/goals` | ms 从 Loom | 列举本租户目标；worker 角色凭读能力调用 |
| 解析模板 | `GET /v1/domain-packs/{name}/{version}/templates/{template_id}` | ms 从 Loom | 响应给出模板标识与解析好的定义 |
| 提交目标 | `POST /v1/goals` | ms 到 Loom | 必带幂等键；自由文本只承载参数值与描述 |
| 提交计划 | `PUT /v1/goals/{run_id}/plan` | ms 到 Loom | 必带定义、期望修订号与幂等键 |
| 读取计划 | `GET /v1/goals/{run_id}/plan` | ms 从 Loom | 给出状态、修订号与摘要，是批准的入参来源 |
| 读取进度 | `GET /v1/runs/{run_id}/events?after_seq=&limit=` | ms 从 Loom | 需新增游标，现为全量快照 |
| 读取状态 | `GET /v1/runs/{run_id}/progression` | ms 从 Loom | 已存在，但不含修订号 |
| 领取任务 | `POST /v1/runs/{run_id}/claim` | ms 到 Loom | 本机执行器注册为 worker 主体 |
| 提交产出 | `POST /v1/runs/{run_id}/tasks/{task_id}/submit` | ms 到 Loom | 必带 epoch 与幂等键 |
| 续租 | `POST /v1/runs/{run_id}/tasks/{task_id}/renew` | ms 到 Loom | 需新增；Phase 1 不做 |
| 批准计划 | `POST /v1/goals/{run_id}/plan/approve` | ms 到 Loom | 必带期望修订号、摘要与幂等键；由人触发 |
| 读取待办干预 | `GET /v1/interventions` | ms 从 Loom | 已存在；“等我确认”卡片的数据来源（`src/loom/api.py:344-346`）【30】 |
| 暂停运行 | `POST /v1/runs/{run_id}/control/pause` | ms 到 Loom | 已存在；执行器请求人工介入时调用（`src/loom/api.py:372-376`）【30】 |
| 恢复运行 | `POST /v1/runs/{run_id}/control/resume` | ms 到 Loom | 已存在；人处理完后调用（`src/loom/api.py:372-376`）【30】 |
| 登记副作用 | `POST /v1/runs/{run_id}/effects` | ms 到 Loom | 需新增；执行器在动作开始前登记意图，带 epoch、动作标识与副作用等级 |
| 裁决副作用 | `POST /v1/runs/{run_id}/effects/{call_id}/reconcile` | ms 到 Loom | 已存在；结算已登记的副作用（`src/loom/api.py:378-383`）【30】 |

十六个动作里需要新增代码的有三处：事件出口的游标分页、租约续租端点、副作用登记端点。续租端点在 Loom 侧只有存储层实现、没有暴露成路由（`src/loom/store.py:376`）【30】。副作用登记端点必须新建，原因见 8.2 节。其余十三个动作都已存在，因为 Loom 早就为“多个消费者异步领取任务”做过设计：领取携带 worker 标识与租约时长，提交携带 epoch 栅栏与幂等键，两者合起来保证同一任务不被重复完成（`src/loom/api.py:529-541`）【30】。

人工介入的动作面已经存在，但它的形态与“创建一条介入记录”不同。中心的介入列表是派生视图——它从运行状态、任务状态、副作用与预留的未结算情况算出来（`src/loom/operator.py:52-72`）【30】。介入不是一等记录，所以没有“新建介入”的接口；可用的动作是控制面那三个：暂停、恢复、终止（`src/loom/api.py:372-376`）【30】。

外部执行器请求人工介入时走暂停。暂停把运行状态改成暂停中，而领取动作要求运行状态是开放中才会发任务（`src/loom/store.py:313`）【30】。这一条是服务端的硬闸门而不是协作约定：运行一旦进入暂停中，任何执行器都领不走它的任务；租约到期后回收逻辑只改任务状态、不改运行状态（`src/loom/store.py:289-306`）【30】，所以任务回到待领取也不会被重新领走。人处理完调用恢复，恢复前会校验没有未结算的副作用与预留、预算没有超、尝试次数没有用尽，然后才把相关任务放回待领取并递增栅栏（`src/loom/operator.py:124-154`）【30】。

这条链有一个权限前提：控制类端点要求主体具备控制能力（`src/loom/api.py:214`）【30】，而当前角色集里这个能力只属于 operator 角色，worker 角色没有（`src/loom/auth.py:22-23`）【30】。ms 的执行器主体要拿到这个能力，处置见 5.3 节。

副作用登记这一处是本方案里最容易漏掉、后果又最重的一条。Loom 的副作用账本由执行器进程内的四处调用写入，全部在它自己的执行路径里（`src/loom/execution.py:132`、`src/loom/execution.py:174`、`src/loom/artifacts.py:510`、`src/loom/quotas.py:160`）【30】。外部的 ms 执行器没有这条路径：它在动作开始前无处登记，中心账本里就不会有那一行。若它随后在提交产出之前被杀死，回收逻辑判不出这次副作用尚未结算，任务会回到待领取队列，那次不可逆写操作就会被执行第二次——这正面击穿 7.5 节的“恢复时永不重放”。所以登记端点是分布式形态下的必需项，不是优化项。

### 8.2 事件出口的游标化改造

当前事件接口返回全量，没有游标（`src/loom/store.py:615-618`）【30】。多台 ms 各自轮询全量事件流，代价随事件数线性增长，且无法保证各自的读取进度。

改造后的语义是：请求带 `after_seq` 与 `limit`，响应给出事件列表、新的游标与是否还有更多。游标归消费者所有——每台 ms 各自持有自己的 `after_seq`，不设共享游标。

这个选择排除服务端推送。理由是推送会把“断线不重试”这条治理规则推翻，而这条规则是 ms 本机在 NAT 后面能稳定运行的前提（见 5.2 节与 1.3 节）【10】。Phase 1 与 Phase 2 都不实现服务端事件流。

游标化的一个副作用要写明：游标是每消费者一份，意味着同一个事件会被多个消费者各读一次。这是刻意的——各消费者的读取进度互不影响，任一消费者落后不会阻塞其他消费者。

### 8.3 幂等与幂等键的租户内共享

幂等记录以租户与键为主键（`src/loom/store.py:77-79`）【30】，键空间在整个租户内共享。多台 ms 并发提交因此需要键不相交，键的格式在 5.4 节定义为四段式。

一个容易被忽略的后果是：重试与并发在这里是同一件事。同一个键的第二次到达可能是网络超时后的重试，也可能是另一台机器的并发提交，两者在中心侧无法区分。区分的办法是让第二次到达的请求参数与第一次完全一致——参数不同则直接冲突而不是返回缓存结果，这样冲突会被暴露而不是被静默吞掉。

### 8.4 回传方式

回传以轮询为主。rakazo 对外部云端 agent 的既有做法也是轮询：`CloudAgent` 用租约令牌、租约到期时间、下次轮询时间与唤醒世代管理一次外部委派，没有出网回调【8】。这与不做任意出网回调的既有拍板一致，也天然适配 ms 在 NAT 后的部署。

本机侧的出网方向只有一条：ms 连中心。中心不连本机。吊销信息因此只能随轮询响应下发，ms 在下一次轮询时得知自己的令牌已被吊销。这条与 1.3 节引用的 rakazo 治理规则存在一处差异，需要明确：rakazo 的吊销是服务端主动下发消息【10】，ms 的吊销是轮询被动得知。差异带来的代价是吊销生效有一个轮询周期的延迟，这个延迟在实现上要显式处理——收到吊销标记后要立即停止在途任务并清理本地状态，不能等下一个周期。

### 8.5 错误与失败模式的对照

契约的每个动作都有对应的失败模式与处置。下表列出七种需要显式处理的失败。

| 失败 | 判定依据 | ms 侧处置 | Loom 侧处置 |
|---|---|---|---|
| 幂等键冲突 | 同一键但参数不同 | 停止重试，标记冲突上报 | 返回冲突，保留原始记录 |
| 修订号过期 | 批准时修订号不匹配 | 重新读计划再让用户确认 | 返回 409，不改状态 |
| 摘要不匹配 | 批准时摘要不匹配 | 同上 | 返回 409，不改状态 |
| 租约过期 | 提交时 epoch 不匹配 | 任务标记为需重试 | 拒绝提交，任务回池或转人工 |
| 权限不足 | 主体能力集不含该动作 | 停止调用，换主体或换路径 | 返回 403，不泄露资源存在性 |
| 中心不可达 | 连续轮询失败 | 进入降级独立（4.4 节） | 无 |
| 游标失效 | 游标指向的事件已不存在 | 从头重读一次并记录 | 返回可识别的失效标记 |

表中七行的共同原则是：ms 侧的处置不改变 Loom 侧的状态，Loom 侧的处置不假设 ms 一定在线。两侧的失败处理互不依赖。

## 第九章 等待期人类在场

本章是 1.5 节决策的展开。内容覆盖口径的准确表述、三种形态下的实现、界面表达与不可承诺清单。

### 9.1 口径的准确表述

等待期人类在场的承诺，按形态分三句表述。

独立形态：**本机进程存活且对话可达期间，流程可以因人工确认而继续；进程终止、机器休眠或连接中断时，流程停在待人工，恢复后由人重新触发，不自动续跑。**

组合形态：等待期由中心承接。ms 的进程存活不构成流程存活，流程的存续取决于中心侧的执行器与租约。人在本机对话窗口里可以确认，中心继续推进。

分布式形态：等待期绑定到具体执行域。本机执行域的等待期受本机进程存活约束；远端执行域的等待期受租约约束，租约到期后按回收规则处理。

三句表述的共同点是都写出了“谁来维持流程存活”这一前提，而不是笼统地承诺流程会继续。

### 9.2 实现方式

Loom 侧的挂起语义是确定的：进入等待期时任务状态转为待人工、租约被置空、运行状态同步转为待人工（`src/loom/execution.py:191-192`）【30】。租约过期后，没有未结算副作用的任务回到待领取并递增 epoch，有未结算副作用的任务转入待人工裁决、不自动回池（`src/loom/store.py:289-306`）【30】。回收是惰性的，在下一次领取任务时触发（`src/loom/store.py:318`）【30】。

但要分清路径：置空租约、转入待人工这套动作发生在 Loom 自己的执行器里，外部 ms 执行器走的是领取与提交契约，到不了这条路径。Loom 暴露出来的挂起动作是暂停运行（`src/loom/api.py:372`），它只改运行状态、不动任务租约（`src/loom/operator.py:95-106`）【30】。

所以组合形态下的等待期人类在场，Phase 1 靠三步实现：执行器收到人工介入请求时调用暂停动作，运行状态变成暂停中；执行器随后不提交产出、不续租；租约到期后任务回到待领取，但因为运行处于暂停中，没有执行器能领走它。人处理完调用恢复动作，运行重新开放，相关任务才回到可领状态。

这里有一个此前写错的后果需要纠正：显式的释放租约端点不再必要，因为暂停本身已经挡住了领取。相应地，挂起时长也不再受租约上限约束——租约上限是一小时（`src/loom/store.py:308-339`）【30】），但暂停中的运行不会被任何执行器领取，所以等待可以超过一小时。

这条保证是服务端硬闸门提供的，不是 ms 单方的协作约定。它依赖两件事：执行器确实调用了暂停动作，以及恢复动作的校验没有被绕过。判据见 11.8 节的 G7。

放弃租约这条路径要有可判定的判据，因为它同时决定“进程被杀掉”和“人主动等待”两种情况的行为：判据见 11.8 节的 G7。

### 9.3 界面表达

等待期在界面上要能让人一眼看出“现在轮到我”和“现在轮到机器”，并且要能区分等待的两种性质。

| 状态 | 界面表达 | 可用动作 |
|---|---|---|
| 等我确认 | 显眼的待办卡片，含确认与拒绝 | 确认、拒绝、查看详情 |
| 机器在跑 | 进度展示，含当前阶段 | 查看、暂停 |
| 等租约回池 | 说明性提示，含预计回池时间 | 手动重试 |
| 中心失联 | 顶部条幅，含降级说明 | 查看本地队列 |

表中四行的第三行容易被忽略：等租约回池与等我确认在语义上不同，前者不需要人参与，后者必须人参与，两者的界面处理方式应当不同。

跨端确认的一致性也是需求。人在 ms 客户端确认计划批准，中心侧的对话界面应当同步显示已批准状态。两个界面的同步靠轮询事件流实现，延迟是一个轮询周期。

“等我确认”这张卡片的数据来源是中心的干预列表读取动作（8.1 节的第十二个动作），已存在的路由是 `GET /v1/interventions`（`src/loom/api.py:344-346`）【30】。ms 客户端轮询这个接口拿到待办，再结合事件流推进卡片状态。

### 9.4 不可承诺清单

三条不承诺写进产品文案与部署向导，不做模糊化处理。

人不在时任务继续跑：本机形态不具备这个前提。Duet 与 dots 之所以能承诺，靠的是任务跑在云端机器上【25】【26】，ms 的本机形态没有等价条件。

跨会话保持对话上下文：等待期结束后，上下文不自动延续。需要延续时由人显式引用上一段会话的结论。

后台推送批准提醒：ms 不做出网回调，也不向中心注册推送通道。人在对话窗口里等着就会看到；人不在，回来后能看到待办列表，但不会收到主动提醒。

这三条与 1.5 节的推翻条件对应。若将来在本机引入常驻守护进程，第一条仍然不成立，只是约束对象从进程变成守护进程。

### 10.2 依赖关系

六个批次之间有五条依赖边。

批次零是所有批次的前置。原因不是技术难度，而是复现性：如果来源没有钉住，后面每一处改动都无法回答“这是相对哪个版本改的”【11】【15】【16】。

批次一依赖批次零。批次二依赖批次一，因为调度器要向中心登记实例、领任务。

批次三只依赖批次零，不依赖批次一与批次二。这是有意为之：Loom 侧的改造可以与客户端并行推进，两条线互不阻塞。这一条是排期上最省时间的地方。

批次四依赖批次二与批次三。跨机契约要同时有本机运行时与中心改造才能端到端打通。

批次五依赖批次四。能力插件的跨进程传输要有可用的跨机通道才能验证。

这条依赖链的形状意味着：最长的关键路径是批次零 → 一 → 二 → 四 → 五，批次三可以插在批次零之后并行。这条并行线值得优先启动。

### 10.3 批次零：钉住来源

批次的产出有三件。来源锁文件记录 rakazo 的主干 SHA、tag、以及 `apps/web`、`apps/api`、`packages/adapters` 三个包的依赖版本【11】【15】【16】。迁移基线记录 fork 当下的数据库结构快照，用于后续比对。fork 骨架是把 monorepo 的工作区配置、包依赖图与构建脚本原样复制过来。

这一步的价值在方案里已经体现过一次：上一轮核对时，主干 SHA 因 TLS 握手失败与 API 速率限制未能取到，导致方案正文无法引用任何 rakazo 的具体版本号【1】。锁文件把这个风险关掉。

批次零还有一个验收动作：来源钉住之后，从正文里抽查十条 file:line 引用，逐条回到对应文件核对行号是否漂移。行号漂移是这类文档最常见的失真源，而在 SHA 钉住之前根本没有核对行号的基准——引用的行号对不对，取决于引的是哪个版本。抽查结果写进批次零的交付说明，漂移的条目当场改并记进变更说明。

### 10.4 批次一：客户端骨架与身份登记

批次一开工前有一个前置决策要先定：打包载体是桌面壳还是本机服务加浏览器。两者对第 9.1 节的口径影响不同——桌面壳里三个进程的生命周期绑在应用上，机器休眠与用户注销的处理也由系统决定；本机服务加浏览器的形态下，服务可以独立于浏览器存活，用户关掉页面不等于进程死。9.1 节“本机进程存活期间”这个承诺的边界，取决于载体怎么定，所以这一条要在批次一动手前先拍。

> **〔2026-11-01 已拍，见修订前言拍板六〕** 载体定为 **dsh / Codex 式 CLI harness**：终端对话入口（CLI/TUI）+ 本机常驻服务（调度器/执行器/插件宿主，可脱离终端存活）+ 本机 Web 控制台（仅回环、Loom 风格中文界面）。"本机进程存活"收窄为**常驻服务进程存活**；CLI 与浏览器只是服务的两层壳，随时可开可关。此口径比原 9.1 节更严格，对用户更有利。

批次一交付四件东西。

客户端骨架是 ms 的最小可运行进程：能启动、能连中心、能显示对话。它复用 rakazo 的 web 包外壳（React 19、Tailwind、oRPC）并把默认装配改成客户端角色【15】。

设备注册走 rakazo 既有的用户设备模型。客户端首次启动生成设备密钥，向中心注册为当前用户名下的一台设备【8】。注册的授权模式由 `USER_DEVICES_ENABLED` 控制，该开关在 rakazo 侧默认开启（`docs/self-host-configuration.md:70`）【4】。ms 的部署向导需要把这个开关显式写出来，因为“桌面端可以让 bot 在用户自己的电脑上跑命令”这句话对用户的安全含义重大【4】。

双主体登记按 5.3 节的划分实现。认证沿用 Better Auth 的口令、通行密钥与组织插件组合（`packages/auth/src/index.ts`）【14】。中心侧不开放自助注册：`signupsEnabled` 置否，`signupAllowlist` 指定允许的用户【8】。

审计的隐私默认值沿用 rakazo 的选择：轨迹记录默认关闭【9】。ms 的部署向导要把“打开轨迹记录意味着什么”写在开关旁边，而不是留给文档角落。

这一批还有一个必须做的核对：部署所有者的概念在 rakazo 里没有对应的角色表，`Actor.isDeploymentOwner` 硬编码为 `false`【12】，而自助注册是可控的（`docs/self-host-accounts.md:13`、`docs/self-host-accounts.md:18`）【5】。ms 需要一个能管理租户的入口。

现成的落点有两个，不必新造：`DeploymentSettings` 上已经有部署所有者标识字段（schema 标注为已弃用，但字段还在）【8】，另外还有一条引导所有者账号的初始化路径，生成的是普通已验证账号、没有服务器权限【5】。方案改为：复用既有字段承载单一部署所有者，另加一个名单字段承载多所有者，并把引导脚本产出的账号显式升格为所有者。

“部署所有者能做什么”要在方案里写死，不能留给实现：所有者可以管理部署设置、邀请与移除用户、调整空间的执行域默认值、查看全部空间的审计；所有者不能代替用户批准计划、不能代替用户确认交付、不能读取用户的会话内容。这条边界与“不做自动批准”那条拍板是同一条线——所有权不等于操作权。

### 10.5 批次二：本机运行时

批次二交付本机侧的三个进程、两个存储、一个派活入口与一处归集约定。

调度器参考 rakazo 既有的唤醒与定时两套机制（`packages/adapters/src/wakeup.ts`、`packages/core/src/cron.ts`）【17】【18】，但落在本机 SQLite 上而不是中心数据库上。触发规则表以数据库为准，重启不丢。

本机队列有两张表：待触发任务表与待交产物表。待交产物表对应 4.4 节的降级独立行为。

本机派活入口是独立形态的落地物。它是一个本机命令，接受一段自然语言或一个模板标识与参数，在本机建任务、立刻执行、返回产出。独立形态的用户不需要中心也能干活，这条路径是唯一的入口，因此它必须在批次二就可用。

本地审计替身用与 Loom 相同的信封形状（第 5.5 节），写本机 SQLite。

归集约定落在客户端一侧：提交目标时在描述文本头部插入固定前缀 `requested-by:<用户标识>`，中心侧据此解析出发起人并落成派生表（5.6 节）。客户端这一侧要做的是前缀写入与用户标识的取值，中心那一侧的派生表属于批次三。

关于“全天候”这个定位，有一条外部参照需要写清楚。dsh 的日程包能力是“会话内提醒、冷会话恢复、没有外部通知通道”【20】，dsh-bot 那种常驻实体的记忆是本机文件树，硬门禁拒绝身份证、卡号、密码与令牌一类内容【29】。ms 的独立形态定位与 dsh 同级，因此 ms 也不承诺外部通知通道，也不把敏感内容过滤作为安全边界——过滤只能降低误触概率，不能替代机器的权限边界。

### 10.6 批次三：Loom 侧改造

批次三有十个子项，其中两个体量大、需要先做可行性探针。

四个小项是接口与字段类。事件出口加游标分页（8.2 节）。租约续租端点把存储层已有的 `renew_claim` 暴露成路由【30】。计划读接口按 `src/loom/workflow.py:290-293` 的返回形状提供状态、修订号与摘要【30】。域包模板补参数契约，参数契约的形状取自工具声明的入参模式（第 7.3 节）。

三个新增项是协议与字段类。副作用登记端点按 8.2 节新建，它是分布式形态下不重放的前提，不能省。执行域策略的两个字段与它们的迁移脚本按 6.2 节落地。发起人归集用的派生表按 5.6 节落地。

一个小项是安全侧：关闭机器批准路径（5.3 节）。验收判据在 11.3 节。

两个大项需要先做探针。第一个是 PostgreSQL 存储适配。Loom 的存储层明说自己是“SQLite 的本地参考实现，不是 PostgreSQL 行级安全或分布式调度的实现”（`src/loom/store.py:1-5`）【30】，而 PG 侧的迁移脚本只覆盖了核心表结构。参照物是 rakazo 侧的两级持久化：本地数据卷承载最新副本，对象存储承载可移植的快照与修订（`docs/self-host-storage.md`）【6】。Loom 侧要达到同等形态，同样需要存储抽象与快照边界两层设计。要补齐成完整的 PG 存储适配，工作量取决于抽象边界是否干净——如果存储访问全部经过一个接口层，适配是机械工作；如果业务代码里散落着直接 SQL，则是一次重写。探针要回答的是这个，答案是“有接口层”或“没有”，不预估天数。

第二个是 Loom 的插件内核与运行预设（第 3.3 节的缺口表最后两行）。这一项属于批次五的承接范围，但探针可以提前做，因为它决定了 RV 执行器以什么方式接入。

这个批次还要处理行级安全的一处细节：rakazo 侧的 PG 部署按 Space 生效行级安全【4】。Loom 侧的租户隔离在 SQLite 阶段靠凭证携带的租户号完成（`src/loom/store.py:1-5`）【30】，迁到 PG 后需要把同样的判定落到数据库层，做到“查询本身就看不到别人的数据”而不是“查出来再过滤”。这是 PG 适配的验收要点之一。

### 10.7 批次四：跨机契约与分布式

批次四把契约面从纸面变成可跑通的链路。

十六个动作里十三个直接用现有接口，三处新增来自批次三（8.1 节）。契约的字段定义沿用 rakazo 的 RPC 契约层【13】，这样 ms 客户端与服务端之间的调用不需要另造一套序列化。

双令牌按 5.3 节落地：两枚令牌绑两个具名主体，主体名带实例前缀。

跨机幂等键按 5.4 节的四段式落地，并在客户端侧加一个防重用检查：同一台机器上两个进程不得生成相同的键前缀。

并发语义有三条要验证：两台 ms 同时领取同一批任务时领取集合无交集（租约与 epoch 保证）；两个人同时批准同一个计划时只有一个成功（修订号与摘要双重校验保证，冲突方收到 409）；两台 ms 同时提交同一任务的产出时只有一次生效（幂等键与 epoch 共同保证）。

分布式形态还有一个必须写进前提的硬约束：中心的并发是有上限的，不是无限的。执行的并发上限默认四个工作位，并且为校验类任务预留一位——业务类任务能占满三个就停，剩下那一位留给校验（`src/loom/approved_execution.py:139`、`src/loom/store.py:122-124`）【42】。也就是说“多机并发提交”在 Phase 1 的真实含义是“多机并发排队，中心按四个工作位放行”。这个上限在界面上要显示当前占用，在文档与部署向导里要写明，调大它要动中心的配置而不是 ms 的代码。

审批侧的跨机语义沿用 rakazo 车队的既有原则：车队写操作永远弹审批卡，自动审阅与永久放行都跳不过（`docs/fleet-management.md:47-50`）【7】。ms 的跨机审批沿用同一条原则，即批量或自动触发的写操作同样需要人确认，不因为发起方是机器而豁免。

还有一条来自 rakazo 的约束要写进 ms 的跨机设计：车队工具绑定在运行所在的空间与账号内，不得跨空间搬运 bot（`docs/fleet-management.md:71`）【7】。ms 的跨机提交因此必须在空间内进行，不能把一个空间的 bot 派到另一个空间的机器上。

### 10.8 批次五：能力插件层与 Loom 自立

批次五是体量最大的批次，包含六个子项。

插件宿主提供两种宿主模式（第 7.3 节）：进程内 TypeScript 插件与进程外 MCP 插件。进程外插件通过标准输入输出通道与宿主通信，协议沿用 MCP——rakazo 侧已有 `McpServer`、`BotMcpServer`、`CapabilityInstall` 三组模型可循【8】。契约本身不新建，沿用 `packages/adapter-kit` 的 provider 契约层并在其上补 ms 需要的实现【34】【35】【36】。

RV 执行器作为一个进程外插件接入。能力声明部分成本低：把 `harness/skills.py:82` 的注册表内容映射成工具声明（名称、说明、入参模式），工具发现与执行两步的接口形状由连接器 provider 规定【31】【34】。执行面部分成本高：RV 的 `AgentSkill` 是规划侧契约，只有 `plan(planner, arguments)` 一个方法，执行由宿主注入的 planner 承担（`harness/skills.py:19-31`、`harness/bridge/execution.py:388-424`）【31】【41】。适配层因此要新增 planner 注入与“路由结果到具体执行”的衔接，以及过程事件到事件流的转换。这一项是批次五里最重的一块，也是 10.1 区间里最不确定的一块。

工作状态机迁移到中心侧（第 7.5 节）。迁移的判据是副作用标记：工具声明的只读标记为否的动作、以及批量动作声明里的每个动作，在中心的副作用账本上单独留痕、恢复时永不重放（`harness/bridge/execution.py:855-856`）【31】。语义与 RV 现有的重复执行防护一致，只是判定的位置从插件侧挪到中心侧。

宿主中介的两项处置落在这一批。凭证路径绊线：对既知凭证路径的中介访问一律拒绝并记审计事件，显式上报、不许静默跳过。联网声明的落地：安装确认界面与调用审计事件都带上这一项，未声明的按可联网处理。两项的实现细节在 7.2 节，风险口径在 3.2 节与 12.1 节。

运行预设把能力组合成可复用的任务模板，模板带参数契约。这个概念正好补上 Loom 域包模板缺的参数契约（`src/loom/domain_packs.py:81`）【30】：预设本身就是一张模板标识到能力名加参数契约的注册表。

Pi 运行时接入需要在中心与本机之间做选择。Pi 的 SDK 边界是 `createAgentSession` 与 `SessionManager`，官方明示“在 Web 服务里还要自行设计每段对话的标识、存储和访问隔离，不能把内存模式误认为已完成多用户持久化”【33】。ms 的本机形态每个实例是单用户单会话，隔离问题简单；中心形态要处理多用户多会话，必须用持久化的会话管理器而不是内存模式【33】。

搬迁的改造面因此可控：rakazo 侧的 agent 运行时已经是一个 provider，接口只有描述、运行与中止三个方法，能力集声明流式、压缩、工具与脚本四项，实现按职责分成会话记录、工具宿主、模型解析、流式回传、错误映射、回退策略与子 agent 等模块【34】【39】。ms 的本机侧要做的是把这些模块装进一个本机宿主并注册到运行时插槽，而不是重写运行时。

Loom 自立形态是这一批的最后一项。Loom 自己要能像 dsh 那样一条命令起本地 Web UI、插件化、有轨迹记录。dsh 的插件元框架与可逆副作用的设计（`docs/computer-runtime.md:34` 提到的容器边界、`docs/self-host.md:80` 提到的 supervisor 结构）可以作为参照【3】。但 dsh 自身的安全状况要写进风险清单：它出现过沙箱自逃逸的公开漏洞，且官方自述没有做过安全审计【19】【21】【22】【23】【24】。这条不构成不做的理由，构成的是“不把 dsh 的沙箱当成可直接复用的安全边界”的理由。

### 10.9 不做什么

每个批次都要有一份“不做”清单，用来防止范围膨胀。六条总计如下。

第一，Phase 1 不做自动路由（第 6.3 节）。第二，Phase 1 不做服务端事件推送（8.2 节）。第三，Phase 1 不做租约续期端点的实际使用，只做端点本身，单任务时长以不超过租约为约束（8.1 节）。第四，Phase 1 不做单用户精简版（第 1.2 节）。第五，Phase 1 不做 Loom 侧模板参数字段的持久化，模板标识进审计链留到之后（第 7.4 节）。第六，Phase 1 不做分布式下的长时间挂起，挂起靠放弃租约实现（第 9.2 节）。

这七条加上第一章的五项决策，构成方案范围的完整边界。

第七条：Phase 1 不做 `MS_ROLE=orchestrator` 这一形态。中心形态的装配开关保留在代码里，但本方案不承诺它的产出——ms 自身作为编排中心的那套服务面不在六个批次的产出清单内，跨机契约也没有为它准备第二种走法。理由是它与 Loom 自立形态在职责上重叠，而后者已经有明确的批次归属（批次五最后一项）。等 Loom 自立形态跑通，再判断 ms 有没有必要再做一套编排中心。

第八条：Phase 1 不引入操作系统级沙箱。可选方案有三套现成的——macOS 的沙箱执行、Windows 的受限令牌、Linux 的 bubblewrap。不做的理由有两条：三平台三套实现，且会破坏合法插件的网络与文件访问；而 Phase 1 的插件是用户自己显式安装的，信任模型等同于装一个软件，沙箱在这里解决的不是主要问题。

这一条的重启条件写死：一旦出现第三方分发的插件形态，或者插件的安装者与使用者分离，操作系统级沙箱从可选升为必选，本条随即作废，回到 13.2 节重议。

## 第十一章 验收判据

### 11.1 判据的设计原则

验收判据要写成机器可判定的形式，且断言落在可观测的产物上，而不是落在内部调用次数上。这一条来自实践：只断言“危险的内层调用没发生”与“状态停在待批准”，会让多种错误实现同时通过。

因此本章的判据统一断言三类可观测量：对外接口的响应内容、持久化存储的最终状态、以及事件流里出现的记录条数与元数据。判据本身不自证充分性——它证明的是“这些已知错误形态被抓住了”，判据够不够由评审方判断。

### 11.2 契约与幂等类判据

这一组判据覆盖跨机契约的行为语义，从接口可用性到并发正确性。

| 编号 | 判据 | 判定方式 |
|---|---|---|
| A1 | 十一个契约动作全部可调用 | 逐个发请求，断言返回码与响应结构符合契约 |
| A2 | 事件出口按游标分页 | 给定游标与限额，断言返回条数等于限额且新游标连续 |
| A3 | 游标语义是每消费者一份 | 两个消费者从同一游标起步，断言各自独立推进 |
| A4 | 跨机幂等键不相交 | 两台 ms 生成键后比对，断言前缀不同且全租户唯一 |
| A5 | 同键不同参数被拒 | 用同键发两次不同参数，断言第二次被拒且不写库 |
| A6 | epoch 栅栏挡下过期执行器 | 用旧 epoch 提交，断言被拒且任务状态不变 |
| A7 | 并发领取集合无交集 | 两台 ms 并发领取，断言领取到的任务标识集合交集为空 |

表中七条覆盖契约面的可用性、分页语义、键空间与并发栅栏。A5 与 A7 是最容易漏的两条——A5 区分“重复提交”与“键冲突”，A7 验证租约与 epoch 组合起来的实际效果而不是各自的局部正确。

### 11.3 主体与权限类判据

这一组判据锁住身份与授权边界，是“不做自动批准”这条拍板的落地检查。

| 编号 | 判据 | 判定方式 |
|---|---|---|
| B1 | 双主体能力集分离 | 断言 operator 主体调用领取接口被拒、worker 主体调用批准接口被拒、operator 主体调用批准接口同样被拒 |
| B2 | 同一主体不得重复登记 | 断言第二次登记同主体身份失败且既有身份文件仍可加载 |
| B3 | 主体不得同时持两个互斥角色 | 断言同时持 operator 与 worker 的登记被拒（`src/loom/auth.py:68`） |
| B4 | developer 主体不得执行批准 | 用旧式密钥派生的主体调用批准，断言被拒 |
| B5 | 批准事件 actor 具名 | 断言批准事件的主体字段不是兜底字面量，且不是空 |

表中五条对应 5.3 节的全部结论。B5 的判定要写成“主体字段等于操作人的具名标识”而不是“主体字段不是空”——空对象被服务端丢弃后落成兜底字面量，只判非空会漏掉这个失效形态。

### 11.4 形态与降级类判据

这一组判据覆盖五种形态里的四种，重点在降级路径能否闭环。

| 编号 | 判据 | 判定方式 |
|---|---|---|
| C1 | 独立形态本机派活入口可用 | 不连中心，直接派活，断言本机产出可读且本机审计有记录 |
| C2 | 中心失联时任务留在本机队列 | 断网后触发，断言任务进入待交队列且未提交 |
| C3 | 中心恢复后可以补交 | 恢复网络后补交，断言中心收到且幂等键不冲突 |
| C4 | 组合形态端到端跑通 | 提交目标、批准、领取、执行、回传，断言事件流里终态标记唯一 |
| C5 | 分布式多机提交互不踩踏 | 三台 ms 并发提交同一工作区，断言各自任务独立完成 |

表中五条覆盖五种形态里的四种（Loom 自立形态的判据在批次五验收）。C2 与 C3 是一对，必须一起验——只验 C2 会让“积压但永远补不回去”的实现通过。

### 11.5 插件与能力类判据

这一组判据覆盖能力插件的契约面与生命周期管理。

| 编号 | 判据 | 判定方式 |
|---|---|---|
| D1 | 参数契约校验拒绝非法参数 | 用违反参数模式的参数发起委托，断言被拒且不提交计划 |
| D2 | 模板标识必填 | 不带模板标识发起委托，断言被拒 |
| D3 | 进程外插件可调用 | 通过 MCP 通道调用一个进程外能力，断言返回结构化结果 |
| D4 | 能力停用不需重启 | 停用一个在用能力，断言新调用不再路由到它且进程未重启 |

表中四条对应第 7.4 与 7.6 节。D1 与 D2 合起来锁住第一条既有拍板（模板化委托、参数校验、机械映射），D4 锁住“能力要能被停用与升级而不必重启整台机器”这句结论。

### 11.6 存储与审计类判据

这一组判据覆盖审计链的完整性与降级补交后的连续性。

| 编号 | 判据 | 判定方式 |
|---|---|---|
| E1 | 事件链校验通过 | 对一段事件序列跑链校验，断言全部连续无断链 |
| E2 | 本机补交后链连续 | 补交本机事件后重跑链校验，断言本机链内序号连续且哈希匹配，断言中心原有链的哈希未受影响 |
| E3 | 发起人可归集 | 提交带 `requested-by:` 前缀的目标，断言归集结果指向正确用户 |

表中三条里，E2 是降级独立形态的闭环判据：补交的不只是“任务到了”，还要保证审计链不断。

### 11.7 安全与隔离类判据

这一组判据覆盖租户隔离与凭据下发的拒绝语义。

| 编号 | 判据 | 判定方式 |
|---|---|---|
| F1 | 非成员访问被拒 | 用非成员身份访问他空间的对象，断言被拒 |
| F2 | 拒绝不泄露存在性 | 断言“对象不存在”与“无权访问”返回相同的状态码与消息 |
| F3 | 旧式密钥不能派生 developer | 用旧式租户密钥请求 developer 角色，断言被拒 |
| F4 | 跨空间提交被拒 | 在空间 A 的客户端向空间 B 提交，断言被拒 |

表中四条对应第 5.2、5.3、10.7 节。F2 的判定要看状态码与消息两者都相同，只看状态码会漏掉消息差异泄露。

### 11.8 安全性质与形态专项判据

前面六组判据覆盖的是接口行为与结构性质。这一组覆盖的是安全性质与形态专项——它们各自只有一条判据，但缺了整条链就没有闭环。

| 编号 | 判据 | 判定方式 |
|---|---|---|
| G1 | 副作用登记与不重放 | 执行器在不可逆动作开始前登记；随后杀掉执行器并让任务重新被领取，断言该动作没有被再次执行，且账本里留有那一行 |
| G2 | 凭证作用域与跨机不外传 | 断言跨机调用只携带带作用域与到期时间的令牌，断言原始凭证不出现在请求体、事件载荷与日志里 |
| G3 | 推送面为零 | 断言中心侧不存在服务端到 ms 的事件投递通道，断言吊销信息只能随轮询响应下发 |
| G4 | Loom 自立形态可用 | 不装 ms，直接用 Loom 自己的界面完成一次从目标到产出的流程 |
| G5 | 中心并发上限可见 | 触发超过四个工作位的排队，断言界面显示占用与排队数量，断言任务不因排队而失败 |
| G6 | 批准主体可判定 | 用实例主体发起批准，断言被拒；用用户会话发起批准，断言通过且批准事件的主体字段等于该用户标识而非兜底字面量 |
| G7 | 等待期的暂停闸门 | 在任务执行中请求人工介入，断言运行状态变为暂停中；断言此时任何执行器领取该运行的任务都被拒；断言租约到期后任务回到待领取但仍不可领；断言恢复后任务才重新可领 |
| G8 | 三处显示的执行域一致 | 同一个 bot 在派活入口、bot 详情、空间管理三处的生效执行域与来源徽标一致，且等于按 6.2 节继承规则算出的值 |
| G9 | 能力安装的披露与凭证路径绊线 | 断言安装确认界面显示能力名称、只读标记与联网声明三项；断言审计事件含这三项；断言对既知凭证路径的中介访问产生拒绝事件且该事件进入审计 |

表中九条各有落点：G1 对应 8.2 节的副作用登记端点与 7.5 节的账本，G2 对应 5.7 节的凭证归属，G3 对应 4.3 节的回传方式，G4 对应批次五的最后一项，G5 对应 10.7 节的并发上限，G6 对应 5.3 节的人类身份通路，G7 对应 9.2 节的暂停闸门，G8 对应 6.3 节的三处显示，G9 对应 7.2 节的联网声明与凭证路径绊线。

### 11.9 判据的覆盖缺口

本章的判据覆盖接口行为、并发语义、形态切换、插件契约、审计链与隔离判定六类。以下四类不在判据覆盖内，需要靠人工评审与代码走查补上。

第一类是性能特征。响应时间、轮询频率这类指标需要压测而不是功能判据。中心的并发上限（10.7 节）有一个例外：它不是性能指标而是硬约束，G5 对它做的是行为断言。第二类是界面体验。等待期的四态表达、跨端同步延迟、断联提示的时机需要人工确认。第三类是异常恢复的完整性。进程被杀、机器休眠、中心重启三种中断下的恢复正确性需要故障注入。第四类是授权文档的准确性。部署向导里的每一句安全承诺都要与代码实际行为对得上，这一条只能靠人读。

第五类是权限判定的读取范围。走查要确认没有任何权限判定路径读取组织级角色——Phase 1 组织层只是结构（5.2 节），一旦有代码去读它，权限模型就出现了第二个维度。

## 第十二章 风险与回滚

### 12.1 风险清单

下表列出十项风险，每项给出触发条件、影响面与缓解手段。

| 风险 | 触发条件 | 影响 | 缓解 |
|---|---|---|---|

### 12.2 回滚策略

四个层级的回滚动作如下。

批次级回滚：每个批次独立提交、独立可部署。批次三的七个子项各自独立上线，存储适配单独成一个里程碑——它的失败不影响游标分页与读接口。

形态级回滚：ms 客户端保留“只读中心”的降级模式，即只读事件与计划、不提交任何写操作。这个模式在批次四出问题或用户不信任中心时可用，实现成本低，因为它只是把提交类调用关掉。

功能级回滚：能力插件层退回进程内构造注入，仅本机能力可用，跨进程能力暂不开放。这个退路的存在依据是 1.4 节的推翻条件——只要所有在用能力都在本机进程内，构造注入的方案仍然完整。

整体级回滚：独立形态本来就是完整的可用形态，中心侧全部不可用时 ms 仍可对话与干活（4.4 节）。这意味着“中心不可用”这个最坏情况不需要额外的降级代码，它是形态设计的自然结果。

### 12.3 不可承诺清单的工程落点

9.4 节的三条不承诺不能只写在文档里，要落到工程上。

第一条“人不在时任务继续跑”的落点是：不引入任何后台推进机制。本机调度器在检测到没有活跃对话时不领取新任务，只保留已触发任务的执行。中心侧的推进不依赖 ms 在线。

第二条“跨会话保持对话上下文”的落点是：等待期结束后不自动注入上一段会话的上下文。需要在会话历史里引用时由人显式引用。

第三条“后台推送批准提醒”的落点是：ms 不注册任何推送通道，中心也不向 ms 推送。全部回传走轮询（8.4 节）。

这一条是主动收窄而不是缺件。rakazo 侧其实有移动推送通道，API 与 worker 通过 Expo 的推送服务向 iOS 与 Android 发通知，访问令牌由服务端持有【40】。ms 不接这一条，理由是不做出网回调这条既有拍板：接推送通道等于中心主动向本机发起连接，与那条拍板冲突，也会推翻本机连接“断线不重试”的治理规则【10】。

### 13.3 与既有拍板的衔接

三条既有拍板在本方案里的延续方式如下。
