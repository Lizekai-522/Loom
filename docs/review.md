## 一、审查结论

**结论：建议退回修订，当前 v2.0 不宜冻结为实现与验收基线。**

事件溯源、显式证据链、验证容量预留、外部副作用不确定态等方向可以继续保留。但方案在验证放行、审计完整性、消息可靠投递、多副本状态、预算封顶与灾备恢复等方面，存在会影响正确性或承诺可实现性的缺陷。

本报告登记 **24 项问题：13 项 P1、11 项 P2**。其中，双签状态放行、审计哈希覆盖范围、可空幂等键、容量判定和收敛语义已通过文档示例的内存反例核对。其余主要是明确的文本矛盾或尚未闭合的设计契约，**不等同于已经在实际系统中复现漏洞**。

用户原请求以“如果没问题”为进入项目推进的条件；本次发现了阻塞问题，因此不启动代码实现或部署。本报告给出可以先执行的设计修订工作包，以及修订通过后的建议实施顺序。

## 三、P1 问题详述与关闭标准

### R01：双签状态判断存在放行漏洞

**证据。** `gate_v()` 使用 `not artifact.dual_sign` 判断是否缺少双签；但 `dual_sign` 是字符串枚举，`pending`、`disputed`、`blocked`、`single` 都是真值。原文函数在证据引用可解析时，对这些状态全部返回通过，见第五节 T01。

**影响。** 如果按此示例实现，要求双签的产物可能在未完成双签或存在争议时通过 Gate-V。

**修订建议。** 强制双签时仅允许明确的成功状态；验证记录必须绑定产物内容哈希、证据版本、规则版本和两位验证者的身份。产物或关键证据变化后，旧签名不得继续使用。区分“证据结构校验”与“双签完成后的最终放行”，明确两阶段状态迁移。

**关闭标准。** 所有非 `signed` 状态均被拦截；缺签、争议、产物被修改、旧版本签名和重复签名都有拒绝用例。

### R02：人工接受形成验收旁路

**证据。** §8.6.3 写明人工“接受”可直接将产物置为 `verified`、Intent 置为 `done`；基准未通过仅需二次确认。该行为与 P3/P4/R4 的“判据不得放宽、验证不能绕过”不一致。

**影响。** 人工确认可以把未满足冻结验收标准的结果计为验证成功，导致成功率与可信度口径失真。

**修订建议。** 明确两类动作：满足判据后的正常验收，以及业务上接受残余风险。后者使用独立状态，例如 `accepted_with_exception`，保留失败判据，不计入正常验证通过。验收标准变化时，新建版本化 Goal/Anchor 并重新验证。

**关闭标准。** 对仍有硬门禁失败的产物，人工操作无法直接产生普通 `verified/done` 成功记录；例外统计与正常成功统计分开。

### R03：规则的表达形式不能证明规则和证据可信

**证据。** §4.5.1 称无副作用表达式“结构上不具备放水能力”，§4.5.5 又承认恒真宽条件可语义放水。示例领域规则直接读取 `artifact.metrics.line_coverage` 等字段，未明确这些数值是否由受信测试执行器产生。复核依赖“与领域语义等价”的内核判定器，而 §10.7 又要求内核判据不含领域语义。

**影响。** 即使 CEL 求值器正确，`coverage=1.0`、`unexplained_failures=0` 仍可能只是未经核验的自报数据。通用结构检查无法替代任意领域结论的语义判定。

**修订建议。** 将内核结构不变量、经授权发布的领域规则、独立评测判据分开。关键指标须来源于受信执行器的证据记录，绑定代码版本、测试集和工具版本；Pack 不能直接写入受信指标。任意新领域的语义判定由独立发布的评测适配器或独立评审者负责，不承诺“通用内核自动拥有等价领域判定能力”。

**关闭标准。** 伪造指标、替换报告文件、规则弱化和证据版本错配均能被识别；独立判定器有清晰来源与发布权限，接入方式不与领域中立要求冲突。

### R04：哈希保护范围不完整

**证据。** 哈希输入只有前序哈希、`payload` 和 `submission_key`，未包含 `type`、`actor`、`tenant_id`、`run_id`、`chain_id`、`seq` 等事件元数据。内存反例表明，将事件从 `gate.failed` 改成 `gate.passed`，并修改操作者，示例哈希完全不变，见 T03。

**影响。** 审计事件的实际含义或责任人可变化，而示例校验无法发现，不能据此满足“任意篡改可检测”。

**修订建议。** 定义版本化、规范编码的完整事件信封，将身份、归属、类型、顺序、载荷摘要与前序摘要一并认证；定义链起点、结束标记、事件数量、跨链引用和截断检测规则。

**关闭标准。** 对每个受保护字段单独篡改均能检出；重排、删除、复制到其他 run、截断链尾也有验证用例。

### R05：异步补链协议未与数据结构和不可变性统一

**证据。** `event.hash` 是 `NOT NULL`，但 §4.8.2 又规定先写事件、异步补链，补链前为 `pending_chain`；DDL 没有该状态及配套流程。若补写回原表，又需要解释如何维持 append-only。`submission_key` 可空，但哈希函数无条件调用 `.encode()`，空值会报错，见 T04。签名在链结束时生成，外部锚定每日执行，长运行与未补链窗口如何保护未定义。

**影响。** 当前方案无法直接确定事务提交时哪些数据已受认证保护，以及补链前数据被改动时如何发现。

**修订建议。** 优先对“事务内计算完整事件摘要，链头异步签名”做基准验证，再决定是否确需异步补链。若保留异步方案，应将原始事件与追加的认证记录分离，定义待认证期间可见性、发布限制、故障恢复、单链顺序及周期检查点。统一空幂等键的编码规则。

**关闭标准。** DDL、追加协议、恢复协议一致；空幂等键正常处理；补链前后崩溃、长 run 和链尾丢失都能受控恢复并验证。

### R06：提交后发布仍可能永久丢通知

**证据。** §5.1 在数据库事务提交后直接 `bus.publish(receipt)`。进程若在提交后、发布前崩溃，事件已存在，通知未发出；同键重试又可能直接返回旧回执，仍不发布。§5.3 的本地重试队列不能覆盖进程丢失。幂等检查在事务外执行，也未给出并发唯一键冲突后的回执读取协议。

**影响。** 任务可能已经提交却无人派发；相同请求并发到达时，结果或错误语义不稳定。

**修订建议。** 在同一事务持久化事件、回执与 outbox；由可恢复发布器向 JetStream 投递并记录进度，消费方按持久化键去重。也可采用具备持久游标与恢复扫描的事件日志投递器。请求摘要应覆盖操作类型、目标资源、版本及规范化参数。

JetStream 提供已投递消息的持久化及至少一次交付；它不能替代应用数据库到消息系统之间的事务桥接。[NATS 官方说明](https://docs.nats.io/concepts/jetstream)

**关闭标准。** 在数据库提交后、消息发布前强制退出，重启后任务仍被派发；重复通知只生效一次；同键并发同参返回同一回执，同键异操作或异参被拒绝。

### R07：内存计数不能独自承担多副本全局权威

**证据。** 生产拓扑有 N 个控制面副本；热路径计数由各调度器内存同步增减，30 秒与 claim 表对账。方案未说明分片所有者、领导者选举、跨副本容量预占及故障接管顺序。claim DDL 也未展示“一个任务至多一个有效 claim”的数据库约束或 CAS 协议。

**影响。** 两个副本可能同时依据各自余量派发，产生超配、重复认领或计数双扣减；事后对账无法阻止当时发生的越限。

**修订建议。** 明确调度分片与单写者边界；共享 Agent/验证池的容量由可原子预占的账本控制。claim 发放、epoch 更新与所有权判断必须有数据库原子协议。内存状态可以用于快速计算候选集，但需明确其授权边界。

**关闭标准。** 双调度器竞争、网络分区、旧领导者继续运行、接管时重放等场景下，有效 claim 唯一且全局容量不超限；重启时先完成权威状态重建再开放派发。

### R08：容量函数无法表达验证预留

**证据。** `can_dispatch()` 的第一分支在 `verify_live < cap_verify` 时直接返回真，函数没有任务通道参数。业务 Worker 已达 200、验证为 0、预留为 40、总上限为 200 时，原函数仍返回真，见 T02。

**影响。** 若调用方没有额外且正确的通道限制，业务派发也可走验证余量分支。当前函数本身不能证明业务不会挤占验证资源。

**修订建议。** 输入明确的通道类型；分别校验业务上限、验证上限和总资源上限，并原子预占。区分“验证最低保留量”和“验证最大容量”，定义是否允许借用及收回。

**关闭标准。** 业务满载时业务请求被拒、验证仍能获得其预留；总容量始终不超过声明上限；验证排队时不会继续向业务借出预留。

### R09：成本封顶缺少原子预留与最坏计费上界

**证据。** NFR-020 要求实际成本不超过声明上界，而 §6.4.1 仅在调用前“预估”单次成本，run 级累计又被标注为软观测。多个并发调用可读取同一剩余额度；输出、推理 token、重试及中断后继续计费的处理未定义。

**影响。** 每次调用前检查仍可能发生并发超支。“超限后一次调用内熔断”不能同时证明此前从未超出硬上限。

**修订建议。** 建立 run/任务共享的原子预算预留账本，调用前按可强制的最大计费量预留，完成后结算并释放。计入规划、验证、修复、采样及可能收费的失败请求。不能给出可执行最大计费上界的提供方，应明确使用软预算口径。

**关闭标准。** 多任务同时竞争最后额度、超时重试、流式输出中断、验证追加采样等情况下，所有预留与结算都满足预算不变量；成本承诺区分硬上限与估算值。

### R10：副作用安全需要覆盖旧 Worker 和记录丢失

**证据。** epoch 校验主要约束平台提交，尚未明确出口网关是否在真正调用外部系统前校验有效 claim、唯一调用标识及调用权限。NFR-008 允许事件日志 RPO 最多 5 分钟，但副作用恢复表把“无 intent”视为“未发起”。

**失败场景一。** 旧 Worker 租约到期后仍在运行，外部动作已经发生，即使其最终提交被拒也无法撤销动作。

**失败场景二。** `tool.intent` 已提交后执行了外部写；灾备恢复丢失最近日志，恢复端看不到 intent，可能再次发起。

**修订建议。** 出口网关按稳定 `call_id` 原子控制发起权，并校验 claim/epoch；禁止传输层对非幂等写进行透明重试。外部动作开始前，发起记录须达到设计要求的持久性等级。对可能丢失记录的恢复窗口，默认冻结相关写操作并核对独立账本或外部系统，不能直接判为“从未发起”。工具幂等键契约还需定义作用域、参数绑定和去重有效期。

**关闭标准。** 旧 Worker 继续执行、请求已送达但响应丢失、数据库主备切换及恢复到动作前时间点时，均不会由平台自动重复发起不可安全重放的动作；保证范围与 NFR-022 一致。

### R11：图状态回退不等于执行效果回退

**证据。** §4.6.2a 将 `graph.reverted` 描述为“无需补偿逻辑”。§4.2.4 又要求上游回滚后下游标记 `stale`，但没有完整的依赖传播、在途取消、签名作废或已发生外部效果处理协议。

**影响。** 图显示已经回退，后续产物、正在执行的任务或外部系统仍可能保留旧效果。

**修订建议。** 分开定义投影回放、工作流回退、产物失效和外部补偿。修复事务应带目标图版本，校验无环与前置版本；回退后撤销相关执行权限，传播下游失效，并保留外部效果的独立状态。无法补偿的效果显式转人工。

**关闭标准。** 已有下游产物和在途写操作时执行回退，不会继续使用失效证据或旧签名；补偿失败可见，不能因图回退而将外部效果记为已撤销。

### R12：租户隔离设计尚不能据 DDL 直接验收

**证据。** `artifact`、`observation`、`execution_claim` 未直接包含 `tenant_id`，部分引用只有单列 ID，未提供经 `run` 关联的完整 RLS 方案和同租户引用约束。缺少直接租户字段并不自动构成漏洞，但当前材料不能证明隔离成立。§7.3.1 一方面要求审计角色仅见授权范围，另一方面赋予其 `BYPASSRLS`。

`BYPASSRLS` 会绕过行级策略，表所有者通常也会绕过，不能同时依靠同一套 RLS 限定审计范围。[PostgreSQL 16 官方文档](https://www.postgresql.org/docs/16/ddl-rowsecurity.html)

**修订建议。** 统一租户/run 归属模型，使用直接字段或可验证关联策略，并约束跨表引用的归属一致性。业务连接使用非 owner、无绕过权限的角色。审计通道选择“受 RLS 限制的角色”或“特权服务加独立强制授权”之一，明确权限边界。对象存储下载、证据解析和队列消费也需校验租户归属。

**关闭标准。** 两租户交叉引用 ID、下载对方对象、复用 claim、审计越范围查询均被拒绝，且测试使用真实应用数据库角色而非超级用户。

### R13：停滞不能被解释为验收成功

**证据。** 收敛函数只检查最近产出和连续空闲，不检查验收判据，甚至不使用 `intent` 参数。未满足验收的任务连续两轮无产出时，也返回 `ConvergeResult(True, "threshold_met", ...)`，见 T05。正文 1383 行将该状态解释为“真正的问题解决”。

**影响。** 若上层把该结果映射为成功终态，会将持续失败或无进展误记为成功。

**修订建议。** 拆分 `succeeded`、`stalled`、`budget_exhausted`、`awaiting_human`。只有冻结验收判据全部通过才能成功；停滞只是停止自动尝试的条件。产物哈希只能去除字节相同内容，不能证明语义进展；阈值还需上下界和全局预算约束。

**关闭标准。** “连续无产出且验收失败”只能进入停滞/失败/人工路径；产生不同字节但无有效进展的产物不能无限推迟终止。

## 四、P2 问题与修订要求

### R14：Gate-P 的确定性要求自相矛盾

§4.3.2 用“启发式 + LLM 辅助判断”判断唯一子目标；§10.2 又要求门禁函数不含 LLM 调用。用标题中是否包含“和/以及”判断目标数量，也会误伤正常任务。

**要求：** 用结构化目标、输出契约和范围字段执行确定性门禁；LLM 可提供拆解建议，建议不能直接成为硬门禁真值。验证门禁不依赖标题措辞。

### R15：不可变性需要明确对象、主体和版本

CN-005 与 P6 将阈值和判据定义为编译期常量，但 Pack manifest 又携带阈值、规则与排除清单，并支持热加载；FR-040 要求出口策略即时生效。§5.4 的内容型 Anchor 存储与 §11.4 的编译期 Anchor 表述也不一致。

**要求：** 明确内核最低安全约束不可由运行主体降低；领域规则由有权限的发布者版本化发布；run 绑定不可变规则快照。说明哪些紧急收紧可立即作用于在途 run，哪些变更只影响新 run，避免把所有配置都称为编译期常量。

### R16：补全可执行数据与状态契约

主要缺口如下：

- `intent.from_facts` 为 `UUID[]`，`observation.id` 为 `BIGSERIAL`，Fact/Observation/Artifact 的统一引用类型未定义；“非空”又与默认空数组缺少强约束相冲突。
- DSL 使用 `depends_on`，修复支持改边，但未给出依赖边表、图版本和无环校验契约；首个 Intent/Task 的支撑事实如何创建也未说明。
- 每个 Intent 一个 owner 与同一 Intent 下并行 Task 的执行所有权关系需要明确；Reasoner 并行提议也需区分协调者与提议子任务。
- Task 的状态注释未包含正文使用的 `stale`、`indeterminate`、`rejected_by_gate` 等状态，合法迁移和终态定义缺失。
- per-run `seq` 声称连续且唯一，但示例未给出对应唯一约束及并发分配机制；`severity`、`verification_required` 等验证字段也未进入完整模型。

**要求：** 给出带版本的事件 schema、状态迁移表、引用模型和核心 DDL；对同租户/run 引用、有效 claim、序号唯一及图无环建立可执行约束。若 DDL 仅为示意，应明确哪些规范另文提供，避免将节选直接当实现基线。

### R17：机制测试与业务收益评测需要分开

Canonical 场景主要检查状态机、门禁、租约和幂等，能证明机制行为，不能单独证明复杂任务成功率、人工返工下降或单位成功成本优于单 Agent。§1.7 包含人工基线，§6.3 的端到端基线改为广播式调度，也缺少完整对照映射。

**要求：** 保留平台一致性测试；另设独立持有的领域 held-out 效果评测，由独立判据判断业务结果。对照组使用相同任务、模型资源与成本核算口径，报告人工工时、失败、超时、策略拒绝和基础设施故障。条件正确率与端到端完成率分开，避免排除网络故障后掩盖实际完成能力。

“2–5 倍成本”“首次通过率上升”等目前应标为待验证假设。CAIRN 原论文也报告低工作量任务可能增加 token 成本却没有可观察收益，支持先按任务复杂度分层验证。[CAIRN 原论文摘要](https://arxiv.org/abs/2609.32700)

### R18：抽样复核需要选定放行时序与统计规则

§4.5.5 同时写“同步执行”“不阻塞主流程”“结果异步回写”。偏差超阈值在不同章节分别触发 P1/P2、立即暂停/连续两次暂停；小于 30 个样本不判定也未说明冷启动风险。

**要求：** 被抽样的关键产物应在复核完成前维持不可交付状态；若选择事后监测，应明确其存在风险窗口。统一统计窗口、分母、最低样本、置信区间、告警和恢复条件。高风险错误可单次阻断，不能全部等待总体偏差超过 2%。

在独立同分布假设下，30 个样本零偏差时，单侧 95% 偏差率上界仍约为 **9.50%**，不足以证明真实偏差率不超过 2%。若要求零偏差样本的该上界不超过 2%，至少需要 **149** 个样本；1% 抽样下约需 14,900 个通过产物才能期望累积到该数量。该计算用于说明样本量要求，不是对真实系统样本独立性的认定。

### R19：回放与重新执行的承诺需拆开

“同输入复现同轨迹”“给定种子和模型版本完整重放”没有区分读取历史事件与再次调用外部模型。§4.7.4 对幂等工具允许恢复重试，也不能用于解释无副作用的审计回放。

**要求：** 历史回放只消费记录，禁止模型调用和工具写操作；恢复执行另设授权与副作用判断。完整重建应保留模型/工具请求响应、提示词与上下文版本、Pack/规则版本及对象摘要。重新推理只能在所声明条件下追求统计可复现，不能单凭随机种子承诺同轨迹。补齐事件、Observation、产物及冷存储的联合保留期与缺失处理。

### R20：上下文预算与经验条目准入需补边界

C1 要求所有祖先产物和观测必留，C4 又允许超预算裁剪，未定义必留内容本身超过模型窗口的情况。小图中全部内容都是必需项时，token 比例也可能达到 100%，不能无条件满足“≤40%”。经验条目需先被两个不同 run 引用才允许进入召回，但尚未说明最初两次引用的受控来源。

**要求：** 区分必须保留的引用/摘要与可按需读取的正文；预算不足时拆任务或明确失败，不能静默丢判据。限定 token 降幅指标的适用样本并同时验证质量。经验条目先经审核进入试用层，再依据独立 run 的结果晋升，明确 held-out 不流入经验库。

### R21：阶段依赖与验收口径需重排

M2 要求 §10.2 全部不变量通过，其中副作用与多租户等能力却安排在 M3；Canonical 基准套件到 M4 才出现，前期已有依赖它的验收。两个参考 Pack 被写为 v1 交付，第二个又在 M4。

NFR-016 要求鲁棒性保持率不低于 85%，极端规模场景却接受 80%；FR-020 的事件推送延迟引用了任务派发 NFR；500 个 run 各有 20 个“活跃任务”与 200 Worker 的关系未区分排队和执行。若 2,000 events/s 持续 180 天，将达 **311.04 亿条**事件，峰值吞吐、平均负载、存储容量与重建时间需要分别建模。

**要求：** 把测试框架、权威状态、基础隔离和副作用协议前移到其首个使用阶段。逐条为 NFR 定义测量起止点、负载、硬件、样本、分母与通过阈值。团队、预算和现有资产不明，当前不宜给出确定工期。

### R22：ADR 与需求引用需要机械校验

§9.1 的 ADR-001 是“不用独立图数据库”，§12.4 的 ADR-001 却是“事件日志唯一真相源”；ADR-004 在两处分别指 A2A 与分链审计；§9.1 列到 ADR-010，§12.4 只到 ADR-008。§1.2.1 多个 NFR 引用也与实际含义不符，例如把多租户指向事件吞吐编号。

**要求：** 建立唯一 ADR 索引，正文引用自动解析；逐条校验 FR/NFR/CN/ADR 的存在性、唯一性、含义及追踪关系，补齐失效章节引用。此项可作为最先关闭的低成本工作包。

### R23：数据结构与注册表不是完整安全边界

代码、报告、摘要、schema 字符串与证据正文仍能携带提示注入，传递引用并不消除接收方读取内容时的风险。§9.1 的“进程内注册表”也没有说明包含可执行薄工具的 Pack 是否会把第三方代码载入可信控制面；仅约定“不能访问内核结构”不能约束同进程代码。

**要求：** 将模型建议与实际操作授权分开，在工具和状态变更点强制鉴权、范围及预算校验。声明式 Pack 与工具执行镜像分开发布；不可信工具放在隔离进程/容器，不能因注册成功获得控制面内存或数据库权限。常驻执行器复用还需定义跨租户清理与隔离规则。

### R24：任务优先级需要进入任务选择队列

对同一个 Task 比较候选 Agent 时，`priority_weight(task.priority)` 是对所有候选者相同的加数，不会改变候选 Agent 排序。因此仅凭此打分项不能满足 FR-014 的任务优先级派发要求。

**要求：** 先按依赖就绪、任务优先级、等待时长和租户公平性选择任务，再对候选 Agent 打分。增加优先级更新、低优先级防饥饿及多租户公平性的用例。

## 七、建议推进顺序与工作包

当前可以推进的是设计修订与验证策划。以下为建议工作分解，尚未分配实际人员、创建项目任务或执行实现。负责人仅指角色；没有团队配置与现有资产信息，不作日历工期承诺。

| 阶段 | 交付物与工作包 | 建议负责角色 | 进入下一阶段的条件 |
|---|---|---|---|
| S0 设计修订 | 统一成功/停滞/例外状态；确定规则与证据信任模型；确定事件、outbox、claim、预算和副作用协议；修复 ADR 与需求引用 | 架构负责人、平台后端、安全评审角色 | R01–R13 有明确决策、契约和可执行反例；P2 均有处理归属 |
| S1 最小确定性内核 | 以合成任务跑通 Goal→Intent→Task→Artifact；实现持久事件、outbox、基础投影、claim/fencing、Gate-P/V、预算预留、租户边界；保留必要的业务/验证两类容量 | 平台后端、测试角色 | 不使用 LLM 也能完成正常链路、回放、拒绝路径；关键正确性用例通过 |
| S2 故障与副作用验证 | 使用本地桩模拟外部写；覆盖提交后崩溃、重复消息、旧 Worker、部分响应、回滚及恢复记录丢失；接入独立签名记录与人工队列 | 平台后端、测试、SRE 角色 | 单机和多副本故障矩阵通过；无未经确认的自动重复写；不确定态挂起有效 |

2. **受信证据及规则发布契约：** 谁能写指标、谁能改规则、谁持有评测判据、验证绑定哪些版本，关闭 R03/R15/R18。

### 首批必须保留的验收场景

| 场景 | 必须观察到的行为 |
|---|---|
| 要求双签但状态为 pending/disputed | 不能进入正常验证成功或交付状态 |
| 基准失败时人工点击接受 | 保留失败事实；只能按明确例外流程处理 |
| 提交成功后、消息发布前进程退出 | 重启后仍能派发，重复投递不重复生效 |
| 两个调度器争抢最后容量/预算 | 仅允许满足全局约束的预占成功 |
| 旧 Worker 在租约失效后继续请求外部写 | 出口不能授予新的有效发起权 |
| 外部写已发生，响应或近期日志丢失 | 标记未知并核对，不以“无记录”直接自动重做 |
| 图回退时存在下游已验证结果 | 依赖结果和签名失效，在途任务被隔离或取消 |
| 两租户复用他方资源 ID | 数据、证据、对象与 claim 均无法跨租户使用 |
| 连续无进展但验收未通过 | 停滞/升级人工，不标为成功 |
| 事件 type/actor/seq 等被修改或链尾被截断 | 完整性验证失败 |
