# Loom 实施路线与阶段验收计划

记录日期：2026-10-22（Asia/Shanghai）。依据 Loom 技术方案 v2.1 修订方向及审查报告 R01–R24，服务于已启动的本地确定性内核建设。

## 当前项目状态

项目已从纯方案进入 **S1 本地参考内核开发与验证**。当前有 FastAPI API、SQLite 持久存储、确定性策略函数和针对关键不变量的测试源码。方案文本修订、单机参考实现与生产系统验证是三种不同交付，不能相互替代。

- **设计修订：** 桌面 Loom.md 已按 R01–R24 修订为 v2.1 实施基线候选；文字改正不表示架构复审或生产验收通过。
- **本地已实现源码：** `src/loom/store.py`、`src/loom/policy.py`、`src/loom/api.py`。下文逐项说明实现范围，不把尚未运行的生产检查计为通过。
- **测试状态：** 已有策略、存储和 API 测试；具体通过数与命令以本轮主执行者最终测试记录为准。存在测试文件不等同于相应用例已经全部通过。
- **生产待验证：** PostgreSQL/RLS、NATS、OIDC/RBAC、真实模型网关、沙箱/出口网关、签名服务、真实写操作故障恢复与容量/SLO 都没有因本地代码出现而完成。

依赖复用取舍见 [GitHub 复用记录](github-reuse.md)，已安装依赖的归属见 [第三方声明](third-party-notices.md)。本轮以 FastAPI/Pydantic 实际构建接口和契约，没有把 Temporal、LangGraph 或 NATS 写成已接入能力。

## 本轮环境限制与处理

| 已知条件 | 当前处理 | 后续进入条件 |
|---|---|---|
| 本轮尚未接入并验证项目模型凭据 | 正常链路使用确定性 fixture；不宣称真实多模型协作、双模型效果或计费封顶已实测 | 配置明确的模型提供方、模型版本、密钥注入与任务预算，再执行小额受控联调 |
| 环境检查时 Docker Linux daemon 不可连接 | 本地 SQLite 适配器推进事件/事务/状态语义；不把 PostgreSQL DDL 或容器配置文件当运行成功，不执行未隔离的模型生成代码 | Docker 或等价容器运行时可用后，启动隔离 PostgreSQL/NATS/Worker 环境；S2 最小沙箱/出网/凭据隔离实测通过后才能执行生成代码 |
| 本轮为单主机 SQLite | `BEGIN IMMEDIATE` 串行事务作为一致性参考；数据库保存容量设置避免同库实例配置漂移 | PostgreSQL 原子预占、claim 争用、多副本接管和分区故障测试通过 |
| HTTP API 使用租户 Bearer key | 仅适用于本地受控开发；接口不得暴露真实写操作及可自报通过的验证完成入口 | OIDC 主体、角色和资源授权落地，验证服务与 Worker 使用不同权限 |
| 没有真实外部写执行器 | 只记录发起/完成/不确定态，使用受控桩观察调用行为 | 出口发起权、幂等键契约、记录持久性、人工核对与灾备冻结策略验证完成 |

不承诺固定日历工期。排程依据依赖、团队投入和每阶段可复核的出口推进；基础设施暂不可用不应导致把参考适配器改称生产实现。

## R01–R24 关闭追踪

“本地覆盖”表示已可从源码检查相应机制；最终关闭需要相应测试证据。生产列出的工作仍然保留，不能因本地用例通过而删去。

| 审查项 | 本地源码覆盖 | 继续关闭所需证据或生产差距 |
|---|---|---|
| R01 双签放行 | `policy.gate_v` 只接受明确成功状态，核对内容/规则/证据版本及独立身份；`Store.complete` 绑定任务尝试和产物哈希 | 真实受信签名验证器、模型身份/能力档位认证；禁止把模型字段复制为 `authenticated=True` |
| R02 人工旁路 | `policy.manual_accept` 区分普通成功、例外接受和驳回，例外不计正常成功 | 持久裁决事件、职责分离授权、双人高风险审批及控制台；纯函数不是已上线人工流程 |
| R03 可信指标/判定器 | 类型化产物、证据受信标志与规则版本约束 | 受信测试执行器、证据签名/来源、独立领域判据与模型结果认证；布尔标志本身不是信任根 |
| R04 完整事件哈希 | `Store._event` 摘要覆盖完整事件信封，`verify_events` 验证链身份、序号和前序摘要 | 独立持有的链头/数量检查点、签名服务、外部锚定，才能证明截断与全库重写被检测 |
| R05 补链/不可变性 | 事务内计算摘要，事件表拒绝 UPDATE/DELETE，空命令键可编码 | 生产数据库权限与触发器、长期签名检查点、密钥轮转及校验恢复 |
| R06 投递/幂等 | 事件、回执、outbox 在同一事务提交；支持持久 inbox 去重与 outbox drain | 真实 JetStream durable ack、并发发布者、确认丢失和进程退出集成；回调桩不等于消息系统实测 |
| R07 全局权威状态 | 同一 SQLite 数据库下原子认领/计数，epoch 与租约校验 | 多主机数据库事务、调度分片所有权、旧领导者隔离、全局/租户配额与接管协议 |
| R08 验证容量 | `claim_next` 分开限制业务与总容量，预留验证槽 | 验证通道主体授权、全局容量压力和扩缩容；租户 key 当前不是生产 Worker 角色 |
| R09 预算硬界 | `reserve/settle` 在事务中竞争额度，金额使用整数微美元；结算超预留会记录并挂起 | 真实提供方最大计费量约束、流式/推理 token 上界、失败计费、超时请求对账与取消语义 |
| R10 副作用安全 | 稳定 operation ID、唯一发起记录、claim 校验；租约过期把未知效果挂起 | 网关实际发起权、禁止透明重试、独立账本/RPO 窗口冻结、人工核对、部分完成恢复 |
| R11 回退/失效 | `invalidate` 传播下游 stale、递增 epoch、记录外部补偿需求 | 撤销真实在途动作、补偿/不可补偿结果、重新规划及原子版本冲突；记录事件不代表补偿完成 |
| R12 租户隔离 | API token 绑定租户；Store 查询与复合键约束包含租户 | PostgreSQL RLS 使用真实业务角色、审计授权、对象下载权限、租户凭据与队列隔离 |
| R13 停滞/成功 | `classify_progress` 区分验收成功、停滞、预算耗尽和运行中；`finish_run` 需全部任务通过及冻结判据满足，演示中持久化成功终态 | 完整 Intent 终态、人工/停滞路径与统计；不能把 `task.completed` 自动外推为整个 Goal 成功 |
| R14 确定性 Gate-P | `gate_p` 使用结构化契约及受信 scope/anchor/criterion 集，无 LLM 判断 | 真正的任务书 DSL/注册表；本地 `local-fixture` 作用域不能代替实际仓库范围授权 |
| R15 冻结规则边界 | run 保存规则版本；产物签名绑定版本 | 版本化规则注册表、发布授权、允许收紧的在线策略与在途版本兼容；任意字符串名称不是已发布规则 |
| R16 数据/状态模型 | root Goal/Intent 事件、任务依赖及部分状态迁移、租户/run 边界 | 完整 DSL、边版本、子工作流、修复计划、迁移脚本与规范 schema；本地模型是明确子集 |
| R17 效果评测 | 本地不变量测试可验证机制 | 独立 held-out 领域评测、单 Agent/固定流程对照、任务分层、人工返工与单位成功成本 |
| R18 抽样复核 | 尚未实现产品抽样引擎 | 高风险同步不可交付状态、独立判定器、样本量/置信度/告警/恢复统一规则 |
| R19 回放边界 | `replay` 只消费持久事件，不调用模型或工具 | 所有投影字段等值性、对象联合保留期、缺失/损坏处理、独立检查点；重新执行不能承诺模型同轨迹 |
| R20 上下文/经验 | `assemble_context` 保留必需项、超预算明确报错并返回丢弃项 | 实际 tokenizer、证据按需加载、检索和经验试用/晋升，验证裁剪后的质量 |
| R21 阶段/指标 | 本路线前置确定性测试与故障验证，使用可测出口 | 硬件/平均与峰值负载、统计分母、指标起止点、存储保留容量及 SLO 实测 |
| R22 ADR/引用 | 由方案修订与审查对照表统一编号和引用 | 将唯一性/存在性/追踪完整性机械检查接入 CI；不以手工文字检查长期替代 |
| R23 安全隔离 | API 不执行真实外部写、不提供 Worker 自行验证成功入口 | 受信执行器、容器沙箱、出口鉴权、提示注入对抗、复用工作区清理与供应链固定 |
| R24 任务优先级 | Store 优先级队列；`select_task` 与 `select_agent` 分离，纯函数具备 ageing 逻辑 | 将公平/老化策略接入持久调度路径，验证优先级更新、租户公平和防饥饿 |

## 阶段依赖与可测出口

路径为 **S0 → S1 → S2 → S3 → S4**。S0/S1 中互不冲突的文本修订、类型契约与测试可以并行；真实模型与外部动作的开放必须等待其依赖机制通过。

### S0：设计契约与审查修订

交付：v2.1 候选方案、24 项修订对照、唯一 ADR 索引、事件信封/状态机/预算/副作用决策表及本路线。

出口：

1. R01–R13 的设计决策明确，成功、例外、停滞、未知态互不混用。
2. R14–R24 均有处理方式、所属模块及可测验收，不再保留互相矛盾的承诺。
3. 规范区分本地适配器和生产契约；指标的分母、负载与起止点可执行。
4. 核心拒绝路径先形成测试；文本已修订与系统已验证分开登记。

### S1：单主机确定性内核

依赖：S0 核心状态和信封契约。

交付：单机 SQLite 适配器、API、结构化任务书、Gate-P/V、事件/回执/outbox、claim/epoch、通道容量及预算预留；提供不需要模型密钥的正常/拒绝路径演示。

出口：

1. API 可创建 run/任务、认领与提交；OpenAPI 正常生成，租户 token 和幂等键作为预期 Header 工作。
2. 同键同参取回同一回执；同键异参/异操作拒绝；并发请求不能重复创建状态。
3. 已提交输出保持 `submitted`，不因 Worker 自报完成而打开下游依赖；只有受信验证入口才能完成验证。
4. 非成功双签、旧版本签名、过期 claim、跨租户资源 ID 被拒绝。
5. 业务满载时验证预留仍可用；并发预算预留不超过本地账本余量。
6. 持久投影与纯回放对照至少覆盖任务提交/拒绝/重试、预算、失效和未知副作用；字段差异必须修复或明确超出当前子集。
7. 文档运行命令在干净本地数据库中实际执行，并保存测试与演示结果。

### S2：故障矩阵与真实基础设施适配

依赖：S1 的事件/outbox/claim/预算契约。Docker 或等价容器运行时可用后引入隔离 PostgreSQL、NATS 和最小代码执行沙箱；在此之前可先用本地安全桩实施故障注入，但独立记录结果，不运行未隔离的模型生成代码。

交付：生产数据库迁移与角色、JetStream 适配器、受信网关接口、持久化人工队列及恢复决策矩阵；同时前置交付首次代码执行必需的最小沙箱、出网 scope 限制、任务凭据隔离和受信测试报告来源校验。S4 继续生产隔离加固，不承担首次引入隔离。

出口：

1. 数据库提交后、发布前退出可恢复；broker ack 后本地标记前退出允许重投，但消费者只应用一次。
2. 两个调度实例竞争同一任务、最后容量及最后额度时，全局不变量成立；旧实例不能继续取得新发起权。
3. 外部写桩在发起前/已送达/响应丢失/完成记录前分别退出，产生正确的未发起、已完成或不确定态。
4. 恢复到可能丢失发起记录的时间点时，写动作被冻结并核对；不能把“无记录”直接解释为“未执行”。
5. PostgreSQL 集成测试使用真实受限角色，覆盖跨租户引用、RLS、审计范围与对象访问。
6. 独立链头/事件数检查点能够发现截断，不能只复算当前数据库后返回 `valid=true`。
7. 最小代码沙箱验证只读根、任务专用可写区、非特权执行与资源限制；越界读取、未授权出网和跨任务残留状态不可使用。测试使用隔离环境中的受控样本，不以宿主进程直接运行生成代码。
8. 工具/模型调用只取得任务所需凭据，不能读取其他任务或租户凭据；受信测试报告来源、代码/测试版本和内容摘要均可验证。上述隔离与来源检查未通过前，不进入 S3 的模型生成代码执行。

### S3：首个 software-dev 场景与收益证据

依赖：S1/S2 相关安全与持久化检查，尤其 S2 最小代码沙箱、出网 scope、任务凭据隔离及受信报告来源实测通过；真实模型联调另需提供方配置和预算。不能因仅运行在本机便跳过执行隔离。

首个场景采用受控 fixture 仓库的小型软件修改：输入冻结需求和可执行验收用例，按“需求解析 → 实现 → 独立测试/复核 → 报告”形成结构化证据。先用确定性执行器演示状态链路，再增加真实模型；不要求第一轮就开放任意仓库写权限。

交付：精简 `software-dev` Pack、版本化验收/测试集、受信测试结果、独立验证与失败修复分支。

出口：

1. 相同输入与 fixture 可演示通过、测试失败、补证、旧签名拒绝、预算耗尽和人工例外。
2. 真实测试结果由受信工具生成，绑定仓库版本、任务尝试、测试集与产物摘要；模型不能直接填写受信覆盖率和通过标志。
3. 真实双模型仅接收允许的原始证据，身份由网关确定；没有两个模型时明确挂起，不能用固定布尔桩宣称双模型完成。
4. 独立 held-out 场景按难度分层，和单 Agent、固定流程使用可比任务与资源；报告失败、超时、人工工时和总成本。
5. 如果复杂编排没有证实收益，调整适用任务和流程规模，不能用内核单元测试通过替代业务效果结论。

### S4：生产化与第二领域验证

依赖：S2 故障与隔离矩阵、S3 场景效果、基础设施和团队运维责任。

交付：OIDC/RBAC、独立 Worker 身份、沙箱/出口代理的生产隔离加固、审计签名、告警/Runbook、备份恢复、压测与灰度；再引入第二 Pack 验证领域中立。最小执行隔离已在 S2 验收，不能延迟至本阶段才部署。

出口：

1. 明确的容量模型与硬件下达到延迟/吞吐/SLO；同时报告平均负载、峰值与 180 天保留成本。
2. 真实出口默认拒绝未授权目标，无法绕过租户/任务预算和作用域，敏感凭据不进入事件或模型上下文。
3. 完成月度恢复流程演练，验证投影、外部效果和审计链，明确达成的 RPO/RTO。
4. 第二领域通过同一内核契约与一致性套件接入；无内核业务分支改动，且不依靠相同自评场景证明通用效果。
5. 所有已接入依赖固定发行版本，保留许可证/SBOM/来源；灰度与回滚不破坏在途 run 的版本语义。

## 状态登记规则

每项任务记录设计状态、代码状态、最近测试证据和生产验证状态。实际通过后再更新；失败保留反例；依赖缺失标记具体原因，不把“计划”“存在文件”“源码检查过”写成“验收通过”。

本地 API 与 sqlite 文件只用于本阶段受控开发。生产开放、真实外部写、付费模型并发和跨租户部署应分别通过上述相应出口，再扩大范围。
